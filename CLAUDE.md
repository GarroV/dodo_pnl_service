# Контекст проекта

Сервис для партнёров Dodo в разных странах: **собирает первичные данные** и на их
основе формирует P&L единого формата.

Главное, что нужно помнить: задача проекта — облегчить **сбор и накопление**
информации. Что делать с данными потом (отчёты, аналитика, дашборды) — вторично.
Сейчас у партнёров всё в Excel и считается руками.

## Принципы

**Обкатываем на Сербии, проектируем максимально масштабируемо.** Сербия — первый
тенант и источник требований, а не архитектура. Любая страновая специфика живёт
в конфигурации, а не в коде. Если появляется `if country == "RS"` — что-то пошло не так.

**Мультитенантный SaaS.** Один инстанс, изоляция данных партнёров через RLS по
`tenant_id`. Внутренний продукт Dodo Brands.

**Три регистра учёта: `official`, `supplementary`, `internal`.** Все живут в системе.
Регистр — свойство сотрудника, группы или операции, не компании. Видимость регистра
определяется ролью пользователя, и механизм для этого есть на уровне базы. Но у
партнёра сейчас бухгалтер и оперативный директор имеют **равный** доступ — оба видят
все три регистра (D036, ответ владельца); срез по регистру реально работает у
управляющего точки (официальный и дополнительный). Доступы будут сужаться позже,
там где понадобится, поэтому механизм держим живым, а не выпиливаем. Законность
не является ограничением — это инструмент управления бизнесом, а не отчётности
для налоговой.

**Версионирование по датам везде, где есть правила.** Ставки, коэффициенты, правила
разнесения, условия найма. Изменение правила не должно ломать закрытый период.

**Закладываем больше вариантов, чем известно сейчас.** Часть механик у партнёра
неясна, вопросы висят у бухгалтера. Вместо того чтобы гадать — поддерживаем оба
варианта и выбираем тот, что сходится с их таблицей. Лишнее выпилим потом.

**Пресеты вместо голых настроек.** Чтобы избыток ручек не убил юзабилити, страна
поставляется готовым набором правил. Партнёр меняет только отличия.

## Стек

Python 3.13, Django 6.1, свой Postgres 17. Разграничение доступа — политики самой
базы (RLS), вход — Django auth. Веб-интерфейс — основной, в том числе
для управляющих точек с ограниченным доступом. Telegram — поверх собственного API,
только для быстрых сиюминутных внесений.

## Структура

```
manage.py             точка входа Django
src/config/           настройки проекта (DATABASE_URL, ATOMIC_REQUESTS)
src/core/             схема данных
  models.py           таблицы
  fields.py           enum-типы Postgres в моделях
  db_types.py         регистрация доменных типов в драйвере psycopg
  migrations/         схема, комментарии, политики RLS, роль app_user
                      0230_facts — центральная таблица фактов и сборка P&L
  rules.py            правила из базы: сборка пресета на дату и по уровням
  roles.py            форма ролей продукта: регистры, точка, права
  role_delivery.py    форма ролей доезжает до поднятой базы, не затирая правку партнёра
  management/commands/seed_dev.py     тестовые данные из обезличенной фикстуры
  management/commands/load_presets.py первичная загрузка правил стран из YAML
  management/commands/platform_admin.py право вести правила стран (вне ролей)
  management/commands/roles_sync.py   сверить форму ролей с базой и довезти её
src/payroll/          зарплатный движок: правила в конфиге, не в коде
  engine.py           расчёт
  presets.py          сборка пресета из тела и уровней переопределения
  trace.py            след расчёта: какие правила сработали и с какими входами
  presets/*.yaml      правила стран — источник ПЕРВИЧНОЙ загрузки в базу
  importers/          импорт таблиц партнёров (формат у каждого свой)
src/payrun/           расчёт периода целиком: база → движок → ведомость
src/web/              интерфейс: страницы, контекст пользователя в базе
docs/architecture.md  ЧТО за продукт, поверхности, сценарии, глоссарий — начинать отсюда
docs/user-guides.md   материалы для людей: гайды и когда их обновлять (правило владельца)
docs/routes.md        карта адресов: экран → модуль. Собирается `manage.py routes --write`
docs/discovery.md     концепция, решения, открытые вопросы
docs/payroll-engine.md разбор правил Сербии и что осталось неясным
docs/document-recognition.md что забрано из проекта-предшественника по накладным
docs/forge/           документы стройки: спека, план, решения, блоки, задачи
tests/                регрессия движка + тесты схемы и доступа
```

Список выше — для ориентировки. Полная карта кода живёт в `docs/architecture.md`
(что за продукт, поверхности, сценарии, глоссарий, что в каком пакете) и
`docs/routes.md` (все адреса → модуль). Список выше подробностей не дублирует
нарочно.

Насколько им можно верить: `routes.md` собирается из кода и сверяется целиком —
разошлась хоть на один адрес, прогон красный. У `architecture.md` тестом закрыт
только инвентарь пакетов (в обе стороны: нет забытого и нет ссылок на удалённое).
Продуктовая рамка, сценарии и глоссарий там написаны руками и проверяются
чтением — как и должно быть, сгенерировать их нельзя.

Схема ведётся миграциями Django. Всё, чего Django не видит — enum-типы, функции
контекста, политики RLS, роль приложения, — пишется руками через `RunSQL`.
Движок `src/payroll/` остаётся чистым Python без ORM: Django его вызывает,
но не переписывает.

## Стенд и демо: сначала проверить, потом утверждать

Площадка MUSPELHEIM **общая**: рядом с нашим стендом живут чужие проекты, и один из
них занимает корень публичного адреса. Поэтому ни одно утверждение о стенде не
делается по памяти о коде — только по факту:

```bash
python tools/stand.py            # площадка: наше против чужого, версия, публичность
python tools/stand.py --host local
```

Скрипт отвечает на четыре вопроса разом: какие контейнеры **наши** (префикс
`dodo-pnl`, всё остальное — чужой проект, не трогать), совпадает ли код стенда с
`origin/master`, доехала ли дизайн-система в **каждый** образ, и что реально
опубликовано в интернет и чьё оно.

Куплено ошибками 22.08.2026, обе — утверждения без проверки:

- «демо уже выглядит как продукт» — на стенде стоял образ пятидневной давности;
- «публичный адрес уже включён» — включён он был для чужого проекта, и владелец,
  открыв ссылку, увидел не наш продукт.

Три правила, которые из этого следуют:

1. **Демо живёт под профилем compose.** Обычный `docker compose up -d` его не
   трогает: демо остаётся на старом образе молча. Поднимать
   `docker compose --profile demo up -d`.
2. **Код на стенд едет только через GitHub.** У площадки ключ развёртывания на
   чтение (`~/.ssh/dodo_pnl_deploy`), `origin` там переключён на SSH. Значит
   локальные коммиты сначала пушатся, иначе стенд обновится в никуда.
3. **Публичный адрес** — `https://muspelheim.tail48dfee.ts.net:8443` → демо (8010).
   Корень `:443` занят чужим проектом и не трогается. Продукт (8030) наружу
   **не** публикуется: демо изолировано отдельной базой и тестовыми данными, а
   продукт — нет.

## Тесты

```bash
pip install -e ".[dev]"       # нужен Python 3.13
pytest
```

Тесты схемы (`tests/test_schema_access.py`, `tests/test_seed_dev.py`) сами
создают временную базу, накатывают миграции и удаляют её за собой. Нет
доступного Postgres — пропускаются.

Покрытие меряется вместе с подпроцессами — `manage.py` тесты гоняют настоящим
подпроцессом, иначе проверялось бы не то, что запускает человек:

```bash
COVERAGE_PROCESS_START=$PWD/pyproject.toml pytest --cov
```

Тест доступа обязан гоняться ролью `app_user` (`as_app_user` в `conftest.py`):
владелец таблиц и суперпользователь обходят RLS, поэтому политики можно написать
неправильно и получить зелёный прогон. Проверено на живой базе — именно так
дефект видимости регистров и прожил незамеченным.

Постоянная регрессия — `tests/test_regression_sample.py` на обезличенном файле
`tests/fixtures/plata-sample.xlsx` (пересобрать: `python tools/make_fixture.py`).
Она ловит изменение поведения движка, но не сходимость с бухгалтерией.

Данные партнёров в репозиторий не кладём никогда — там ФИО и суммы живых людей.
Настоящая таблица подключается путём в `PAYROLL_FIXTURE`; без неё сверка пропускается.

`tests/test_serbia_june_2026.py` — главный тест. Движок должен воспроизводить расчёт
бухгалтерии Сербии за июнь 2026 до копейки: 30 сотрудников, четыре схемы расчёта.
Если он красный, правила разъехались с реальностью.

## Порядок работ

Продуктовая карта на годы вперёд: идём от самой больной точки, автоматизируя
таблицы партнёра по одной. Это не план текущих работ — он в `tasks.md`.

1. Ядро — тенанты, роли, справочники, версионирование ✅
2. Зарплатный движок — сходится с таблицей бухгалтерии, месяц считается в браузере ✅
3. Ручной ввод и наличные — веб-формы, API, расходы из кассы, НДС ✅
4. Платежи поставщикам — контрагенты, счёт и платёж разными событиями,
   разнесение по точкам, инбокс классификации ✅
5. **Часы и оплата труда целиком** ← здесь сейчас (D053, решение владельца
   26.08.2026). Движок считает, но формы оплаты бедны: есть только почасовая
   ставка с коэффициентом и сдельные меры. Нужны оклад, именованные надбавки,
   должности с вилкой ставки, гарантия часов по договору, массовые изменения
   условий и предпросчёт «что попадёт в расчёт» до расчёта месяца
6. Импорт банковской выписки
7. Коннектор Dodo IS — выручка, сырьё, списания, часы
8. Классификатор документов — разбор + очередь на подтверждение
9. Сборка P&L — агрегация, консолидация в EUR
10. Сверки и аналитика
11. Telegram поверх готового API

## Что дальше по зарплатам

**Текущий план работ живёт в одном месте — `tasks.md`** (граф задач со статусами
и зависимостями), а вопросы, ждущие ответа бухгалтера, — в
`docs/forge/questions.md`. Здесь список не дублируется: копия плана разъезжается
с графом молча, и тогда непонятно, какой из двух настоящий.

Открытые вопросы предметной области разобраны в `docs/payroll-engine.md` —
там же сказано, где движок намеренно поддерживает оба варианта до ответа.

## Тон документации

Пишем по-русски, простым языком, без канцелярита и маркетинговых оборотов.
Комментарии в коде объясняют **почему**, а не что. Правила предметной области
комментируем обязательно: через полгода никто не вспомнит, откуда взялось 0,701.
