# Dodo P&L Service

Сбор первичных данных и сборка P&L для партнёров Dodo в разных странах.

Партнёры ведут управленческий учёт в таблицах: платежи поставщикам, зарплаты,
касса — всё вбивается руками каждый день. Данные разбросаны по нескольким системам
и не бьются между собой, расходы не привязаны к точкам, ошибки всплывают в конце
месяца или не всплывают вовсе. Сервис автоматизирует сбор и приводит всех
к единому справочнику статей — чтобы по сети были сопоставимые цифры.

Обкатывается на Сербии, проектируется под любую страну.

## Быстрый старт

Нужен только Docker. Больше ничего ставить не надо: Python, Postgres и схема
приезжают сами.

```bash
cp .env.example .env          # значения в примере рабочие, править не обязательно
docker compose up -d --build  # собрать образ, поднять базу, накатить миграции
docker compose run --rm migrate python manage.py seed_dev   # тестовые данные
open http://localhost:8000/
```

**Схему накатывает отдельная одноразовая служба `migrate`**, а не приложение на
старте. Руками её запускать не надо: `docker compose up` сам дожидается, пока она
отработает, и только потом поднимает приложение и рабочий процесс очереди.
Разделены они не для красоты: роль продукта намеренно не имеет права на DDL —
на этом стоит разграничение доступа, — а роль, накатывающая схему, владеет
таблицами. Локально это одна и та же роль (`POSTGRES_USER`), на площадке **три
разных**: `MIGRATION_DB_USER` (владелец схемы), `APP_DB_USER` (продукт) и
`QUEUE_DB_USER` (рабочий процесс очереди). Третья не прихоть: очередь читает
свои таблицы соединением напрямую, а роль продукта умеет там ровно одно —
поставить задачу, — и одной ролью на обе службы рабочий процесс не поднимается
вовсе (`permission denied for table django_q_ormq`). Кто в какой роли состоит и
что заводится руками при развёртывании — в `docs/forge/blocks/deploy.md`,
раздел «Роли базы на площадке».

**Форма ролей едет тем же шагом.** Какие регистры учёта роль видит и что ей
позволено — записано в коде (`core/roles.py`), а в базе роли лежат данными.
Раньше правка кода не меняла поднятую базу ничем, и это стоило двух дефектов
подряд («администратор видит 8 сотрудников из 35»; «расчёт периода не входит в
права вашей роли»). Теперь `migrate` довозит форму до базы и говорит, что
довёз. Правку партнёра он при этом **не затирает**: роль помнит, что ей ставил
продукт, и роль, отличающуюся от этого снимка, доставка показывает, а не
переписывает. Сверить, не разъехались ли база и код, — `manage.py roles_sync
--check`: список расхождений и код возврата 1, если они есть. Разбор механизма и
четыре исхода на роль — в `src/core/role_delivery.py`.

Доставку обязана выполнять роль, **обходящая RLS** (владелец схемы,
`MIGRATION_DB_USER`): `roles` под `force row level security`, и роль без обхода
увидела бы ноль строк и отчиталась бы «доставлять нечего». Отчёт это проверяет и
говорит первой строкой, если сверка ничего не доказывает.

Из этого же следует, откуда гоняются разовые работы обслуживания вроде
`seed_dev`: `docker compose run --rm migrate ...`, то есть ролью владельца.
Тестовый сид пишет в таблицы мимо контекста пользователя, и ролью продукта
политики базы его бы не пустили.

База поднимается на том же образе `pgvector/pgvector:pg17`, что стоит на площадке.

Что видно в браузере сегодня: вход по логину и паролю, список периодов, табель
с сеткой ввода часов, страница периода с кнопкой «Посчитать» и ведомость по 35
выдуманным сотрудникам. Учётки заводит `seed_dev`: логины `director`, `accountant`,
`manager`, `admin`, пароль у всех один — `SEED_USER_PASSWORD` (по умолчанию
`dodo-dev`). Пока `DEV_LOGIN=1`, на странице входа есть кнопки быстрого входа
этими учётками: кнопка подставляет тот же пароль и идёт тем же путём. **На
площадке `DEV_LOGIN=0`** — тогда кнопок нет, а выданные ими сессии перестают
действовать.

**Порты** берутся из `.env` и нигде не зашиты. По умолчанию приложение на 8000,
база на 5440 — только на `127.0.0.1`, наружу она не смотрит. Порт занят
(например, 8000 держит `runserver` из venv) — поменяйте `APP_PORT` в `.env`
и повторите `docker compose up -d`. На площадке те же переменные равны 8030 и 5440.

`APP_PORT` — порт **снаружи**; внутри контейнера приложение слушает 8000 всегда,
и проверка здоровья ходит именно туда. Разводя порты под второй стенд, править
надо только `APP_PORT`, `DEMO_APP_PORT` и `POSTGRES_HOST_PORT` — переменной с
внутренним портом больше нет (issue #107).

**Второй стенд рядом с первым** поднимается в другой рабочей копии как есть:
имя проекта Compose берётся из имени каталога, поэтому контейнеры, тома и образы
у копий свои. Хочется имя покороче — `COMPOSE_PROJECT_NAME` в `.env` этой копии.
Что бы ни случилось, `docker compose down -v` теперь уносит только свой стенд.

**Проверить, что живо:**

```bash
docker compose ps                                  # все три контейнера healthy
docker compose ps -a                               # плюс migrate — Exited (0)
docker compose exec app python docker/healthcheck.py
docker compose exec worker python docker/queue_healthcheck.py
```

Постоянно работающих контейнеров три: база, приложение и рабочий процесс очереди
(`worker`) — он считает периоды фоном. Четвёртый, `migrate`, отрабатывает схему и
выходит, поэтому в обычном `docker compose ps` его не видно: смотреть `-a`, там
он должен быть `Exited (0)`. Ненулевой код выхода означает, что схема не
накатилась, — и приложение в этом случае не поднимется вовсе, а не поедет на
старой схеме. Проверка приложения ходит и в веб, и в базу: она краснеет
не только когда упал процесс, но и когда сервер жив, а база недоступна. Проверка
очереди спрашивает не «жив ли процесс», а «разбираются ли задачи»: надзиратель
очереди бывает жив и при этом работу не берёт. Проверка, которая проходит всегда,
хуже отсутствующей.

Рабочего процесса нет или он лежит — продукт **не перестаёт считать**: страница
периода видит, что задачу никто не взял, говорит об этом словами и предлагает
посчитать прямо сейчас. Совсем без очереди работает `PAYRUN_BACKGROUND=0` —
тогда расчёт идёт прямо в запросе и прогресса страница не обещает.

**Остановить и убрать:**

```bash
docker compose down       # остановить, данные в томе остаются
docker compose down -v    # то же и стереть базу целиком
```

## Проверки

Два вида проверок, и они про разное. `pytest` (см. «Разработка без Docker» ниже)
гоняет движок и схему без браузера — быстро, но не видит экран. Смоуки в
`tools/smoke_*.mjs` — живой headless-Chrome кликает по настоящей странице
настоящими событиями мыши и клавиатуры на поднятом стенде: они ловят то, что
разбором разметки не доказать. Список — `ls tools/smoke_*.mjs`; таблицы здесь
нет намеренно, чтобы не разъезжаться с каталогом.

Смоуку нужен поднятый продукт с сидом и headless-браузер с открытым портом
отладки:

```bash
docker compose up -d && docker compose run --rm migrate python manage.py seed_dev
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
    --headless=new --disable-gpu --no-first-run \
    --remote-debugging-port=9339 --user-data-dir=/tmp/chrome-smoke &
APP=http://127.0.0.1:8000 CDP_PORT=9339 COMPOSE_PROJECT_NAME=<имя стенда> \
    node tools/smoke_timesheets.mjs
```

`APP` — адрес продукта, `CDP_PORT` — порт отладки Chrome (по умолчанию 9339).
**`COMPOSE_PROJECT_NAME` обязателен** — без него смоук откажется стартовать.
Причина не в порядке запуска, а в том, что смоук сам приводит стенд к сиду
командой `docker compose run --rm migrate python manage.py seed_dev`, а
`docker compose` без имени проекта возьмёт проект по умолчанию — то есть чужой
запущенный стенд, а не тот, что смоуку выделили.

**Два смоука требуют большего, и без этого краснеют исправным продуктом** —
проверено, оба раза выглядит как поломка, а не как ошибка запуска:

- `smoke_i18n` берёт список данных партнёра (имена, точки, названия схем)
  переменной `PARTNER_DATA` прямо из базы стенда — этот файл список не хранит
  намеренно, иначе в него однажды тихо доедет непереведённая строка продукта.
  Команда сбора — в шапке `tools/smoke_i18n.mjs`, оттуда и копировать. Без
  переменной смоук считает русскими **данные** и даёт 19 ложных красных;
- `smoke_demo` идёт на **демо-стенд**, а не на продукт: `APP` — адрес демо
  (`DEMO_APP_PORT`, обычно `http://127.0.0.1:8010`). На продукте маршрутов
  `/demo/*` нет вовсе (`DEMO_MODE=0`), и смоук падает на переходе по пустой
  ссылке.

Договор смоука о состоянии стенда (T098, канонический источник — шапка
`tools/cdp.mjs`) — три правила, обязательные для каждого `smoke_*.mjs`:

1. смоук сам приводит стенд к сиду в начале, не рассчитывая на то, что это
   сделал кто-то до него;
2. он ничего за собой не оставляет — возврат к сиду зарегистрирован через
   уборку и срабатывает даже при падении на полпути;
3. он сам задаёт себе размер окна браузера, а не полагается на то, что дал
   Chrome по умолчанию.

Из первых двух правил следует, что смоуки можно запускать в любом порядке и
по одному, не думая, кто был запущен раньше. Платится за это лишней минутой на
два сброса стенда (в начале и в конце) — это цена изоляции, а не тормоза
харнесса.

### Сигнал о красном прогоне

Двое суток и 25 запусков подряд CI был красным, и об этом узнали случайно
(issue #196). Проверка, о результате которой никто не узнаёт, — не проверка,
поэтому за состоянием master следит `tools/ci_watch.py`: спрашивает у GitHub
приговор по свежему прогону и, если он красный, пишет в канал уведомлений.

```bash
python tools/ci_watch.py            # спросить и, если надо, отправить
python tools/ci_watch.py --dry-run  # показать, что отправилось бы
python tools/ci_watch.py --run <id> # разобрать конкретный прогон
```

**Почему это не шаг внутри `ci.yml`.** Канал живёт на домашнем сервере по
адресу тайлнета и наружу не опубликован. Раннер GitHub в тайлнет не входит —
маршрута до такого адреса у него нет вовсе, поэтому никакие секреты
репозитория делу не помогут: секрет нужен тому, кто может дозвониться.
Сторож поэтому ходит с машины владельца, где тайлнет есть, и никаких новых
секретов не заводит. Подробный разбор трёх выходов из этого — в шапке
`tools/ci_watch.py`.

Красным считается только приговор (`failure`, `timed_out`, `startup_failure`).
Отменённый прогон приговором не является и пропускается: у master включён
`cancel-in-progress`, и каждый пуш вдогонку отменяет предыдущий прогон —
принимать это за поломку значило бы звонить впустую по нескольку раз в день.
Состав пропусков сторож не разбирает: это уже делает
`.github/scripts/check_skips.py` внутри прогона, и пропуск без объявленной
причины приходит сюда обычным `failure`.

**Тишина — отдельная тревога, и это главное (D067).** Сигнал только о падении
молчит ровно тогда, когда молчит сам прогон: отменённый по concurrency, не
запустившийся вовсе, упавший до шага с тестами — всё это не «падение», а
отсутствие результата, и человек о нём не узнает так же, как не узнал в тот раз.
Двадцать пять запусков подряд без единого зелёного были именно тишиной, а не
серией падений. Поэтому сторож умеет сказать три вещи: «master красный»,
«master зелёный» и «по master давно нет никакого результата». Тишиной считается
отсутствие приговора среди свежих прогонов, приговор старше суток
(`CI_WATCH_STALE_HOURS`) и верхушка ветки без прогона старше получаса
(`CI_WATCH_GRACE_MIN`) — то есть «workflow не запустился».

О том же красном прогоне сообщается один раз, о возвращении к зелёному — тоже
один раз и только если до этого была тревога. Память лежит в
`~/.claude/forge/ci-watch/`, рядом с профилем канала, а не в репозитории.

Чтобы сторож срабатывал сам, а не когда о нём вспомнили, он вешается на
расписание:

```bash
tools/ci_watch_agent.sh render    # показать, что будет поставлено
tools/ci_watch_agent.sh install   # поставить (раз в 15 минут)
tools/ci_watch_agent.sh status    # состояние и хвост журнала
tools/ci_watch_agent.sh remove    # снять
```

Агент всегда нацеливается на **основную** копию репозитория, даже если позвать
его из рабочей копии (`git worktree`): рабочие копии удаляются после слияния, и
агент, нацеленный на такую, однажды молча перестал бы находить файл.

## Демо-стенд

Живое демо — **отдельный экземпляр на отдельной базе**, а не режим продукта.
Смотрящий открывает адрес, жмёт одну кнопку и попадает в наполненный продукт:
два юрлица, три точки, тридцать выдуманных англоязычных сотрудников, все четыре
схемы расчёта и все три регистра учёта, три месяца — два закрытых и один
открытый.

```bash
docker compose --profile demo up -d      # поднять стенд рядом с продуктом
open http://127.0.0.1:8010/demo/         # DEMO_APP_PORT из .env
```

Три службы, и они разделены по времени жизни: `demo-init` один раз собирает
эталон и восстанавливает из него демо, `demo` — сам стенд, `demo-reset` —
служба расписания, возвращающая демо к эталону каждые `DEMO_RESET_MINUTES`
минут. Ручной кнопки сброса нет намеренно: демо, которое чинят руками, чинят
ровно до первого дня, когда на него никто не смотрит.

**Демо изолировано от боевых данных (D016), и это проверяется, а не
подразумевается.** Сброс — это `drop database` и `create database ... template`,
поэтому ни одна демо-команда не выполняется, пока не доказано, что она работает
с демо-базой: адрес должен совпадать с `DEMO_DATABASE_URL`, в базе не должно
быть ни одного чужого партнёра, а пересоздать можно только базу, помеченную
самой же командой. Настоящие данные партнёра в демо не попадают физически:
источник у демо-набора другой (`src/demo/dataset.py`), обезличенная фикстура
здесь не участвует.

**Раздел, который ведёт другая роль, в демо не тупик.** Справочники и правила
ведёт администратор сети, а кнопка входа приводит оперативного директора — и
раздела, которого роль не ведёт, в шапке нет вовсе. В продукте это правильно:
партнёр знает своё устройство. Посетителю демо сравнивать не с чем, и он читает
отсутствующий раздел как отсутствующую функциональность. Поэтому **только в
демо** на месте такого пункта стоит ссылка «этот раздел ведёт такая-то роль —
открыть ею»: она переключает роль и приводит туда, куда посетитель шёл. Права
ролей при этом не меняются ни на копейку, и шапка продукта остаётся прежней
(`src/demo/switching.py`).

**Демо всегда англоязычное**, независимо от языка продукта: демо-службы
поднимаются с `UI_LANGUAGE=en`, а подписи правил (виды часов, надбавки,
схемы) приезжают в демо-базу переопределениями на уровне партнёра — тем же
механизмом, которым партнёр меняет любое другое правило.

Руками то же самое:

```bash
python manage.py seed_demo            # наполнить демо-базу
python manage.py demo_reset           # вернуть демо к эталону
python manage.py demo_reset --rebuild-template   # пересобрать эталон (после выкладки)
```

## Переменные окружения

Единственный канонический список: значения — в `.env` (в git не попадает),
имена и безопасные значения по умолчанию — в `.env.example`. Скопировали пример,
поменяли пароль и ключ подписи — окружение рабочее.

| Переменная | Кто читает | Смысл |
|---|---|---|
| `SECRET_KEY` | Django | Ключ подписи сессий. На площадке обязательно свой |
| `COMPOSE_PROJECT_NAME` | compose | Имя стенда: свои контейнеры, тома и образы. Не задано — берётся имя каталога рабочей копии, и это безопасно: каталоги у копий разные. Пока имя было зашито в `docker-compose.yml`, `up` из соседней копии переставлял порты чужому стенду, а `down -v` уносил чужую базу (issue #51) |
| `DJANGO_DEBUG` | Django | `1` — трассировка на 500 и раздача статики под `runserver`; на площадке `0`. Страницы 404 и 403 человек видит продуктовыми при любом значении (T099) |
| `DJANGO_ALLOWED_HOSTS` | Django | Имена хостов через запятую, без пробелов |
| `DJANGO_SETTINGS_MODULE` | Django | Модуль настроек |
| `DEV_LOGIN` | `web` | Кнопки быстрого входа учётками сида на странице входа. Не отдельный способ проверки личности: подставляют пароль сида. Умолчание — по `DJANGO_DEBUG`; **на площадке `0`** |
| `SEED_USER_PASSWORD` | `seed_dev`, `web` | Пароль учёток тестового сида и кнопок быстрого входа. Данные для разработки, не секрет площадки |
| `DATABASE_URL` | приложение, `manage.py`, тесты | Подключение к базе. С хоста — `127.0.0.1:5440`, внутри compose собирается из `POSTGRES_*` с хостом `db` |
| `DEMO_DATABASE_URL` | `seed_demo`, `demo_reset` | Адрес демо-базы. Он же предохранитель: команда демо не выполняется, если подключена не сюда. Рядом заводится эталон `<имя базы>_template` — своей переменной у него нет |

## Разработка без Docker

Движок, тесты и `manage.py` работают и напрямую. Нужны Python 3.13+ и Postgres
16+ (на площадке — 17); базу удобно взять из compose, она слушает на 5440.

```bash
python3.13 -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"

set -a; . ./.env; set +a          # DATABASE_URL, DODO_TEST_ADMIN_DSN и прочее
python manage.py migrate          # схема с нуля
python manage.py seed_dev         # тестовые данные

pytest
```

Ожидаемый результат — 2507 зелёных тестов и 8 пропущенных (прогон 2026-09-02).

Пропущенные — это сверка с настоящим расчётом бухгалтерии Сербии за июнь 2026.
Та таблица содержит ФИО, ставки и суммы живых людей, поэтому в репозитории её нет
и не будет. Если файл у вас есть, укажите путь и получите полную сверку:

```bash
PAYROLL_FIXTURE=/путь/к/plata-2026-06.xlsx pytest    # пропущенных не остаётся
```

Тесты схемы и сида сами создают временную базу, накатывают миграции и удаляют её
за собой. Нет доступного Postgres — они пропускаются, остальной прогон остаётся
зелёным. Куда подключаться, задаёт `DODO_TEST_ADMIN_DSN`.

Постоянная регрессия гоняется на обезличенном файле `tests/fixtures/plata-sample.xlsx`:
та же структура и те же четыре схемы расчёта, выдуманные люди. Он пересобирается
командой `python tools/make_fixture.py`. Важно понимать границу: зелёный прогон без
`PAYROLL_FIXTURE` означает «движок не изменился», а не «сходится с бухгалтерией».

## Что уже работает

**Зарплатный движок.** Правила начисления лежат в **базе** и версионируются по
датам; YAML-пресет остался источником первичной загрузки — её делает
`manage.py load_presets`. Движок про Сербию ничего не знает. Проверен на реальных
данных: воспроизводит расчёт бухгалтерии за июнь 2026 до копейки по всем
30 сотрудникам и четырём схемам расчёта.

Правил в базе нет — расчёт **отказывается считать** и называет команду загрузки,
а не подхватывает файл молча: иначе он прошёл бы мимо переопределений партнёра,
выглядя правильным.

```python
from payroll import Employee, PayrollEngine, Timesheet, load_preset

engine = PayrollEngine(load_preset("serbia-2026"))

slip = engine.calculate(
    Employee(
        ext_id="0101990800123", name="Петар Петровић",
        group="kitchen", scheme="standard",
        base_rate=371, coefficient=1.181,
    ),
    Timesheet(
        hours={"regular": 152, "vacation": 16, "sick": 8},
        insured_hours=176, norm_hours=176,
    ),
)

print(slip.net, slip.gross, slip.contributions, slip.total_cost)
for component in slip.components:
    print(component.code, component.amount, component.ledger, component.channel)
```

Расчёт возвращает не одно число, а набор компонентов. У каждого свой регистр учёта
(`official`, `supplementary`, `internal`), канал выплаты (банк или касса)
и признак налогообложения.
Из этого собирается и ведомость к выплате, и строки P&L, где зарплата и налоги
идут раздельно.

**Схема БД** миграциями Django: тенанты, оргструктура, роли с видимостью
регистров учёта, справочник статей, контрагенты с версионируемыми правилами
разнесения по точкам, зарплатные таблицы.

**Центральная таблица фактов.** Все первичные события — выручка, сырьё, фактуры,
зарплата, наличные из кассы, переводы, налоги — стекаются в одну таблицу `facts`,
из которой собирается P&L (`pnl_lines`, `pnl_by_unit`, `pnl_by_network`). Строка
факта это позиция документа, а не документ: накладная с едой и канцелярией даёт
два факта с разными статьями. Повторная загрузка того же события ничего не
меняет (ключ идемпотентности считает источник), правка идёт заменой версии, а не
поверх старой, и закрытый месяц не принимает правок ни одним путём записи.
Расход на юрлицо целиком приходит без точки и разносится правилом — поровну,
пропорционально выручке или на фиксированную точку; сумма детей сходится с
родителем до копейки. Факт, для которого правила нет, остаётся видимым в списке
нераспределённых, а не исчезает.

**Расход из кассы вносится с экрана** — своей точкой, своей статьёй и своей
кассой. Касса это справочник: у точки их может быть несколько, у каждой своя
точка и свой регистр учёта, и регистр расхода приезжает **из кассы**, а не
выбирается к каждой трате (D039). Остаток по кассе продукт не ведёт и вести не
будет (D040): касса нужна как источник денег и признак регистра, а не как
кассовая книга. Роль видит только кассы своих точек и только в видимых ей
регистрах — режет это RLS, а не выборка экрана.

**Цикл периода расчёта.** Статусы `draft` → `calculated` → `approved`, откат даёт
явный `reopened` — по журналу видно, что период открывали. Разрешённых переходов
ровно четыре, всё остальное отвергает база; утверждённый расчёт не меняется и не
удаляется **ни одним путём записи**, включая чистый SQL и суперпользователя.
Держат это триггеры, а не политики: политики суперпользователя не касаются.
Каждый переход попадает в журнал `payrun_transitions`, и его тоже пишет триггер —
поэтому перехода без записи в журнале не бывает. Утверждение и откат делаются со
страницы периода; откат требует причины, и она попадает в историю рядом с именем
автора. Спорную строку ведомости можно заморозить по одному человеку: месяц
закрывается вместе с ней, а пересчёт её обходит стороной.

Учётный месяц закрывается **вместе с утверждением расчёта** и открывается
обратно вместе с откатом — отдельного действия нет и не нужно: сегодня месяц
закрывает только зарплата. «Закрыт» — состояние, а не история: месяц, расчёт
которого откатили, снова открыт, а то, что его утверждали, осталось в журнале
переходов. Ставить `periods.status` руками нельзя — его задаёт расчёт, и это
тоже держит триггер.

**Правки задним числом.** Если данные закрытого месяца изменились после
утверждения — правили часы, поменялось правило расчёта или условия найма, —
страница периода показывает расхождение построчно и предлагает **перенести
разницу** в первый неутверждённый месяц. Закрытый период при этом не
переписывается: разница ложится в получателя отдельной строкой с пометкой «за
какой месяц» и **в тот же регистр учёта**. Как партнёр ведёт такие правки —
переносом или пересчётом через явное переоткрытие — решает настройка тенанта
`tenants.retro_mode`, а не переменная окружения.

Двойного счёта не бывает, и держат это два правила базы: пересчёт
месяца-источника **отменяет** уехавшую из него разницу (триггером, то есть
пересчёта без отмены не случается вовсе), а месяц, разница за который уже
утверждена у получателя, заново не открывается — деньги выплачены.

**Разграничение доступа в самой базе.** Приложение ходит ролью `app_user` — она
не владеет таблицами, не суперпользователь и не имеет `bypassrls`. На всех
таблицах с `tenant_id` включён `force row level security`, политика изоляции
тенанта пермиссивная, политики видимости регистров — ограничивающие
(`as restrictive`), иначе они складывались бы через OR и не сужали доступ.
Контекст пользователя приходит в GUC `app.user_id` внутри транзакции запроса,
поэтому забытый фильтр даёт пустой результат, а не чужие строки.

**Тестовые данные.** `manage.py seed_dev` наполняет чистую базу выдуманными
людьми из обезличенной фикстуры: три точки, 35 сотрудников, четыре учётки с
разной видимостью регистров и точек, один открытый период.

**Сверка с таблицей бухгалтера и выгрузки.** Со страницы периода загружается
таблица, в которой бухгалтер считает зарплату руками, и сравнивается с расчётом
построчно — до копейки, без допуска; расхождение меньше динара названо
округлением отдельной группой. Каждое расхождение объясняет себя входами: часы,
ставка, коэффициент, надбавка. Загруженный файл нигде не сохраняется — в нём ФИО
и суммы живых людей (D028). Роли, которой база не отдаёт итоги расчёта, сверка
показывает не пустой экран и не мнимое совпадение, а сверку входов: они от
регистра учёта не зависят.

Оттуда же скачиваются три книги xlsx — ведомость к выплате, строки для P&L
(начисления и налоги раздельно) и вид, привычный бухгалтеру партнёра. Все три
берут тот же срез с тем же разрезом, что показан на экране, поэтому файл не
может разойтись с увиденным, а регистр, которого человеку не видно, не попадает
в файл физически.

**Справочники ведутся с экрана.** Сотрудники, группы, точки, юрлица и
производственный календарь — пять разделов; ведёт их роль с правом
`directory.manage` (в сиде это администратор сети).

У сотрудников это право решает не «видно или нет», а «правка или чтение» (D047).
Список и карточку читает каждый, кого завели к партнёру, а строки режет база:
управляющий точки видит людей своей точки и не видит чужих — чужая карточка
отвечает ему «не найдено», как несуществующая. Нужно это для работы: ставок в
Dodo IS нет вовсе (это условия найма, наши данные), и проверить их управляющий
может только здесь. Читателю показываются факты вместо форм, сквозной ключ
(в Сербии JMBG) не показывается вовсе, а сумм расчёта на этих экранах нет.

Карточки сотрудников экраном не заводятся: они приходят из данных партнёра, а
править их — можно.

Правка условий найма **заводит новую версию** с даты, а прежнюю закрывает: ставка
меняется вперёд, а не задним числом, и закрытый месяц пересчитывается теми же
числами. Правку, которая задела бы утверждённый месяц — версию с датой внутри
него, смену схемы расчёта группы, норму часов, — экран отклоняет и называет
месяц, из-за которого отказано; обходится это переоткрытием месяца с причиной.

Право спрашивается дважды: интерфейс не показывает того, что запретит, а база не
даёт записать мимо интерфейса — политики на всех шести таблицах справочника.
Календарь общий для страны, поэтому право на него считается по стране тенанта.

**Правила расчёта — тоже с экрана.** Раздел «Правила» у роли с правом
`rules.manage` — реестр: правило ищется по коду, у каждого значения написано,
откуда оно взялось (набор страны, настройка партнёра, версия группы или
человека) и с какого числа. Правка заводит новую версию с датой, а прежнюю
закрывает — тем же способом и по тому же доводу, что у условий найма, поэтому
уже посчитанный месяц от неё не двигается.

**Кому адресована правка — выбирается на форме**: всему партнёру, одной группе
сотрудников или одному человеку. Уровни складываются, человек сильнее группы,
группа сильнее партнёра — тем же порядком, каким их читает расчёт. Правило,
адресованное кодом группы (`groups.<код>.…`), ниже партнёра завести нельзя, и
отказ говорит почему: после перевода человека в другую группу такое
переопределение молча перестало бы применяться, поэтому его поимённые свойства
живут в условиях найма.

**Набор правил самой страны тоже виден в продукте** — значение, дата, история
версий, — но правит его не партнёр: тело общее для всех партнёров страны, и
правка с экрана одного поменяла бы расчёт другому. Право лежит вне роли, в
таблице `platform_admins`, и выдаётся командой `manage.py platform_admin`. Правка
страны заводит новую версию пресета с датой; уже посчитанные месяцы собираются
своей версией и не двигаются, а повторный `load_presets` такую версию не
перезаписывает и говорит, что пропустил.

Оттуда же переключается способ оплаты группы (часы, доставки, фиксированная
выплата) — он же продублирован полем в карточке группы, потому что человек ищет
его там. Смена способа — такая же версия правила с датой.

## Как устроены правила

Правило может быть задано на четырёх уровнях, каждый следующий переопределяет
предыдущий: **страна → партнёр → группа сотрудников → конкретный человек**.
Всё версионируется по датам, поэтому изменение правила не ломает закрытые периоды.

Новая страна — это новый YAML-пресет, а не новый код. Пресет заводится в базу
командой `manage.py load_presets` (идемпотентно), и дальше правила читаются
оттуда: расчёт всегда берёт версию, действующую на дату периода.

```python
from core.rules import load_rules_at

rules = load_rules_at(tenant_id, "RS", date(2026, 6, 30))
preset = rules.preset(group_id=..., employee_id=...)
```

Переопределения уровней (партнёр, группа, человек) заводятся строками в
`rule_overrides` и тоже действуют с даты. Все три заводятся с экрана правил —
адресат выбирается на форме. Тело пресета страны правится там же, но отдельным
правом (`platform_admins`) и не переписыванием, а новой версией `rule_presets`.
