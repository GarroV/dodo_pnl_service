# Dodo IS API: что там есть и что нам из этого нужно

> Выписано из официальной документации `docs.dodois.io` (раздел English
> Documentation) 2026-08-17. Документация публичная, читается без входа; ссылка
> на неё лежит и в Базе знаний («Документация Dodo IS API», пространство
> «Техподдержка»). Файл — **конспект для планирования шестой очереди**, а не
> копия документации: за истиной идти в первоисточник, здесь только то, что
> касается нас, и вывод, который из этого следует.

## Доступ: что нужно на самом деле

Вчерашний вывод «коннектор упирается в модерацию» был **неверен**, и вот
почему. На странице каждого метода написано «API access is granted after the app
is published in the Dodo IS Marketplace and passes moderation», но в разделе
«Начало работы» на `docs.dodois.io` порядок другой и короче:

1. создать приложение в **личном кабинете разработчика**
   (`marketplace.dodois.io/manage/apps`), выбрав способ авторизации;
2. получить `Client Id` и `Client Secret`;
3. получить токен по руководству (OAuth 2.0);
4. звать API — для большинства методов нужна учётная запись пользователя Dodo IS.

**Публикация в маркетплейсе — про РАСПРОСТРАНЕНИЕ приложения другим франчайзи,
а не про доступ к API для себя.** В инструкции «Как разместить своё приложение в
маркетплейсе» начальное условие звучит дословно: «У вас уже есть приложение,
которое использует API». То есть сначала работающая интеграция, потом витрина.

Что несёт публикация, если однажды до неё дойдём: подписочная модель и тарифы,
интеграция с сервисом лицензий, требование «три клика от подписки до первого
результата», модерация командой маркетплейса (проверяют в режиме пользователя,
могут проверить безопасность, если приложение работает с чувствительными
данными), заведение реквизитов для платежей. Почта для связи —
`marketplace@dodois.io`.

Для нас сейчас это значит: **шестая очередь ничем не заблокирована**. Нужен
только заведённый в кабинете разработчика клиент и учётка Dodo IS у партнёра.

## Аутентификация

- OAuth 2.0, два потока по документации: **Franchisees_Authorization** (от имени
  человека) и **Franchisees_Service Token** (от имени приложения). На практике в
  кабинете разработчика второй не предлагается вовсе — см. «Как начать».
- Сервер авторизации — `auth.dodois.io`, база API — `https://api.dodois.io/…`.
- У сети есть идентификатор концепции (`businessId`), он приезжает в вызовы:
  `63d4829611ea45c8ae71394860a2481c` — Dodo Pizza,
  `c0b18e725258427a8bffea4f73957b0e` — Drinkit.

Для нашего продукта это ложится на уже принятую модель: токен — секрет площадки
(в `.env`, не в репозитории), а срез данных задаёт сам Dodo IS по правам
приложения, как у нас его задаёт база.

## Что нам нужно, по нашим очередям

### Шестая очередь — коннектор. Порядок задан владельцем (D044)

**Сначала часы, потом сырьё и списания, потом выручка с разбивкой.** Ничего из
этого не стопорит текущие очереди — коннектор кормит их данными, а не заменяет.

Порядок совпадает с ценой ручной работы: часы вбиваются в табель каждый месяц
руками, это самая дорогая рутина у партнёра.

**Шаг 1 — часы**

| Что нужно | Метод в Dodo IS API |
|---|---|
| Фактические смены по точке | `Team → Employee shifts (by pizzeria)` |
| Смены по конкретному человеку | `Team → Employee changes (by ID)` |
| Графики (плановые часы) | `Team → Schedules`, `Schedules: predictive metrics` |
| Справочник людей и должностей | `Team → Employee List`, `Employee information`, `Employee Positions` |
| Справочник точек | `Units → Information about units`, `Shifts of units` |

Наш табель при этом никуда не денется: он остаётся местом, где часы правят и
подтверждают, а коннектор станет ещё одним путём ввода, наравне с загрузкой
таблицы. Есть готовый пример на Python — «Построение расписания смен сотрудников»
(`github.com/dodobrands/partner-api-examples`).

**Шаг 2 — сырьё и списания**

| Что нужно | Метод |
|---|---|
| Списания сырья и продуктов | `Accounting → Written-off raw materials`, `Written off products`, `Discarded products` |
| Списание в производство | `Inventory → Write-offs of raw materials to production` |
| Питание персонала (вопрос Q007 про топли оброк) | `Accounting → Team meals` |
| Движение и остатки | `Accounting → Raw material movements`, `Warehouse balances`, `Raw material receipts` |

**Шаг 3 — выручка с разбивкой**

| Что нужно | Метод |
|---|---|
|---|---|
| Выручка по точке за день | `Finance → Day sales by unit` |
| Выручка по точке за месяц и за период | `Finance → Monthly sales by unit`, `Sales by unit for the period` |
| Выручка по стране (сверка итогов) | `Finance → Country Day Sales`, `Monthly national sales` |
| Продажи для разнесения по статьям | `Accounting → Sales` |

**Чего в API нет для нас.** Ни зарплатных начислений, ни налогов, ни платежей
поставщикам — то есть первые пять очередей нашего продукта коннектор не
заменяет. Есть `Team → One-time bonus`, `Premium to remuneration per hour`,
`Position premium…` — это **запись** премий в Dodo IS; возможный обратный путь,
но он про их учёт, а не про наш P&L.

### Четвёртая очередь — платежи поставщикам

`Accounting → Vendor List`, `List of local suppliers`, `Supplies → Raw material
receipt(s)`, `Manufactures → Unit orders`, `Delivered orders`. То есть
справочник поставщиков и поставки у Dodo IS свои. Заводя своих контрагентов
(T150), стоит держать в голове, что однажды их придётся сводить с этим списком —
и ключ сопоставления лучше предусмотреть сразу, а не искать потом по названию.

## Что ещё есть в API и что из этого нам полезно

> Перечень сверен 2026-08-20 по **коллекции Postman** (`dodobrands/dodo-api-postman-collection`,
> файл `dodo-is-api-postman-collection.json`, единственный коммит 13.08.2025) — она
> называет точные пути, чего сайт документации не отдаёт машинно (Stoplight —
> SPA, `curl` получает пустую оболочку). Важная оговорка: **коллекция неполна** —
> финансовых методов в ней нет вовсе, хотя в документации они есть. То есть
> коллекция хороша для путей, дока — для полноты; расходятся — верить доке.

Путь строится как `/{концепция}/{страна}/{раздел}/{метод}` — в коллекции это
`/dodopizza/{country}/…`. Значит коннектор параметризует и страну, и концепцию
(у Drinkit свой `businessId`), а не только точку — это ложится на нашу
мультитенантность без специальных случаев.

**Разделы и объём:** Учёт 25 методов, Команда 19, Производство 9, Рейтинги 8,
Доставка 4, Заведения 4, Auth 3, Оргструктура 2, Инвентаризация, Найм, Заказы —
по одному.

### Полезно нам сверх запланированного (D044)

| Что берём | Метод | Зачем именно нам |
|---|---|---|
| Точки пользователя и его данные | `auth/roles/units`, `connect/userinfo`, `auth/roles/list` | Вход через Dodo IS вместо своих паролей и **автоматическая привязка управляющего к его точкам**: сейчас `unit_ids` ведутся руками (D047, T173) |
| Число доставок курьера | `delivery/couriers-orders`, `staff/couriers-on-shift` | Мера для **сдельной оплаты курьеров** — она уже поддержана движком (D032, T075), но вводить число доставок сегодня некому |
| Питание персонала | `accounting/staff-meals` | Прямо про открытый вопрос Q007: топли оброк в зарплате и списанный продукт в статье «Питание персонала» — двойной учёт видно только если обе цифры рядом |
| Юрлица и точки | `organization-structure/legal-entities`, `legal-entity-types`, `units/shifts`, `units/work-stations` | Наполнение наших справочников и ключ сопоставления вместо ручного ввода |
| Люди, должности, история должностей | `staff/members`, `members/search`, `staff/positions`, `positions/history` | Заведение сотрудника из интерфейса (T164) и версионирование условий: история должностей уже датирована — ложится на наши версии по датам |
| Начисленное в Dodo IS | `staff/incentives-by-members`, `staff/incentives/premium` | Сверка: их премии против нашего расчёта. Не замена движку — налогов и схем Сербии там нет |
| Цели на месяц | `units/month-goals` (GET, PATCH) | План выручки → план-факт в P&L. Единственное место, куда мы могли бы и **писать** план |
| Себестоимость целиком | `accounting/stock-consumptions-by-period`, `incoming-stock-items` (+`/by-supply`), `inventory-stocks`, `stock-transfers`, `inventory/revisions`, `dough-consumption` | COGS считается не только списаниями: приход минус остаток с ревизией — то, что бухгалтер сводит руками |
| Потери | `accounting/write-offs/products`, `write-offs/stock-items`, `defective-products`, `cancelled-sales` | Отдельные строки P&L и объяснение расхождений выручки |
| Поставщики | `accounting/suppliers`, `local-suppliers` | Сведение с нашими контрагентами — ключ `external_id` заведён заранее (T150) |
| Сопоставления идентификаторов | `accounting/mapping/products`, `mapping/cashboxes`, `mapping/stock-items` | Понадобятся, когда придётся связывать наши строки с кассами и фискальными данными |

### Что есть, но нам не нужно (по крайней мере сейчас)

Рейтинги (клиентский опыт, стандарты, апелляции), Производство (производительность,
время выдачи, стоп-продажи, нагрузка), Доставка кроме заказов курьеров, Заказы
(статистика по клиентам), Найм (отклики, вакансии), дни рождения. Это
операционная и HR-аналитика: к сборке P&L отношения не имеет, к аналитике по
кадрам (T167) — разве что численность и вакансии.

### Обратный путь: куда API позволяет писать

`POST accounting/write-offs` (списание), `POST staff/incentives/premium/{one-time,hourly,position}`
(премии), `POST`/`DELETE staff/schedules` (расписания), `PATCH units/month-goals`
(цели). То есть однажды продукт может не только читать, но и возвращать в Dodo IS
то, что посчитал у нас — премии в первую очередь. В скоуп это не входит и
входить не просится: запись в чужую систему учёта — отдельный класс риска.

## Как начать, когда дойдём

1. Завести приложение: `marketplace.dodois.io/manage/apps` — выбрать поток
   авторизации. **В форме кабинета выбор всего из двух** (проверено на живой
   форме 2026-08-21): `Authorization Code Flow` и `Device Flow`. Обещанного
   документацией сервисного токена (`Franchisees_Service Token`, он же Client
   Credentials) в списке НЕТ — значит планировать нужно на потоке от имени
   человека, а сервисный, если он вообще выдаётся, спрашивать у техподдержки.
   **Client Id выдаётся под конкретный поток**: клиент от одного потока для
   другого не годится.

   Форма спрашивает: способ добавления (создать новое или подключить уже
   выданные Clients), название приложения, способ авторизации, название
   организации, контакт для связи (WhatsApp или Telegram) и согласие с публичной
   офертой. Полей `redirect_uri` и scope в ней нет — адрес возврата всплывёт
   дальше (он нужен только для Authorization Code), скоупы запрашиваются в самом
   запросе токена. Client Id и Secret показываются сразу после создания.
2. Скоупы брать со страницы нужного метода, раздел «Security: OAuth 2.0»;
   несколько — через пробел. Для обновляемого токена добавить `offline_access`.
3. Первые запросы — готовой коллекцией Postman
   (`github.com/dodobrands/dodo-api-postman-collection`): она же служит
   песочницей, токен живёт несколько часов.
4. Руководства: «Работа с oauth Dodo IS», «Построение расписаний смен через API»
   — ссылки на них лежат на `docs.dodois.io` в разделе «Руководства и примеры».

## Что нужно, чтобы потом брать другие данные

> Источник — статья-стандарт «Partner API — точки интеграции „Додо ИС“» в Базе
> знаний (пространство «Стандарты управления и внедрения в Евразии», обновлена
> 19.06.2025). Она отвечает на вопрос, которого нет в технической документации:
> расширение набора данных — это не только новый вызов в коде.

**Данные поделены на четыре класса, и от класса зависит, что нужно для доступа.**
Это главное, что стоит знать заранее: «взять ещё одну цифру» иногда бесплатно, а
иногда требует роли у учётки партнёра и его повторного согласия.

| Класс | Примеры из статьи | Что нужно, чтобы получить |
|---|---|---|
| Публичные | **выручка за день**, агрегированные метрики точек, единые справочники, адреса, сведения о юрлицах | Ничего сверх токена: приложение авторизуется само, разрешение пользователя не нужно |
| Непубличные | **смены сотрудников**, перемещения сырья, метрики доставки за период, неагрегированные метрики с историей | Токен приложения; данные закрытые, но делегирования от человека не требуют |
| Конфиденциальные | **персональные данные сотрудников**, коммерческая тайна партнёра, **детализированная структура продаж** | Согласие пользователя И **соответствующие роли у его учётки** в Dodo IS. Узкая учётка не отдаст их даже с правильным scope |
| Строго конфиденциальные | данные клиентов, сырые события производства | **Никогда не будут доступны через API** — на них не стоит планировать ничего |

Отсюда практический вывод для нашего порядка (D044): часы — это смены, то есть
непубличные; выручка за день — вообще публичная; а вот детализация продаж и ФИО
сотрудников — конфиденциальные, и на них понадобится учётка партнёра с ролями,
а не только наш клиент.

**Что именно меняется, когда набор данных расширяется:**

1. **Scope в запросе токена.** Скоупы берутся со страницы каждого метода;
   новый метод — новый scope. Для обновляемого токена нужен `offline_access`.
2. **Повторное согласие партнёра** — если добавились конфиденциальные данные.
   Человек снова видит окно «приложение получит доступ к…» и подтверждает. На
   публичных и непубличных этот шаг не нужен.
3. **Роли учётки, под которой ходим.** Расширяются не в нашем кабинете, а внутри
   Dodo IS у самого партнёра.
4. **Второй клиент, если нужен другой поток авторизации.** Client Id выдаётся под
   поток; сервисный токен и вход от имени человека — это два клиента, а не
   переключатель у одного.
5. **Чего в API нет — можно попросить.** Статья прямо говорит: запросы на
   разработку новых методов принимает техподдержка (`support@dodopizza.com`),
   есть чат разработчиков в Telegram. То есть отсутствие метода — не тупик, а
   срок.

**Чтобы это не превращалось в стройку на нашей стороне**, коннектор должен быть
устроен как правила: источник данных — строка в конфигурации (метод, период,
куда маппится), а не ветка в коде. Тогда «брать ещё и это» — настройка, а не
релиз. Из того же принципа: `external_id` нужен не только контрагентам (T150), а
всем справочникам, которые однажды придут из Dodo IS — точкам, юрлицам,
сотрудникам, должностям.

**Личный кабинет разработчика** — в документации `marketplace.dodois.io/manage/apps`,
в статье Базы знаний `marketplace.dodois.io/dev/apps`; регистрация через
гугл-почту. Расхождение не проверено фактически — проверим при заведении клиента.

## Что осталось невыясненным

- Нужен ли отдельный доступ на каждого партнёра-франчайзи (у каждого свой
  контур?) — на нашем случае это Сербия, и учётка нужна их.
- Есть ли песочница: в документации указан только mock-сервер Stoplight
  (`https://stoplight.io/mocks/dodo-brands/english-documentation/1915948546`),
  а он отдаёт примеры из схемы, а не данные.
- Полный список scope'ов — на странице метода они не перечислены, видно только
  название потока авторизации.
- Ограничения по частоте запросов и глубине истории.
- Есть ли финансовые методы в коллекции Postman: их там нет (проверено
  2026-08-20), а в документации есть. Пути к выручке придётся выписывать с
  сайта документации руками — машинно он не читается.
- **Километраж курьера в API не найден** (проверено 2026-08-20 по коллекции):
  ни `distance`, ни `mileage`, ни пробега в параметрах; примеров ответов в
  коллекции нет вовсе, поэтому по телам ответов судить нельзя. Кандидаты, где он
  может лежать, — `delivery/couriers-orders` и `delivery/statistics`; проверять
  первым живым вызовом. Если его там нет, это ровно тот случай, когда метод
  просят у техподдержки.
- Можно ли править список scope у уже заведённого приложения или нужен новый
  клиент — в кабинете разработчика будет видно; на планирование не влияет.
