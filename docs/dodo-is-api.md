# Dodo IS API: что там есть и что нам из этого нужно

> Выписано из официальной документации `docs.dodois.io` (раздел English
> Documentation) 2026-08-17. Документация публичная, читается без входа; ссылка
> на неё лежит и в Базе знаний («Документация Dodo IS API», пространство
> «Техподдержка»). Файл — **конспект для планирования шестой очереди**, а не
> копия документации: за истиной идти в первоисточник, здесь только то, что
> касается нас, и вывод, который из этого следует.

## Доступ: что нужно на самом деле

Вчерашний вывод «коннектор упирается в модерацию» был **неверен**, и вот
почему. На странице каждого метода написано «API access is granted after the app
is published in the Dodo IS Marketplace and passes moderation», но в разделе
«Начало работы» на `docs.dodois.io` порядок другой и короче:

1. создать приложение в **личном кабинете разработчика**
   (`marketplace.dodois.io/manage/apps`), выбрав способ авторизации;
2. получить `Client Id` и `Client Secret`;
3. получить токен по руководству (OAuth 2.0);
4. звать API — для большинства методов нужна учётная запись пользователя Dodo IS.

**Публикация в маркетплейсе — про РАСПРОСТРАНЕНИЕ приложения другим франчайзи,
а не про доступ к API для себя.** В инструкции «Как разместить своё приложение в
маркетплейсе» начальное условие звучит дословно: «У вас уже есть приложение,
которое использует API». То есть сначала работающая интеграция, потом витрина.

Что несёт публикация, если однажды до неё дойдём: подписочная модель и тарифы,
интеграция с сервисом лицензий, требование «три клика от подписки до первого
результата», модерация командой маркетплейса (проверяют в режиме пользователя,
могут проверить безопасность, если приложение работает с чувствительными
данными), заведение реквизитов для платежей. Почта для связи —
`marketplace@dodois.io`.

Для нас сейчас это значит: **шестая очередь ничем не заблокирована**. Нужен
только заведённый в кабинете разработчика клиент и учётка Dodo IS у партнёра.

## Аутентификация

- OAuth 2.0, два потока: **Franchisees_Authorization** (от имени человека) и
  **Franchisees_Service Token** (от имени приложения).
- Сервер авторизации — `auth.dodois.io`, база API — `https://api.dodois.io/…`.
- У сети есть идентификатор концепции (`businessId`), он приезжает в вызовы:
  `63d4829611ea45c8ae71394860a2481c` — Dodo Pizza,
  `c0b18e725258427a8bffea4f73957b0e` — Drinkit.

Для нашего продукта это ложится на уже принятую модель: токен — секрет площадки
(в `.env`, не в репозитории), а срез данных задаёт сам Dodo IS по правам
приложения, как у нас его задаёт база.

## Что нам нужно, по нашим очередям

### Шестая очередь — коннектор. Порядок задан владельцем (D044)

**Сначала часы, потом сырьё и списания, потом выручка с разбивкой.** Ничего из
этого не стопорит текущие очереди — коннектор кормит их данными, а не заменяет.

Порядок совпадает с ценой ручной работы: часы вбиваются в табель каждый месяц
руками, это самая дорогая рутина у партнёра.

**Шаг 1 — часы**

| Что нужно | Метод в Dodo IS API |
|---|---|
| Фактические смены по точке | `Team → Employee shifts (by pizzeria)` |
| Смены по конкретному человеку | `Team → Employee changes (by ID)` |
| Графики (плановые часы) | `Team → Schedules`, `Schedules: predictive metrics` |
| Справочник людей и должностей | `Team → Employee List`, `Employee information`, `Employee Positions` |
| Справочник точек | `Units → Information about units`, `Shifts of units` |

Наш табель при этом никуда не денется: он остаётся местом, где часы правят и
подтверждают, а коннектор станет ещё одним путём ввода, наравне с загрузкой
таблицы. Есть готовый пример на Python — «Построение расписания смен сотрудников»
(`github.com/dodobrands/partner-api-examples`).

**Шаг 2 — сырьё и списания**

| Что нужно | Метод |
|---|---|
| Списания сырья и продуктов | `Accounting → Written-off raw materials`, `Written off products`, `Discarded products` |
| Списание в производство | `Inventory → Write-offs of raw materials to production` |
| Питание персонала (вопрос Q007 про топли оброк) | `Accounting → Team meals` |
| Движение и остатки | `Accounting → Raw material movements`, `Warehouse balances`, `Raw material receipts` |

**Шаг 3 — выручка с разбивкой**

| Что нужно | Метод |
|---|---|
|---|---|
| Выручка по точке за день | `Finance → Day sales by unit` |
| Выручка по точке за месяц и за период | `Finance → Monthly sales by unit`, `Sales by unit for the period` |
| Выручка по стране (сверка итогов) | `Finance → Country Day Sales`, `Monthly national sales` |
| Продажи для разнесения по статьям | `Accounting → Sales` |

**Чего в API нет для нас.** Ни зарплатных начислений, ни налогов, ни платежей
поставщикам — то есть первые пять очередей нашего продукта коннектор не
заменяет. Есть `Team → One-time bonus`, `Premium to remuneration per hour`,
`Position premium…` — это **запись** премий в Dodo IS; возможный обратный путь,
но он про их учёт, а не про наш P&L.

### Четвёртая очередь — платежи поставщикам

`Accounting → Vendor List`, `List of local suppliers`, `Supplies → Raw material
receipt(s)`, `Manufactures → Unit orders`, `Delivered orders`. То есть
справочник поставщиков и поставки у Dodo IS свои. Заводя своих контрагентов
(T150), стоит держать в голове, что однажды их придётся сводить с этим списком —
и ключ сопоставления лучше предусмотреть сразу, а не искать потом по названию.

## Как начать, когда дойдём

1. Завести приложение: `marketplace.dodois.io/manage/apps` — выбрать поток
   авторизации (Authorization Code для работы от имени человека, Device Flow для
   входа без браузера, Client Credentials для сервисного токена). **Client Id
   выдаётся под конкретный поток**: клиент от одного потока для другого не
   годится.
2. Скоупы брать со страницы нужного метода, раздел «Security: OAuth 2.0»;
   несколько — через пробел. Для обновляемого токена добавить `offline_access`.
3. Первые запросы — готовой коллекцией Postman
   (`github.com/dodobrands/dodo-api-postman-collection`): она же служит
   песочницей, токен живёт несколько часов.
4. Руководства: «Работа с oauth Dodo IS», «Построение расписаний смен через API»
   — ссылки на них лежат на `docs.dodois.io` в разделе «Руководства и примеры».

## Что осталось невыясненным

- Нужен ли отдельный доступ на каждого партнёра-франчайзи (у каждого свой
  контур?) — на нашем случае это Сербия, и учётка нужна их.
- Есть ли песочница: в документации указан только mock-сервер Stoplight
  (`https://stoplight.io/mocks/dodo-brands/english-documentation/1915948546`),
  а он отдаёт примеры из схемы, а не данные.
- Полный список scope'ов — на странице метода они не перечислены, видно только
  название потока авторизации.
- Ограничения по частоте запросов и глубине истории.
