# Dodo IS API: что там есть и что нам из этого нужно

> **С чего продолжать — [dodo-is.md](dodo-is.md).** Здесь справочник по API;
> что решено, что сделано и что делать дальше — там.
>
> ## Объём: только отработанные часы
>
> **Из Dodo IS продукт берёт один вид данных — отработанные часы** (D062,
> решение владельца 30.08.2026). Ни выручки, ни зарплаты, ни себестоимости, ни
> метрик. Один метод: `GET /staff/shifts`.
>
> Причина в замысле: продукт строится, чтобы **считать оклады и коэффициенты
> самому**. Всё, что Dodo IS уже посчитал, не нужно по определению — второй
> источник истины обесценивает движок, ради которого проект и существует. Часы
> — единственное, чего у нас нет и что вбивают руками каждый месяц.
>
> Остальная часть файла — разбор API целиком. Он сделан и пусть лежит: если
> объём когда-нибудь расширят, не придётся выяснять заново. **Но в работу из
> него берётся только раздел про часы.** Доставать отсюда «полезное сверх
> плана» не нужно — это уже дважды уводило разговор в сторону.
>
> **Расширить объём можно будет без переписывания** (D063): каждый поток данных
> — отдельный выключатель с тремя состояниями, `off` / `trial` / `on`, и живут
> они в таблице `data_feeds` у партнёра. `trial` — режим сверки: цифра
> приезжает и видна рядом со своей, но в расчёт и в P&L не идёт. Заведено ровно
> под сомнение владельца в чужой себестоимости: проверить её можно только на
> живом месяце, а проверять то, что уже попало в расчёт, поздно. Правило
> «доверяем или нет» живёт в одном месте — `core/feeds.py`.

> Выписано из официальной документации `docs.dodois.io` 2026-08-17, сверено со
> спекой машинно 2026-08-30. Документация публичная, читается без входа. Файл —
> **конспект**, а не копия: за истиной идти в первоисточник.

## Доступ: что нужно на самом деле

Вчерашний вывод «коннектор упирается в модерацию» был **неверен**, и вот
почему. На странице каждого метода написано «API access is granted after the app
is published in the Dodo IS Marketplace and passes moderation», но в разделе
«Начало работы» на `docs.dodois.io` порядок другой и короче:

1. создать приложение в **личном кабинете разработчика**
   (`marketplace.dodois.io/manage/apps`), выбрав способ авторизации;
2. получить `Client Id` и `Client Secret`;
3. получить токен по руководству (OAuth 2.0);
4. звать API — для большинства методов нужна учётная запись пользователя Dodo IS.

**Публикация в маркетплейсе — про РАСПРОСТРАНЕНИЕ приложения другим франчайзи,
а не про доступ к API для себя.** В инструкции «Как разместить своё приложение в
маркетплейсе» начальное условие звучит дословно: «У вас уже есть приложение,
которое использует API». То есть сначала работающая интеграция, потом витрина.

Что несёт публикация, если однажды до неё дойдём: подписочная модель и тарифы,
интеграция с сервисом лицензий, требование «три клика от подписки до первого
результата», модерация командой маркетплейса (проверяют в режиме пользователя,
могут проверить безопасность, если приложение работает с чувствительными
данными), заведение реквизитов для платежей. Почта для связи —
`marketplace@dodois.io`.

Для нас сейчас это значит: **шестая очередь ничем не заблокирована**. Нужен
только заведённый в кабинете разработчика клиент и учётка Dodo IS у партнёра.

## Аутентификация

> Раздел выверен 2026-08-28 по руководству «API → Авторизация»
> (`buildin.ai/share/f5caf1a5…`, оно же ссылка из документации) и по
> discovery-эндпоинту `https://auth.dodois.io/.well-known/openid-configuration`.

- OAuth 2.0, сервер авторизации — `auth.dodois.io`. Потоков **три**, и выбор
  между ними — не вкусовщина, а вопрос того, будут ли вообще данные (ниже).
- **База API у нас другая, чем записано в примерах документации.** Примеры
  показывают Россию (`https://api.dodois.io/dodopizza/ru`), у Сербии домен
  **`.com`**: `https://api.dodois.com/dodopizza/rs`. Всего в спеке 40 стран,
  домен у каждой свой (`.io` для СНГ, `.com` для остальных) — значит база
  берётся из конфигурации тенанта, а не пишется в код.
- У сети есть идентификатор концепции (`businessId`), он приезжает в вызовы:
  `63d4829611ea45c8ae71394860a2481c` — Dodo Pizza,
  `c0b18e725258427a8bffea4f73957b0e` — Drinkit.

### Три потока и почему сервисный нам не подходит

| Поток | Как получить | Что даёт |
|---|---|---|
| **Authorization Code + PKCE** | Клиент в кабинете; `code_challenge_method=S256` обязателен | Токен от имени человека — полные права его учётки |
| **Device Flow** | Клиент в кабинете; `POST /connect/deviceauthorization`, человек подтверждает код на странице | То же самое, но без адреса возврата |
| **Client Credentials** | В кабинете **не выдаётся**, просить письмом на `marketplace@dodois.io` | Почти ничего: см. ниже |

**Сервисный токен бесполезен для наших данных, и это сказано в руководстве
прямым текстом:** «такой токен не будет привязан к пользователю, а значит не
будет иметь доступов по ролям и заведениям, а значит **большая часть API будет
недоступна**». Он годится только для общедоступного (список заведений, вакансии).

Подтверждается это машинно: **62 метода из 78 требуют scope `user.role:read`** —
«роли и юниты пользователя». Метод без учётки человека просто не отвечает
данными. Отсюда практический вывод: **накопление данных у нас строится на
`offline_access` + `refresh_token`**, то есть человек авторизуется один раз, а
дальше коннектор обновляет токен сам (руководство рекомендует раз в 3 часа при
жизни токена 24 часа).

Три детали, на которых легко обжечься:

1. **`refresh_token` одноразовый.** «Даже после неудачного ответа токен
   перестаёт действовать» — значит обновление токена должно быть атомарным и
   с сохранением нового значения до того, как им воспользуются; иначе цепочка
   рвётся и нужен человек.
2. **`Client Id` выдаётся под конкретный поток.** Клиент от Authorization Code
   не работает в Device Flow, и наоборот.
3. **Токен живёт 24 часа** (`expires_in: 86400` в примерах), но руководство
   советует закладываться на 3 часа.

### Scope: полный список Dodo IS API

Вопрос «полного списка scope» закрыт — он лежит в самой спеке (в интерфейсе
документации виден только заголовок «Security: OAuth 2.0», из-за чего казался
недоступным). Всего у Dodo IS API 23 области:

| Scope | Что открывает | Нужен нам |
|---|---|---|
| `shared` | Общее: заведения, должности, история должностей, вакансии, **вся выручка** | да |
| `user.role:read` | Роли и юниты пользователя | **да, к 62 методам из 78** |
| `staffshifts:read` / `:write` | Смены сотрудников — **наши часы** | да (чтение) |
| `staffmembers:read` / `:write` | Сотрудники (содержит персональные данные) | да (чтение) |
| `staffmembersearch` | Поиск сотрудников | нет |
| `accounting:read` | Учёт: сырьё, списания, остатки, питание команды | да |
| `accounting` | Устаревшая общая область, оставлена для совместимости | нет |
| `sales` | Продажи (`/accounting/sales`) | да |
| `incentives` | Вознаграждения и премии сотрудников | **нет — зарплату из Dodo IS не берём (D061)** |
| `unit:read` / `:write` | Заведения, цели на месяц | да (чтение) |
| `unitshifts:read` | Смены заведений | да |
| `organizationstructure` | Юрлица и их типы | да |
| `localities:read` | Населённые пункты | нет |
| `receipts:write` | Оформление поставок | нет |
| `orders`, `deliverystatistics`, `stopsales`, `productionefficiency` | Заказы, доставка, стоп-продажи, эффективность | нет |
| `offline_access` | Выдача `refresh_token` | **да, обязательно** |

У соседних сервисов свои области: `accounting:write`, `accounting:manufacture`
(Accounting API), `users:feed` (Auth API), `pospayments:read`, `franchisee:read`,
`storeapi:read`/`:write`.

Для нашего продукта это ложится на уже принятую модель: токен — секрет площадки
(в `.env`, не в репозитории), а срез данных задаёт сам Dodo IS по правам
приложения, как у нас его задаёт база.

## Что нам нужно, по нашим очередям

### Шестая очередь — коннектор. Объём: часы, и всё (D062)

Прежний план D044 («сначала часы, потом сырьё и списания, потом выручка»)
**отменён**: шагов два и три не будет. Коннектор забирает часы и на этом
заканчивается.

Часы — самая дорогая ручная рутина у партнёра: их вбивают в табель каждый
месяц. Остальное продукт либо считает сам, либо собирает из первички, и
дублировать это чужими цифрами незачем.

**Единственное, что берём, — часы**

| Что нужно | Метод | Scope |
|---|---|---|
| **Фактические смены по точке** | `GET /staff/shifts` | `staffshifts:read`, `user.role:read` |
| Смены по конкретным людям | `GET /staff/members/shifts` | `staffshifts:read`, `user.role:read` |
| Графики (плановые часы) | `GET /staff/schedules`, `/staff/schedules/forecast` | `staffshifts:read`, `user.role:read` |
| Справочник людей | `GET /staff/members`, `/staff/members/{id}` | `staffmembers:read`, `user.role:read` |
| Должности и их история | `GET /staff/positions`, `/staff/positions/history` | `shared` |
| Справочник точек | `GET /units`, `GET /units/shifts` | `shared` / `unit:read` |

**Главное про `/staff/shifts`: смена приезжает уже разложенной ровно так, как
её считает наш движок.** Это не «сырые отметки времени», которые пришлось бы
интерпретировать самим:

| Поле ответа | Что это | Куда у нас ложится |
|---|---|---|
| `dayShiftMinutes`, `nightShiftMinutes` | Дневные и ночные минуты смены | Ночная надбавка — считается движком, а не выводится из времени вручную |
| `holidayMinutes` | Минуты, попавшие на праздничный день (по настройкам Dodo IS) | Праздничный коэффициент |
| `staffPositionId`, `staffPositionName` | Должность **на смене** | Ставка по должности (пятая очередь) |
| `employmentTypeId`, `employmentTypeName` | Тип трудоустройства | Условия найма |
| `seniority` | Стаж в месяцах на момент смены | Надбавки за стаж |
| `deliveredOrdersCount`, `totalTripsCount`, `totalTripsDistance` | Доставленные заказы, поездки, **метраж поездок** | Сдельная оплата курьеров (D032, T075) |
| `dailyStatistics[]` | То же в разрезе суток | Смена через полночь делится по датам |
| `shiftUpdates[]`, `lastModifiedAt`, `lastModifiedByUserId` | Кто и когда правил смену | Наша авторская отметка в табеле |

Две особенности, которые придётся учесть в коннекторе:

1. **Выборка идёт по началу смены, и смена возвращается целиком.** Если
   `clockInFrom`–`clockInTo` захватил начало, вся смена приедет, даже если она
   вышла за границу периода. Значит «часы за месяц» — это не просто фильтр по
   датам: границу месяца режем мы, по `dailyStatistics`.
2. **Группировать по сотруднику надо у себя.** В документации прямо: «для
   получения всех часов по каждому сотруднику нужно выкачать все смены за период
   и сгруппировать у себя по `staffId`».

Пагинация у всех списочных методов одинаковая: `skip` + `take` (максимум
**1000**, по умолчанию 100), листать до `isEndOfListReached = true`. Ограничение
на список точек в одном запросе разное: у большинства методов учёта — до 30
заведений, у истории должностей — до 5, у Store API — до 10; UUID перечисляются
строго через запятую **без пробелов**.

Доступ к сменам открыт ролям `Division administrator`, `Store Manager`,
`Shift supervisor` — то есть учётка, под которой ходит коннектор, должна быть не
рядовой.

Наш табель при этом никуда не денется: он остаётся местом, где часы правят и
подтверждают, а коннектор станет ещё одним путём ввода, наравне с загрузкой
таблицы. Есть готовый пример на Python — «Построение расписания смен сотрудников»
(`github.com/dodobrands/partner-api-examples`).

**Шаг 2 — сырьё и списания. ОТМЕНЁН (D062), оставлено как разбор**

| Что нужно | Метод | Scope |
|---|---|---|
| Списанное сырьё и продукты | `GET /accounting/write-offs/stock-items`, `/write-offs/products` | `accounting:read` |
| Брак | `GET /accounting/defective-products` | `accounting:read` |
| Списание в производство | `GET /write-offs-by-order` (Accounting API, своя база) | `accounting:read` |
| Питание персонала (вопрос Q007 про топли оброк) | `GET /accounting/staff-meals` | `accounting:read` |
| Расход сырья за период | `GET /accounting/stock-consumptions-by-period` | `accounting:read` |
| Остатки, перемещения, приходы | `GET /accounting/inventory-stocks`, `/stock-transfers`, `/incoming-stock-items` | `accounting:read` |
| **Ревизии** | `GET /revisions` (база `…/dodopizza/inventory`) | `accounting` |
| Расход теста, полуфабрикаты | `GET /accounting/dough-consumption`, `/semi-finished-products-production` | `accounting:read` |

Оговорка из самой документации, важная для сверки: **данные `stock-consumptions-by-period`
могут отличаться от одноимённого отчёта в интерфейсе Dodo IS.** То есть сходимость
с отчётом бухгалтера здесь не гарантирована API — это отдельная проверка, как с
зарплатой.

**Шаг 3 — выручка с разбивкой. ОТМЕНЁН (D062), оставлено как разбор**

| Что нужно | Метод | Scope |
|---|---|---|
| Выручка по точке за день | `GET /finances/sales/units/daily` | `shared` |
| Выручка по точке за месяц и за период | `GET /finances/sales/units/monthly`, `/finances/sales/units` | `shared` |
| Выручка по стране (сверка итогов) | `GET /finances/sales/country/daily`, `/country/monthly`, `/country` | `shared` |
| Продажи для разнесения по статьям | `GET /accounting/sales` | `sales` |

**Выручка — самое дешёвое, что есть в этом API.** Финансовым методам хватает
`shared`: ни ролей, ни согласия на персональные данные. Заодно это снимает
неопределённость с T132, где продукт врал про причину, потому что выручки в нём
нет вовсе.

Что именно приезжает в `/finances/sales/units/daily`: `sales` — **без VAT**,
`ordersCount`, и разбивка `salesBreakdown[]` по каналу продаж (Delivery,
Dine-in, Takeaway), источнику заказа (CallCenter, Website, Dine-in, MobileApp,
Manager, Aggregator, Kiosk, ChatBot) и способу оплаты (Online, Cash, Card,
Aggregator). Для P&L это готовая аналитика: и «выручка на точку в день», и
основание для правила «разносить пропорционально выручке».

**Чего в API нет для нас.** Ни зарплатных начислений, ни налогов, ни платежей
поставщикам — то есть первые пять очередей нашего продукта коннектор не
заменяет. Есть `Team → One-time bonus`, `Premium to remuneration per hour`,
`Position premium…` — это **запись** премий в Dodo IS; возможный обратный путь,
но он про их учёт, а не про наш P&L.

### Четвёртая очередь — платежи поставщикам

`Accounting → Vendor List`, `List of local suppliers`, `Supplies → Raw material
receipt(s)`, `Manufactures → Unit orders`, `Delivered orders`. То есть
справочник поставщиков и поставки у Dodo IS свои. Заводя своих контрагентов
(T150), стоит держать в голове, что однажды их придётся сводить с этим списком —
и ключ сопоставления лучше предусмотреть сразу, а не искать потом по названию.

## Что ещё есть в API и что из этого нам полезно

> Перечень **пересобран 2026-08-28 из самой спеки**, а не из коллекции Postman:
> `python tools/dodo_is_catalog.py` снимает её через открытый API Stoplight и
> кладёт машинный каталог в `docs/dodo-is-catalog.json`. Прежний источник
> (коллекция `dodobrands/dodo-api-postman-collection`) неполон — финансовых
> методов в нём нет вовсе, — и по нему нельзя судить о полях ответов: примеров
> там нет. Именно на этом и родился неверный вывод про километраж курьера.
>
> Коллекция остаётся полезной как песочница для первых живых вызовов; источник
> истины — спека.

**Базовый адрес зависит от сервиса, а не только от страны — и это не деталь.**
Прежнее «путь строится как `/{концепция}/{страна}/{раздел}/{метод}`» верно
только для основного API; соседние сервисы живут по другим адресам, и коннектор,
собранный на одном шаблоне, до них просто не достучится:

| Сервис | База | Пример |
|---|---|---|
| Dodo IS API (основной) | `https://api.dodois.com/dodopizza/rs` | `/staff/shifts` |
| Ревизии (Inventory) | `https://api.dodois.com/dodopizza/inventory` | `/revisions` |
| Учёт: списания, мануфактуры | `https://api.dodois.com/accounting` | `/write-offs` |
| Роли и юниты (Auth) | `https://api.dodois.com/auth` | `/roles/units` |
| Эквайринг (POS payments) | `https://api.dodois.com/pospayments` | `/accounting-report` |
| Сети франчайзи | `https://api.dodois.com` | `/franchisee/units` |

Значит в конфигурации источника хранится **база целиком**, а не только код
страны. Концепция при этом всё равно параметризуется (у Drinkit свой
`businessId`) — это ложится на нашу мультитенантность без специальных случаев.

**Документация — не один проект, а тринадцать**, и основной покрывает меньше
половины. Это объясняет, почему методы «пропадали»: их искали не в том каталоге.

| Проект | Методов | Что внутри | Нужен нам |
|---|---|---|---|
| `dodo-is` | 78 | Учёт, Команда, Финансы, Заведения, Производство, Доставка, Оргструктура | **основной** |
| `english-documentation` | 130 | Английское зеркало **всех** проектов сразу | как сводный указатель |
| `publicapi` | 30 | Старый публичный API (deprecated) | нет |
| `accounting` | 25 | Списания, перемещения, ревизии, мануфактуры | да |
| `control` | 20 | Додо Контролинг | нет |
| `staff` | 11 | Найм | нет |

### Три находки, которых в прежнем разборе не было

**1. Банковская выписка — `GET /accounting-report`** (база
`https://api.dodois.com/pospayments`, scope `pospayments:read`). Отдаёт данные по
юрлицу за диапазон дат в разрезе платёжного провайдера. Смысл дословно из
документации: банк платёжного провайдера переводит деньги на расчётный счёт
юрлица **без указания заведения**, и этот метод нужен, чтобы привязать перевод к
конкретной точке. Параметры: `from`, `to`, `legalEntityId`, `paymentProvider`.

Это прямо шестая очередь нашей карты («импорт банковской выписки») — по крайней
мере в части эквайринга, где ручное сопоставление платежей и точек самое
муторное. Полноценной выпиской банка это не является: только то, что прошло
через платёжного провайдера Dodo.

**2. Ревизии — `GET /revisions`** (база `…/dodopizza/inventory`). Периодичность
`Day`/`Week`/`Month`, фильтры по точкам и по сырью. Без ревизии себестоимость
считается только «приход минус списание», то есть с накопленной ошибкой; ревизия
— то, чем бухгалтер эту ошибку закрывает. Оговорка из документации: **сырьё
может повторяться внутри одной ревизии**, потому что хранится в разных местах —
складывать надо самим.

**3. LFL — `GET /lfl/by-units`, `/lfl/by-countries`** (база
`…/customer-feedback`). Like-for-like по точкам с гранулярностью день/неделя/
месяц. Не для сбора данных, а для будущей аналитики (десятая очередь): сравнение
«та же точка год назад» считается у них, а не у нас. До 30 точек за запрос.

### Обратный путь: куда API позволяет писать

`POST accounting/write-offs` (списание), `POST staff/incentives/premium/{one-time,hourly,position}`

входить не просится: запись в чужую систему учёта — отдельный класс риска.

## Как начать, когда дойдём

1. Завести приложение: `marketplace.dodois.io/manage/apps` — выбрать поток
   авторизации. **В форме кабинета выбор всего из двух** (проверено на живой
   форме 2026-08-21): `Authorization Code Flow` и `Device Flow`. Обещанного
   документацией сервисного токена (`Franchisees_Service Token`, он же Client
   Credentials) в списке НЕТ — значит планировать нужно на потоке от имени
   человека, а сервисный, если он вообще выдаётся, спрашивать у техподдержки.
   **Client Id выдаётся под конкретный поток**: клиент от одного потока для
   другого не годится.

   Форма спрашивает: способ добавления (создать новое или подключить уже
   выданные Clients), название приложения, способ авторизации, название
   организации, контакт для связи (WhatsApp или Telegram) и согласие с публичной
   офертой. Полей `redirect_uri` и scope в ней нет — адрес возврата всплывёт
   дальше (он нужен только для Authorization Code), скоупы запрашиваются в самом
   запросе токена. Client Id и Secret показываются сразу после создания.
2. Скоупы брать со страницы нужного метода, раздел «Security: OAuth 2.0»;
   несколько — через пробел. Для обновляемого токена добавить `offline_access`.
3. Первые запросы — готовой коллекцией Postman
   (`github.com/dodobrands/dodo-api-postman-collection`): она же служит
   песочницей, токен живёт несколько часов.
4. Руководства: «Работа с oauth Dodo IS», «Построение расписаний смен через API»
   — ссылки на них лежат на `docs.dodois.io` в разделе «Руководства и примеры».

## Что нужно, чтобы потом брать другие данные

> Источник — статья-стандарт «Partner API — точки интеграции „Додо ИС“» в Базе
> знаний (пространство «Стандарты управления и внедрения в Евразии», обновлена
> 19.06.2025). Она отвечает на вопрос, которого нет в технической документации:
> расширение набора данных — это не только новый вызов в коде.

**Данные поделены на четыре класса, и от класса зависит, что нужно для доступа.**
Это главное, что стоит знать заранее: «взять ещё одну цифру» иногда бесплатно, а
иногда требует роли у учётки партнёра и его повторного согласия.

| Класс | Примеры из статьи | Что нужно, чтобы получить |
|---|---|---|
| Публичные | **выручка за день**, агрегированные метрики точек, единые справочники, адреса, сведения о юрлицах | Ничего сверх токена: приложение авторизуется само, разрешение пользователя не нужно |
| Непубличные | **смены сотрудников**, перемещения сырья, метрики доставки за период, неагрегированные метрики с историей | Токен приложения; данные закрытые, но делегирования от человека не требуют |
| Конфиденциальные | **персональные данные сотрудников**, коммерческая тайна партнёра, **детализированная структура продаж** | Согласие пользователя И **соответствующие роли у его учётки** в Dodo IS. Узкая учётка не отдаст их даже с правильным scope |
| Строго конфиденциальные | данные клиентов, сырые события производства | **Никогда не будут доступны через API** — на них не стоит планировать ничего |

Отсюда практический вывод для нашего порядка (D044): часы — это смены, то есть
непубличные; выручка за день — вообще публичная; а вот детализация продаж и ФИО
сотрудников — конфиденциальные, и на них понадобится учётка партнёра с ролями,
а не только наш клиент.

**Что именно меняется, когда набор данных расширяется:**

1. **Scope в запросе токена.** Скоупы берутся со страницы каждого метода;
   новый метод — новый scope. Для обновляемого токена нужен `offline_access`.
2. **Повторное согласие партнёра** — если добавились конфиденциальные данные.
   Человек снова видит окно «приложение получит доступ к…» и подтверждает. На
   публичных и непубличных этот шаг не нужен.
3. **Роли учётки, под которой ходим.** Расширяются не в нашем кабинете, а внутри
   Dodo IS у самого партнёра.
4. **Второй клиент, если нужен другой поток авторизации.** Client Id выдаётся под
   поток; сервисный токен и вход от имени человека — это два клиента, а не
   переключатель у одного.
5. **Чего в API нет — можно попросить.** Статья прямо говорит: запросы на
   разработку новых методов принимает техподдержка (`support@dodopizza.com`),
   есть чат разработчиков в Telegram. То есть отсутствие метода — не тупик, а
   срок.

**Чтобы это не превращалось в стройку на нашей стороне**, коннектор должен быть
устроен как правила: источник данных — строка в конфигурации (метод, период,
куда маппится), а не ветка в коде. Тогда «брать ещё и это» — настройка, а не
релиз. Из того же принципа: `external_id` нужен не только контрагентам (T150), а
всем справочникам, которые однажды придут из Dodo IS — точкам, юрлицам,
сотрудникам, должностям.

**Личный кабинет разработчика** — в документации `marketplace.dodois.io/manage/apps`,
в статье Базы знаний `marketplace.dodois.io/dev/apps`; регистрация через
гугл-почту. Расхождение не проверено фактически — проверим при заведении клиента.

## Что осталось невыясненным

Список сильно короче, чем был: 2026-08-28 спека вычитана машинно (см. ниже), и
почти всё, что числилось неизвестным, оказалось в ней.

- **Ограничения по частоте запросов.** В спеке их нет вовсе — ни заголовков
  лимита, ни ответа `429` среди описанных. Проверять первым живым вызовом по
  заголовкам ответа; если лимит есть, он всплывёт на выкачке истории.
- **Глубина истории.** Ни один метод не объявляет предел периода `from`–`to`.
  Похоже, ограничения нет, но проверять надо фактом, а не спекой.
- Нужен ли отдельный доступ на каждого партнёра-франчайзи (у каждого свой
  контур?) — в нашем случае это Сербия, и учётка нужна их.
- Есть ли песочница: в документации указан только mock-сервер Stoplight, а он
  отдаёт примеры из схемы, а не данные. Практическая песочница — коллекция
  Postman с живым токеном.
- Можно ли править список scope у уже заведённого приложения или нужен новый
  клиент — в кабинете разработчика будет видно; на планирование не влияет.

### Что закрылось 2026-08-28

- **Полный список scope'ов** — есть, 23 области, выписаны выше. Прежний вывод
  «на странице метода не перечислены» был про интерфейс, а не про спеку.
- **Финансовые методы** — пути выписаны (`/finances/sales/units/daily` и
  соседние). Их отсутствие в коллекции Postman больше ничего не блокирует.
- **Километраж курьера — НАЙДЕН, и не там, где искали.** Он не в разделе
  «Доставка», а в смене сотрудника: `GET /staff/shifts` возвращает
  `totalTripsDistance` — «расстояние всех поездок за смену **в метрах**» — и
  `totalTripsCount`, плюс то же самое в разрезе суток (`dailyStatistics[]`).
  Прежний вывод «в API не найден» был сделан по коллекции Postman, в которой нет
  примеров ответов; по путям судить о полях нельзя. Практическое следствие:
  сдельная оплата курьеров по километражу (D032, T075) обеспечена данными, и
  просить метод у техподдержки не нужно.
- **Машинное чтение документации** — возможно, вопреки записанному ранее
  «Stoplight — SPA, `curl` получает пустую оболочку». Оболочку получает только
  сама страница; данные лежат в открытом API Stoplight, и оттуда снимается вся
  спека целиком (пути, scope, параметры, поля ответов). Это и есть способ
  держать наш конспект сверенным, не перепечатывая руками.
