# Блок: auth

## Назначение

Вход, роли и — главное — выставление контекста пользователя в базу на время запроса.
Выделен отдельно, потому что это единственное место, где решается, кем именно
приложение представляется базе: ошибка здесь не даёт ошибки в интерфейсе, она даёт
тихую утечку данных.

## API-контракт

```python
# web/principal.py
get_current_principal(request) -> Principal | None
    # Principal: user_id: UUID, tenant_id: UUID | None, unit_ids: list[UUID],
    #            visible_ledgers: list[str], permissions: list[str]
    #            + role_title, tenant_title, display_name — только для показа

# web/permissions.py — права: одно место, где действие сверяется с ролью
check(who, code) -> None            # нет права — PermissionRefused с текстом для человека
has(who, code) -> bool              # то же вопросом, для страниц
TIMESHEET_EDIT, PAYRUN_CALCULATE    # коды прав; те же, что стоят в политиках базы

# web/auth.py — узкое место, где вообще проверяется личность
login_with_password(request, username, password) -> User | None
session_user_id(request) -> UUID | None   # кем представиться базе
logout(request) -> None

# web/dbcontext.py — контекст в базе
set_db_context(connection, user_id) -> None      # только внутри транзакции
db_context(user_id) -> контекстный менеджер      # для кода без HTTP-запроса
```

Middleware: до любого обращения к данным выставляет в транзакции запроса

```sql
set local role app_user;
select set_config('app.user_id', %s, true);
```

Требования, которые блок обязан соблюсти (каждое закрыто тестом,
`tests/test_auth.py` и `tests/test_context_leak.py`):

- `ATOMIC_REQUESTS = True` — контекст живёт только внутри транзакции и физически не
  может пережить её, поэтому не протекает между запросами через пул. Транзакцию
  при этом открывает **само middleware**: `ATOMIC_REQUESTS` оборачивает только
  вызов представления, а middleware работает вне его;
- никогда не использовать `SET` без `LOCAL` (и `is_local = true` в `set_config`):
  обычный `SET` переживает транзакцию и утекает на следующего пользователя;
- **вне транзакции — отказ, а не тишина.** `set_config(..., true)` вне транзакции
  Postgres игнорирует с предупреждением в свой лог; `set_db_context` в таком
  случае бросает `ContextOutsideTransaction`;
- **выставленное перечитывается обратно** — «выполнили два оператора» и «контекст
  стоит» разошлись бы молча;
- фоновая задача выставляет контекст сама — через `db_context`;
- представления **не фильтруют по тенанту вручную**; это работа политик базы;
- реализация входа спрятана за `get_current_principal()` и `web/auth.py`, чтобы
  замена на корпоративный вход позже была подменой одной детали.

Таблица учёток закрыта той же RLS, что и данные (миграция `0010_users`): видно
свою строку (`id = app_user_id()`) и ту, которой прямо сейчас входят
(`app.login_username`, на одну транзакцию). `insert` и `delete` роли приложения
не даны — учётки заводит администратор тем же путём, что миграции.

  до первого запроса к данным, а `request.user` сам читается из таблицы
  `users` — то есть уже под политиками.

### 2026-08-07 — T014: вход, учётки, роли

**Учётка — своя модель `core.User` на `AbstractBaseUser`** (D013: вход на Django
auth, пароли штатным механизмом). Ключевое решение: `users.id` — тот же uuid,
что лежит в `memberships.user_id` и уходит в `app.user_id`. Схема внешнего ключа
не заводит (блок `db` нарочно оставил там голый uuid), но второй таблицы
соответствий «учётка → пользователь тенанта» нет и не будет: это лишнее место,
где однажды окажется не та строка.

`PermissionsMixin` **не подмешан**: права внутри учётки завели бы второй источник
истины о доступе рядом с ролью и политиками — ровно то, против чего D014. Что
человек видит, решает роль в `memberships`, применяет — база.

**Таблица `users` закрыта RLS, как и данные.** Иначе роль приложения читала бы
хэши паролей и список всех, кто есть в системе, и любая дыра в отчёте отдавала
бы этот список наружу. Политик три:

| политика | что открывает | зачем |
|---|---|---|
| `users_own_row` | `id = app_user_id()` | Django сверяет сессию на каждом запросе |
| `users_change_own_row` | своя строка на `update` | смена пароля и отметка последнего входа |
| `users_login_attempt` | `username = current_setting('app.login_username')` | без неё вход невозможен: пароль надо проверить до того, как человек представился |

Разрешение на вход живёт одну транзакцию и выставляется только кодом входа;
после `authenticate` оно снимается сразу, не «до конца запроса». `insert` и
`delete` у роли приложения **отозваны явно** — двойной запрет вместо одного.

Важное про issue #44: политики учётки зовут только `app_user_id()`, а она
читает настройку сеанса и в таблицы не ходит. То есть новое место, где молча
требуется владелец с правом обходить RLS, **не появилось**.

**Чем это проверено фактически** (живая база в контейнере, роль `app_user`):
без контекста — 0 учёток; со своим контекстом — 1, своя; на время входа видна
ровно одна строка, после снятия разрешения — снова ноль; `insert` отклонён
(`permission denied for table users`).

**Порядок в запросе.** Личность читается из сессии (`_auth_user_id`) до открытия
данных, потому что за ней нельзя сходить в базу: таблица учёток закрыта той же
политикой, которой нужен контекст. Мусор в сессии — это `None`, а не попытка
подставить его в контекст: иначе запрос падал бы на приведении к uuid.

**Как сосуществуют настоящий вход и `DEV_LOGIN`** (то, что просили обосновать):

- ярлык **не второй способ проверки личности**. Кнопка подставляет пароль
  учётки сида и идёт тем же `login_with_password`, что человек с клавиатурой.
  Обойти пароль он не может — если пароль учётки другой, кнопка честно
  откажет;
- умолчание флага теперь зависит от `DJANGO_DEBUG`, а не «включено»: забыть
  выставить переменную на площадке проще, чем выставить;
- **выключение действует немедленно и на уже выданные сессии.** Сессия,
  полученная кнопкой, помечена; при `DEV_LOGIN=0` middleware её сбрасывает.
  Без этого «выключили» было бы бумажным: cookie продолжала бы пускать.
  Сессии настоящего входа флаг не трогает — иначе он стал бы выключателем
  входа вообще (проверено обоими тестами).

**Четыре роли спеки** заведены сидом вместе с учётками: `director`,
`accountant`, `manager`, `admin` (пароль один, `SEED_USER_PASSWORD`). У ролей
появились `permissions` — сегодня на видимое влияет только набор регистров,
поэтому «администратор сети не правит данные расчёта» держится не проверкой
прав, а тем же механизмом, что и всё остальное: расчёт пишет строки во все
регистры, а роль, которая их не видит, записать их не может. Отказ 403 виден
и в тесте, и в браузере.

**Неавторизованный** уводится на страницу входа (`login_required`), а не
получает пустую страницу с данными. Пустота остаётся вторым контуром: контекст
не выставлен, выборки пусты — это отдельные тесты.

### 2026-08-07 — T015: утечка контекста

Два случая контракта, оба на живой базе:

- **два запроса на одном соединении.** Тест сам доказывает, что соединение то
  же: `CONN_MAX_AGE` поднимается на время теста и сравнивается backend pid
  Postgres. Без этого проверка была бы фиктивной — Django по умолчанию
  закрывает соединение в конце запроса, и второе было бы чистым само по себе.
  Проверяется и прямой признак: после запроса в соединении не осталось ни
  `app.user_id`, ни роли `app_user`;
- **фоновая задача.** `db_context(None)` — ни строки ни в одной таблице.
  Рядом стоит контроль «с пользователем строки есть», иначе тест был бы
  зелёным и на пустой базе.

Отдельно оставлен тест
`test_a_job_that_skips_the_helper_is_not_protected_by_anything`: запрос мимо
`db_context` идёт ролью подключения, а она сегодня владелец схемы и
суперпользователь — то есть видит всё. Это не защита, это ловушка, и она должна
быть видна в тестах, а не спрятана. Корень тот же, что у issue #44 (T052 блока
`db`): роль, которой подключается приложение, не должна быть владельцем.

**Что проверки не декоративные — показано порчей кода** (каждый раз с
подтверждением, что порча применилась):

| что испортили | что покраснело |
|---|---|
| `set_config(..., true)` → `false` | контекст переживает запрос и фоновую задачу — 2 теста |
| убрано `set local role app_user` | 8 тестов: видимость по ролям, своя строка учётки, оба случая утечки |
| политика учётки → `using (true)` | учётки видны без контекста и видны чужие — 2 теста |
| убран сброс dev-сессии при `DEV_LOGIN=0` | ярлык продолжает пускать после выключения — 2 теста |

### 2026-08-07 — T064: права роли перестали быть надписью

Права были заведены и никем не проверялись: грепом по `src/web`,
`src/timesheets`, `src/payrun` — ни одного обращения, кроме загрузки в
`Principal`. Фактически администратор сети **отредактировал ячейку табеля**, а
отказ на «Посчитать» получал не по праву, а по случайности: ему в сиде выдан
только официальный регистр, и срабатывала проверка регистров. Та же плашка
появилась бы и у роли, у которой право есть, — то есть она ничего не
доказывала.

Сделано два контура, и оба обязательны:

- **База.** Ограничивающие политики на запись (миграция `0022_role_permissions`,
  блок `db`): `timesheet.edit` на `timesheets` и `timesheet_days`,
  `payrun.calculate` на `payruns`, `payslips`, `pay_components`,
  `payslip_totals`. Чтение не трогается вовсе: право править табель — не право
  его видеть, и администратор обязан видеть данные, которые не правит.
- **Приложение.** Новый модуль `web/permissions.py`: коды прав, названия
  действий и одна проверка. Он не второй движок доступа — что человек может,
  решает роль, применяет база, а модуль это объясняет словами. Отказ называет
  действие («Расчёт периода не входит в права вашей роли «Администратор
  сети»»), а не код права: `payrun.calculate` — сообщение для разработчика.

Порядок проверок в `period_calculate` важен: **право проверяется раньше
регистров**, иначе отказ снова объяснял бы видимость вместо права.

Формы отказа: страница периода — 403 с плашкой на той же странице (как уже
сделано для регистров); ячейка табеля — 403 текстом. В `grid.js` подправлена
одна строка: текст ответа показывается теперь и на 403, а не только на 422 —
иначе человек увидел бы «Не удалось сохранить: 403».

Права **не подразумеваются друг из друга**: «умею считать период» не значит
«умею править табель». Иерархия ролей стала бы вторым источником истины рядом
со списком прав.

Что проверено фактически (живой стенд, Postgres 17, сид):

| действие | администратор | контроль |
|---|---|---|
| «Посчитать» на странице периода | 403, «Расчёт периода не входит в права вашей роли» | директор — 302, расчёт прошёл |
| запись ячейки табеля | 403, «Правка табеля не входит в права вашей роли», значение в базе не изменилось | управляющий — 200, `X-Cell-Value: 7.00` |
| правка табеля мимо экрана, ролью `app_user` | `new row violates row-level security policy "timesheet_edit_update"` | — |
| создание расчёта мимо экрана | `new row violates row-level security policy "payrun_calculate_insert"` | — |

В тестовой фикстуре администратору выданы **все три регистра** — специально,
чтобы отказ нельзя было списать на видимость (`tests/test_permissions.py`, 15
тестов). Порча внутри прогона снимает политику и требует, чтобы запись прошла.

Правки в чужих файлах, которых потребовала задача (сказано диспетчеру):
`src/timesheets/views.py` — проверка права перед записью ячейки;
`src/timesheets/static/timesheets/grid.js` — показ текста отказа на 403;
`tests/conftest.py` — у ролей фикстуры появились права, добавлена роль
администратора сети.

### 2026-08-08 — T076: закрывать точку вправе и директор (D033)

**Стенд.** Копия `…-auth2`, ветка `feat/auth2`, порты 8062/5472, имя
compose-проекта `dodo-pnl-auth2`, рабочий процесс очереди остановлен на время
прогонов (issue #65). Базовый прогон до правок — зелёный, 8 пропусков (сверка с
настоящей таблицей партнёра, файла в репозитории нет, D028).

**Что нашлось при чтении и определило объём правки.** Механизм закрытия (T022,
миграция `0031`) уже устроен так, что менять в нём ничего не нужно:

- `unit_close_insert/update/delete` спрашивают `app_has_permission(tenant_id,
  'unit.close')` — то есть право, а не роль;
- ограничивающая `unit_visibility` на `timesheet_closures` режет по
  `app_unit_is_visible`, а у директора точки не заданы вовсе (`unit_ids` пуст =
  все точки тенанта). Значит «директор закрывает любую точку» и «управляющий —
  только свою» получаются **одной и той же** политикой, без единого условия про
  роли;
- экран уже спрашивает `permissions.explain(who, UNIT_CLOSE)` и рисует кнопку
  только при праве, а на её месте — объяснение (T064, T072).

Поэтому задача свелась к набору прав роли, а не к новому механизму. **Шаблон
`grid.html` не тронут ни строкой** — это важно при соседе, который сейчас
перекладывает оформление: правка была бы конфликтом на ровном месте.

**Право добавлено в трёх местах, и все три обязательны:** сид (`seed_dev`) — для
демо-данных; фикстура `tests/conftest.py` — для тестов доступа; миграция
`0110_director_closes_units` — для баз, где сид уже не гоняется. Без миграции
право появилось бы только у того, кто пересоздаст демо-данные.

**Миграция ищет роль по коду `director`, а не по набору прав.** «Кто ведёт месяц
целиком» в данных не записано: `period.approve` есть и у бухгалтера, и выдать
ему закрытие смен заодно значило бы решить за партнёра, как у него устроена
работа. Код роли — единственный признак, который спека называет прямо.

**Миграция не молчит, если её отрезали политики.** `roles` под `force row level
security`, и роль, не обходящая политики, увидела бы отсюда ноль строк:
`update` изменил бы ноль строк, миграция «прошла», право не появилось. Поэтому
после правки стоит проверка результата (`raise exception`, если осталась роль
`director` без права) — тот же корень, что у issue #44.

**Бухгалтер как контрольная роль.** Тест «роль без права не закрывает» раньше
стоял на директоре; теперь на бухгалтере — и это сильнее: он видит все точки
тенанта и утверждает период, то есть отказ нельзя списать ни на видимость, ни
на «мало полномочий вообще».

**Что проверено фактически** (живая база в контейнере, Postgres 17, роль

краснеет только при снятии **обоих** контуров — политика базы и фильтр

свойство двойной защиты, но знать об этом надо: одна порча его не ловит.

## Что осталось следующим очередям

- **Управляющий видит все точки** — `unit_ids` в `Principal` есть и заполнен,
  но никто по нему не фильтрует (T044, блок `web`). Ключ точек готов к
  использованию: `get_current_principal(request).unit_ids`, пустой список
  значит «все точки тенанта».
- **Спека и сид расходятся про управляющего**: спека даёт ему только
  официальный регистр, сид — официальный и дополнительный. Данные не менял:
  это вопрос владельцу, а не решение блока.
- ~~Права ролей заведены, но ничего не решают~~ — закрыто в T064 для
  `timesheet.edit` и `payrun.calculate`, в T025 для `period.approve` и
  `period.reopen`, в T022/T076 для `unit.close`. Остальные (`directory.manage`,
  `rules.manage`, `roles.manage`) по-прежнему ничего не решают, и это правильно: экранов, где им
  место, ещё нет. Заводить проверку — вместе с экраном, парой «политика в базе +
  внятный отказ», а не заранее.
- **Сессии в подписанной cookie**: серверного списка сессий нет, «разлогинить
  всех» — это смена `SECRET_KEY`, одного человека — смена его пароля. Для
  продукта за периметром достаточно, но когда появятся живые пользователи,
  стоит вернуться.
- **Учётки заводит только тот, кто накатывает миграции** (у роли приложения нет
  `insert` на `users`). Экрана управления учётками нет — он часть админки
  справочников (T018).
