# Блок: auth

## Назначение

Вход, роли и — главное — выставление контекста пользователя в базу на время запроса.
Выделен отдельно, потому что это единственное место, где решается, кем именно
приложение представляется базе: ошибка здесь не даёт ошибки в интерфейсе, она даёт
тихую утечку данных.

## API-контракт

```python
get_current_principal() -> Principal
    # Principal: user_id: UUID, tenant_id: UUID, unit_ids: list[UUID],
    #            visible_ledgers: list[str], permissions: list[str]
```

Middleware: до любого обращения к данным выставляет в транзакции запроса

```sql
select set_config('app.user_id', %s, true);
```

Требования, которые блок обязан соблюсти:

- `ATOMIC_REQUESTS = True` — контекст живёт только внутри транзакции и физически не
  может пережить её, поэтому не протекает между запросами через пул;
- никогда не использовать `SET` без `LOCAL` (и `is_local = true` в `set_config`):
  обычный `SET` переживает транзакцию и утекает на следующего пользователя;
- фоновая задача выставляет контекст сама — у неё нет HTTP-запроса;
- представления **не фильтруют по тенанту вручную**; это работа политик базы;
- реализация входа спрятана за `get_current_principal()`, чтобы замена на
  корпоративный вход позже была подменой одной детали.

## Зависимости

Блоки: `db` (функции контекста и политики).

Внешнее: Django 6.1 (`django.contrib.auth`, сессии), psycopg 3.

## Definition of Done блока

- [ ] Вход, выход, смена пароля работают; неавторизованный не видит ничего, кроме
      страницы входа и демо
- [ ] Роль даёт набор точек и набор видимых регистров; тест на каждую из четырёх ролей
- [ ] Тест: два запроса подряд от разных пользователей на одном соединении пула —
      второй не видит данных первого
- [ ] Тест: фоновая задача без выставленного контекста не получает строк, а не берёт
      чужие
- [ ] Тест: попытка представления обратиться к данным вне транзакции запроса падает
      явно, а не молча отдаёт пустоту
- [ ] Пароли хранятся штатным механизмом Django; своей криптографии нет
- [ ] В логи не попадают идентификаторы сотрудников и суммы

## Журнал работы

### 2026-08-07 — старт, что прочитано и что решено до кода

Прочитаны контракт, конституция, спека (роли), план, `decisions.md` (D013, D014),
журнал блока `db`, `src/web/devauth.py`, `tasks.md`. Осмотрено фактически:
Python 3.13.15, Django 6.1, локальный Postgres 16.14 (смоук будет на 17 через
compose), порты 8038 и 5446 свободны.

Что нашлось в нынешнем устройстве и определило решения:

- **Контекст в базу уже выставляется** (`web/dbcontext.py`), транзакцию открывает
  само middleware — `ATOMIC_REQUESTS` оборачивает только представление, и
  `set local` из обычного middleware ушёл бы в автокоммит. Это остаётся.
- **Учётка в `memberships` — голый uuid** без внешнего ключа: схема нарочно не
  знает, чем окажется пользователь. Значит настоящая учётка обязана иметь
  **тот же** uuid, а не свой ключ, — иначе появится вторая таблица соответствий.
- **Личность берётся из сессии**, а не из базы: `set_config` нужно выставить
  до первого запроса к данным, а `request.user` сам читается из таблицы
  `users` — то есть уже под политиками.
