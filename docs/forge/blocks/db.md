# Блок: db

## Назначение

Схема данных и разграничение доступа. Выделен отдельно, потому что на нём держится
главный принцип продукта: изоляция тенантов и видимость регистров учёта живут в базе,
а не в коде. Любой другой блок может забыть фильтр — и должен получить пустой
результат, а не чужие данные.

Здесь же переезд с голых SQL-файлов на миграции Django и переименование регистров
учёта в нейтральные термины.

## API-контракт

Функции контекста, на которые опираются все политики и весь остальной код:

```sql
app_user_id() returns uuid
    -- текущий пользователь; читает GUC app.user_id, выставленный приложением

app_tenant_ids() returns setof uuid
    -- тенанты, где пользователь состоит

app_visible_ledgers(p_tenant uuid) returns ledger[]
    -- регистры, видимые пользователю в этом тенанте; для чужого тенанта — пустой массив

app_unit_ids(p_tenant uuid) returns uuid[]
    -- точки пользователя; null = ограничения нет (все точки), '{}' = ни одной

app_unit_is_visible(p_tenant uuid, p_unit uuid) returns boolean
    -- видна ли строка этой точки; строка без точки видна всем в тенанте

app_employee_is_visible(p_tenant uuid, p_employee uuid) returns boolean
    -- свой ли это человек: есть ли у него условия найма на видимой точке (даты не учитываются)

app_sees_every_ledger(p_tenant uuid) returns boolean
    -- видны ли пользователю ВСЕ регистры учёта вообще (все значения типа ledger)
    -- на этом стоит видимость итогов расчёта: свойство роли, а не строки (T071)

app_has_permission(p_tenant uuid, p_code text) returns boolean
    -- есть ли у пользователя это право в тенанте; без контекста — false
```

Правила, которые блок гарантирует наружу (каждое закрыто тестом ролью `app_user`,
файлы `tests/test_schema_access.py` и `tests/test_rule_periods.py`):

- **RLS и `force row level security` — на каждой таблице продукта.** Список
  таблиц тест берёт из самой схемы, а не из головы: новая таблица без политики
  роняет прогон сама.
- **Политика изоляции тенанта — пермиссивная, политики видимости регистров —
  ограничивающие** (`as restrictive`): пермиссивные складываются через OR и не
  сужают выборку вообще.
- **Строки `tenant_id is null`** в `roles` и `pnl_items` — общие: видны всем, у
  кого есть контекст, и **не пишутся** приложением (`with check` их не пускает).
- **Приложение ходит ролью `app_user`**: не владелец таблиц, без `bypassrls`.
- **Ни работа приложения, ни накат схемы не требуют права обходить RLS** (T052).
  Схема разворачивается обычной ролью — без `superuser` и без `bypassrls`, то
  есть на любом управляемом Postgres, где такой роли не дают вовсе. Требования
  к роли развёртывания только обычные: она владеет схемой и либо имеет
  `createrole` (заведёт `app_user` сама), либо получает уже заведённую
  `app_user` с правом её выдавать. Если роль `app_user` окажется с `superuser`
  или `bypassrls`, миграция **останавливается с внятным текстом**, а не
  накатывается в состояние, где изоляции нет.
  Проверяет это `tests/test_plain_owner.py`: отдельная база, накатанная ролью
  без привилегий, приложение ходит в неё логин-ролью тоже без привилегий.
  Там же сторож `test_the_recursion_would_come_back_with_the_old_policy` —
  возвращает прежнюю политику и требует, чтобы всё снова упало.
- **Политика `memberships` не зовёт функций контекста** — она их корень.
  Условие прямое: `user_id = app_user_id()`, то есть человек видит только свои
  членства. Иначе политика звала бы `app_tenant_ids()`, а той нужна та же
  политика: с владельцем-суперпользователем круг незаметен (он обходит RLS),
  с обычным — `stack depth limit exceeded`. Следствие: экран управления людьми,
  когда появится, берёт чужие членства функцией `security definer`, а не
  расширением этой политики.
- **Обход RLS остаётся нужен администрированию данных**, но не продукту: сид,
  восстановление из дампа и обслуживание идут ролью, которая политики обходит.
  Это осознанно — первое членство иначе некому создать.
- **Без выставленного контекста любая выборка возвращает ноль строк** — проверено
  по всем таблицам продукта разом.
- **Итоги расчёта отделены от строки ведомости.** `payslips` — идентификация
  (кто, где, за какой расчёт) и видна всем в тенанте; суммы (`net`, `gross`,
  `tax`, `contributions`, `total_cost`, `to_bank`, `to_cash`) лежат в
  `payslip_totals`.
- **Видимость итогов — свойство роли, а не строки** (T071). Их видит тот, кому
  видны **все** регистры учёта вообще (все значения типа `ledger`), и не видит
  никто другой — независимо от того, что в строке. Поэтому состояний ровно два:
  «итогов столько же, сколько видимых строк ведомости» и «итогов нет». Прежнее
  правило («видны все регистры **этой строки**») закрывало суммы, но само
  называло людей: `payslips left join payslip_totals where t.payslip_id is null`
  отдавал поимённый список тех, у кого есть выплаты в закрытых регистрах.
  Общая форма дефекта: **пока видимость производной строки зависит от её
  содержимого, отсутствие производной и есть сообщение**. Заводя следующую
  таблицу-спутник, спрашивать `app_sees_every_ledger(tenant)`, а не строку.
- **`security definer` — это публичный вход, а не деталь политики.** Функции
  исполнимы `PUBLIC` по умолчанию, поэтому функция, отвечающая на вопрос о
  **строке**, выдаёт про неё ровно то, что политика прячет. Так и вышло с
  `app_payslip_ledgers_visible()` (удалена в `0023`). Аргументом такой функции
  может быть тенант или сам пользователь, но не чужая строка.
- Набор регистров строки (`payslips.ledgers`) наполняет триггер по компонентам.
  С T071 видимости он больше не держит: колонку читает только сама база.
- **Колонку `payslips.ledgers` роль приложения не читает вовсе** (T065):
  табличная привилегия `select` на `payslips` снята, колонки выданы поимённо
  кроме этой. Иначе по ней поимённо видно, у кого есть выплаты в закрытых от
  роли регистрах. Читают её только сама база (политика через
  `app_payslip_ledgers_visible()`) и триггер — правами владельца. Новая колонка
  `payslips` требует явного гранта, сторож — `tests/test_payslip_visibility.py`.
- **Видимость точек — на `units`, `employment_terms`, `timesheets`, `payslips`,
  `pay_components` и `employees`.** У сотрудника точки нет: своим он считается
  по условиям найма на видимой точке, любой версии (T057).
- **Право на запись проверяется политиками, а не только экраном** (T064):
  `timesheet.edit` — на `timesheets` и `timesheet_days`, `payrun.calculate` — на
  `payruns`, `payslips`, `pay_components`, `payslip_totals`. Только запись:
  чтение правом не ограничивается. Вставка и правка отказывают **громко**
  (`new row violates row-level security policy`), потому что тихий «изменено 0
  строк» неотличим от успеха.
- **Периоды действия версионируемых правил не пересекаются** — ограничения
  `EXCLUDE` поверх `btree_gist` (миграция `0006_rule_periods`):

  | таблица | ключ, внутри которого версии не пересекаются |
  |---|---|
  | `employment_terms` | тенант + сотрудник |
  | `rule_overrides` | тенант + уровень + объект уровня + путь правила |
  | `allocation_rules` | тенант + контрагент + регистр учёта |
  | `rule_presets` | код пресета |

  Границы периода — `[valid_from, valid_to)`: конец не входит, поэтому «по 1
  июля» и «с 1 июля» стыкуются, а не спорят. Пустой `valid_to` — бесконечность.
  Пустой `scope_id` в `rule_overrides` приведён к нулевому uuid: иначе
  `null = null` даёт null и страновой уровень остался бы без защиты.

Именование после переименования: тип `ledger` со значениями `official`,
`supplementary`, `internal`; колонка `ledger` вместо `layer`.

### 2026-08-07 — T009: роль `app_user`

Роль заводится миграцией `0005_app_role`: `nosuperuser`, `nobypassrls`, не владеет
таблицами, права только на данные. Роль групповая (`nologin`) и выдаётся тому, кто
подключается: сервис делает `set local role app_user` в транзакции запроса вместе
с контекстом пользователя. Так пароль логина остаётся делом развёртывания и в
миграцию не попадает.

Проверка на осмысленность (то, чего требует DoD задачи) сделана фактически:
переключение роли в `as_app_user` временно заменено на заглушку, прогон
`tests/test_schema_access.py` — **6 из 7 тестов доступа покраснели**
(изоляция, пустота без контекста, запрет записи в чужой тенант, три теста
видимости регистров). Зелёным остался только `test_isolation_check_is_meaningful`,
который как раз и утверждает, что владелец видит оба тенанта.

Заодно закрыт **T001**: политики видимости регистров написаны сразу
`as restrictive`, на всех таблицах с `tenant_id` — `force row level security`.
Обратный прогон подтверждает, что тест не декоративный: с пермиссивной политикой
три теста видимости падают, бухгалтер снова видит внутренний регистр.

**T002 намеренно не чинил** — это отдельная задача. Дефект (`tenant_id is null`
не проходит политику изоляции, поэтому системные роли и общий справочник статей
не видны никому) описан прямо в миграции `0004_rls`, чтобы не читался как норма.

### 2026-08-07 — T010 и T047: непересечение периодов и правка контракта

Ограничения `EXCLUDE` поверх `btree_gist` заведены моделями Django
(`ExclusionConstraint`), а не сырым SQL: иначе `makemigrations --check` не видел
бы схему целиком и модели могли бы разъехаться с базой молча. Миграция
`0006_rule_periods`.

Что решено по ходу и почему именно так:

- **Границы периода `[valid_from, valid_to)`.** Так уже читает расчёт
  (`collect_cases` исключает версии с `valid_to <= period`), и так оформляется
  обычный перевод сотрудника: «по 1 июля» и «с 1 июля» — стык, а не спор.
- **Пустой `scope_id` приведён к нулевому uuid.** Ловушка: в `EXCLUDE`
  сравнение идёт оператором `=`, а `null = null` даёт null, то есть «не
  совпало». Без приведения ограничение молча не защищало бы страновой и
  партнёрский уровни — то есть самые частые. Тест на это отдельный.
- **Регистр учёта входит в ключ `allocation_rules`.** Первая версия ключа
  (тенант + контрагент) уронила тест видимости регистров из T001: он заводит
  два правила одному контрагенту в разных регистрах. Разбирался, а не подгонял:
  один поставщик действительно может оплачиваться и официально, и из кассы —
  это разные строки P&L, а не спорные версии. Следствие для будущего блока
  разнесения: правило ищется по паре «контрагент + регистр».

T047 (контракт обещал `EXCLUDE`, которого не было) закрыт тем же куском:
раздел «Правила, которые блок гарантирует наружу» переписан под то, что реально
проверяется, с таблицей ключей и указанием тестов. Заодно две гарантии из
контракта перестали быть выборочными — `force RLS` и «без контекста пусто»
теперь проверяются **по всем таблицам продукта**, а список таблиц берётся из
самой схемы. Что эти две проверки не декоративные, показывает
`test_schema_wide_checks_catch_an_unprotected_table`: он создаёт незакрытую
таблицу внутри транзакции теста и требует, чтобы обе упали.

Фактически: 13 тестов периодов (6 из них были красными до ограничений — с
внятным «DID NOT RAISE ExclusionViolation»), полный прогон 100 passed,

### 2026-08-07 — T050: итоги расчёта больше не выдают скрытый регистр

Выбран третий вариант из issue #42 — ограничивающая политика, — но **не на самих
`payslips`**, и это выяснилось прогоном, а не рассуждением.

Первая версия прятала строку ведомости целиком: `payslips.ledgers` (набор
регистров, наполняется триггером по компонентам) плюс политика
`ledgers <@ app_visible_ledgers(tenant_id)`. Проверки задачи позеленели, а два
чужих теста покраснели — и по делу: ведомость собирается запросом к
`pay_components` **с присоединением** `payslips`, поэтому скрытая строка утащила
за собой и официальные компоненты смешанного сотрудника. У бухгалтера пропала
надбавка за питание работников кухни, то есть официальный расход, который она
обязана видеть и провести. Итог по её ведомости упал с 464 752,41 до 434 462,66.

Итоговое решение: суммы вынесены в отдельную таблицу `payslip_totals` (один к
одному), политика стоит на ней. Строка `payslips` остаётся видимой — в ней
больше нет ни одного числа. Вертикальное разделение таблицы — обычный приём там,
где нужна защита на уровне колонок, которой в Postgres нет.

Два других варианта отклонены с причинами (записаны в миграции
`0009_payslip_ledgers`): суммы в разрезе регистра пришлось бы делить по правилу,
которого у партнёра нет (`gross` и взносы считаются от общего нето), а отказ от
суммарных полей потерял бы `gross`, налог и взносы — компонентами они не
являются и из них не выводятся.

**О формулировке требования.** «Ни одного числа, большего суммы видимых
компонентов» буквально невыполнимо: `gross` — это `net / 0.701`, он больше суммы
компонентов даже у строки, где скрытых регистров нет вовсе. Проверяется точная
форма того же требования: **нето каждой видимой строки итогов в точности равно
сумме её компонентов, которые роль видит** — то есть скрытого в ней нет ни рубля.

Что проверка не декоративная, показывает `test_the_protection_is_the_policy_and_
not_luck`: он снимает политику внутри транзакции теста и требует, чтобы проверка
покраснела.

Правки в чужом коде, которых потребовала задача: `payrun/calc.py` пишет итоги в
новую таблицу; `payrun/sheet.py` — только комментарий в шапке, он описывал
прежнее устройство; тестовые вставки `payslips` в `conftest.py` и `test_web.py`
перестали заполнять суммы.

### 2026-08-07 — T052: разграничение больше не держится на суперпользователе

Из трёх путей issue #44 выбран второй, но не в предложенной форме. Выносить
членства в отдельную таблицу без RLS не понадобилось: рекурсия возникала не
из-за того, что функция читает защищённую таблицу, а из-за того, что **политика
этой таблицы сама звала эту функцию**. Достаточно разорвать круг в одном месте.

Первый путь — «зафиксировать требование superuser/bypassrls и проверять его» —
отклонён сознательно: `bypassrls` может выдать только суперпользователь, а на
управляемом Postgres (RDS, Cloud SQL и прочие) суперпользователя не дают
никому. То есть требование означало бы не «настройте площадку», а «продукт туда
не ставится». Проверка честно сообщала бы об этом на площадке заказчика — ровно
то, чего задача просит избежать.

Что сделано:

- **Политика `memberships` перестала звать `app_tenant_ids()`**: условие теперь
  прямое — `user_id = app_user_id()`. Все остальные политики зовут функции
  по-прежнему; глубина стала конечной, потому что корень цепочки самодостаточен.
  Цена — сужение: человек больше не видит членства коллег по тенанту. Ни один
  тест и ни одно место в коде на это не опирались (`principal` читает своё
  членство), а «кто ещё работает у партнёра» из ведомости и не следует.
- **Миграция `0005_app_role` перестала делать `alter role`.** Это была вторая,
  более ранняя поломка, найденная той же проверкой: `alter role ... nosuperuser`
  разрешён только суперпользователю, поэтому обычной ролью схема **не
  накатывалась вовсе** — падала на пятой миграции. Теперь роль либо заводится
  (умолчания `create role` как раз нужные), либо её атрибуты сверяются и при
  `superuser`/`bypassrls` миграция останавливается с внятным текстом и
  подсказкой. Молча продолжать нельзя: роль приложения с `bypassrls` обнуляет
  изоляцию и по работе продукта это не видно. Грант роли тому, кто накатывает,
  выдаётся только если он ещё не член, — повторный требует прав администратора
  роли, которых у обычного владельца может не быть.

Порядок был обратный обычному: сначала `tests/test_plain_owner.py`, потом
правки. Модуль заводит роль без `superuser` и `bypassrls`, накатывает ею
отдельную базу и ходит в неё **третьей** ролью — логин-ролью приложения, тоже
без привилегий и не владеющей таблицами. Обе поломки он увидел до починки:
сначала `permission denied to alter role`, затем `stack depth limit exceeded`
с колонкой из полусотни `SQL function "app_tenant_ids" statement 1`.

Что проверка не декоративна, показывает
`test_the_recursion_would_come_back_with_the_old_policy`: он возвращает прежнюю
политику `memberships` и требует, чтобы запрос снова упал рекурсией
(`StatementTooComplex`), после чего возвращает починенную обратно.

**Находка блока auth снимается — но не самой правкой, а тем, что теперь
возможно.** Тест `test_a_job_that_skips_the_helper_is_not_protected_by_anything`
фиксирует: запрос мимо помощника контекста идёт ролью подключения, и пока ею
был владелец-суперпользователь, он видел всё. Само по себе устройство политик
этого не меняет. Меняется то, что подключаться теперь **можно** обычной ролью —
раньше приложение с не-суперпользовательским владельцем просто не работало.
На такой конфигурации забывчивость даёт пустоту, а не утечку: проверено
`test_a_connection_that_forgets_the_role_sees_nothing` — ноль строк во всех
таблицах с RLS. Чтобы это стало не «можно», а «так и есть», роль подключения
на площадке обязана быть не владельцем; это вопрос развёртывания (T036), и в
нынешнем `docker-compose.yml` приложение по-прежнему ходит суперпользователем.

Границы: административные операции (сид, восстановление дампа) обход политик
по-прежнему подразумевают и без него не работают — первое членство иначе
некому создать. Это записано в контракте как явное разделение, а не умолчание.

### 2026-08-07 — смоук: продукт целиком на базе без суперпользователя

Поднято через `docker compose` отдельным проектом `dodo-pnl-db2-smoke` на

Затем то же самое на конфигурации, которой раньше не существовало:

- роль `owner17` — `nosuperuser`, `nobypassrls`, — накатила **все десять

- данные завёл администратор (`load_presets`, `seed_dev`) — как и положено

### 2026-08-07 — T057: управляющий видит только своих людей

Миграция `0020_employee_visibility`. Пропуск был записан честно ещё в `0011`
(«employees остаются видны целиком: точка у сотрудника не хранится»), и цена
его оказалась выше, чем читалась: `employees.external_id` — это JMBG,
национальный идентификатор, и справочник отдавал его по всей сети.

**Что считается «своим человеком» — решение, а не побочный эффект.** Точки у
сотрудника нет: она в условиях найма, версионируемых по датам. Правило выбрано
такое: свой — тот, у кого есть **хотя бы одна** версия условий найма на видимой
точке, независимо от дат. Каждый случай закреплён отдельным тестом
(`tests/test_employee_visibility.py`):

| случай | что происходит | почему так |
|---|---|---|
| уволенный | остаётся виден своей точке | иначе закрытый период перестал бы читаться: ведомость и табель на месте, а имени к ним нет |
| переведённый в середине месяца | виден обеим точкам | обе версии настоящие; сумм это не открывает — ведомость режется политикой из `0011` |
| версия из будущего | человек уже свой | принят на работу — не «чужой» |
| без условий найма вовсе | виден только тем, у кого нет ограничения по точкам | точку ему не назначали ни разу; это не «ничья строка» из `0011`, где точка была и пропала |

Дата «сегодня» в политике не используется намеренно: с ней один и тот же
закрытый период читался бы по-разному в июне и в июле.

Следствие для записи: управляющий не может завести сотрудника (у нового ещё нет
условий найма). Заводит их администратор сети, у которого ограничения по точкам
нет. Политика `for all`, а не `for select`: иначе чужого человека нельзя было бы
прочитать, но можно было бы переименовать вслепую.

Фактически: 10 новых тестов ролью `app_user`; без миграции пять из них красные,
включая «управляющий видит всех». Порча внутри прогона
(`test_the_protection_is_the_policy_and_not_luck`) снимает политику и требует,
чтобы управляющий снова увидел всю сеть. На живом стенде под управляющим
`select count(*) from employees` — **17 вместо 35**.

### 2026-08-07 — T065: факт наличия скрытого регистра

Миграция `0021_payslip_ledgers_hidden`. Суммы были закрыты (T050), а набор
регистров строки читался всеми в тенанте: запрос `select e.last_name, p.ledgers
from payslips p join employees e ...` под бухгалтером отдавал «Курир →
{internal}». Чисел нет, но D023 требует «ни строк, ни следа», а поимённый список
людей с выплатами в закрытых регистрах — это след.

**Прятать строку `payslips` по-прежнему нельзя** (проверено прошлым заходом:
уносит официальные компоненты смешанного сотрудника). Третья таблица-спутник
тоже не годится: триггеру пришлось бы писать в строку, которую пишущая роль не
видит, обновление молча не нашло бы её, и **неполный набор регистров открывает
итоги** (`'{}' <@ что угодно` — истина). Тихий отказ в сторону «показали
лишнее» — худшее, что тут можно построить.

Сделано иначе: колонка закрыта **привилегией**. Роль приложения теряет табличное
`select` на `payslips` и получает его на все колонки поимённо, кроме `ledgers`.
RLS режет строки и столбцов не умеет — а привилегия на столбец умеет.

Что выяснено фактически по дороге (и то, и другое меняло замысел):

- **`revoke select (ledgers)` при живой табличной привилегии не делает ничего.**
  Отзыв проходит без ошибки, колонка остаётся читаемой. Снимать надо табличную
  привилегию целиком и выдавать колонки поимённо. Сторож на будущее —
  `test_the_columns_the_application_may_read_are_listed_on_purpose`: новая
  колонка без явного гранта роняет тест раньше, чем приложение.
- **Выражение политики проверяется привилегиями вызывающего.** Первая версия
  оставила политику `ledger_visibility` читающей `p.ledgers` напрямую — и итоги
  пропали у **всех**, включая директора: `permission denied for table payslips`.
  Поэтому политика зовёт `app_payslip_ledgers_visible()` (`security definer`).
- **`security definer` даёт права владельца на объекты, но не отменяет `force
  row level security`**, если владелец — обычная роль. Проверено на живой базе
  отдельным опытом. Это две разные вещи, и путать их дорого: на видимость строк
  definer здесь не влияет, читается только колонка уже видимой строки. По той же
  причине `security definer` **нельзя** использовать, чтобы собрать набор
  регистров из `pay_components` — на конфигурации без суперпользователя функция
  увидела бы их через политики, набор вышел бы урезанным и открыл бы итоги.

Триггер `payslip_ledgers_add()` тоже стал `security definer`: он читает и пишет
закрытую колонку. Поле `ledgers` убрано из модели Django (но не из базы) —
иначе ORM спрашивала бы закрытую колонку при любом обращении к `payslips`,
включая удаление ведомостей при пересчёте.

Фактически: 5 новых тестов, два из них красные без миграции; порча
(`test_the_protection_is_the_privilege_and_not_luck`) возвращает табличную
привилегию и требует, чтобы бухгалтер снова увидел чужие регистры. На живом
стенде под бухгалтером тот самый запрос отвечает `permission denied for table
payslips`, а её ведомость не сдвинулась: 44 компонента на 464 752,41.

Правка в чужом тесте, которой потребовала задача:
`tests/test_plain_owner.py::test_the_application_can_still_write` читал
`payslips.ledgers` ролью приложения. Теперь он спрашивает не колонку, а
последствие: бухгалтеру не видны итоги строки дополнительного регистра — то
есть набор заполнился. Так проверка стала даже строже: молча не сработавший
триггер виден как утечка, а не как «ну и ладно».

- **На площадке приложение должно подключаться не владельцем.** Устройство это
  уже позволяет и проверено смоуком (T052), но `docker-compose.yml` поднимает
  продукт под ролью из `POSTGRES_USER`, то есть суперпользователем. Пока так,
  забытый контекст в фоновой задаче показывает всё — тест блока auth это

  на старте, а роль приложения права на DDL не имеет.
  Делать вместе с раскаткой (T036): владелец схемы накатывает
  миграции отдельным шагом, приложение ходит логин-ролью — членом `app_user`,
  без владения таблицами и без права на DDL.
- **Порт `0004_facts.sql` на миграции Django** — за модулем фактов (T005).

### 2026-08-07 — T071: разбор до правки

**Что течёт.** `payslips` видна всем в тенанте, `payslip_totals` — только тому,
кому видны **все** регистры строки. Значит отсутствие итога само по себе
называет человека: `payslips left join payslip_totals ... where t.payslip_id is
null` под бухгалтером отдаёт поимённый список тех, у кого есть выплаты в
закрытых от неё регистрах. Воспроизведено на живой базе до правки.

**Почему «спрятать строку ведомости» не годится — обе формы проверены.**

| правило видимости `payslips` | что получается |
|---|---|
| `ledgers <@ видимые` (подмножество) | вектор закрылся бы, но это ровно то, на чём обожглись в T050: ведомость собирается присоединением к `payslips`, и скрытая строка уносит **видимые официальные** компоненты смешанного сотрудника. Итог бухгалтера падает с 464 752,41 до 434 462,66 — то есть ломает эталон приёмки |
| `ledgers && видимые` (пересечение) | суммы не двигаются (проверено на стенде: смешанный сотрудник остаётся с официальными 100 из 1000), но **вектор не закрывается**: у смешанного сотрудника строка видна, а итога нет — тот же поимённый список |

Кроме того, ограничение по регистру на самой `payslips` **ломает запись**:
ограничивающая политика `for select` блокирует и `update`/`delete` (проверено
опытом на отдельной таблице — `UPDATE 0` по невидимой строке), а роль с
`payrun.calculate` и неполным набором регистров (в сиде это как раз бухгалтер)
после первого же скрытого компонента перестала бы видеть собственную строку:
триггер набора регистров не дописал бы её, пересчёт не удалил бы её, а вставка
следующего компонента получила бы отказ политики. Тихая неполнота набора при
этом **открывает** итоги (`'{}' <@ что угодно`).

**Корень глубже, чем конкретный запрос.** Течёт не «этот left join», а то, что
**видимость производной строки зависит от её содержимого**. Пока она зависит,
любая пара «строка видна всегда — производная видна не всегда» называет людей.
Отсюда правило, которое и делается: **видимость `payslip_totals` определяется
только ролью, а не содержимым строки** — итоги видны роли, которой видны все
регистры вообще (все значения типа `ledger`), и не видны никому другому. Тогда
видимых итогов либо столько же, сколько видимых строк ведомости, либо ноль —
третьего состояния, по которому можно кого-то опознать, не существует.

**Цена, которую надо знать.** Бухгалтер перестаёт видеть сохранённые итоги
вовсе, включая полностью официальные строки (раньше видела 8 из 35 — и это как
раз и был список). Её экран не меняется: ведомость собирается из
`pay_components`, а не из итогов, и `payslip_totals` в продукте сегодня никто не
читает (пишет только расчёт). Чтобы у бухгалтера были бруто и налоги по
официальному регистру, итоги надо раскладывать по регистрам — а это вопрос к
бухгалтеру партнёра (как делить взносы, считанные от общего нето), уже
отклонённый в T050 как «придумать бухгалтерию, которой у партнёра нет».
Заведён issue.

**Соседняя утечка той же формы, которая этим не закрывается.** `payslips left
join pay_components where c.id is null` под бухгалтером называет тех, у кого
видимых компонентов нет вовсе (в сиде — курьеры внутреннего регистра). Закрыть
это можно только спрятав строку ведомости — то есть сломав запись (см. выше).
Причём информации это почти не добавляет: те же люди видны как «есть часы в
табеле, но нет ни рубля в моей ведомости» — табель по регистрам не режется и
резаться не должен. Подробности и issue — ниже по журналу.

**Позиция про табель подтверждена при T100 (2026-08-13), issue #57 остаётся
открытым.** Вопрос переоткрыла шестая утечка регистров: сверка печатала тот же
состав списком. Разобрано и решено в журнале блока `timesheets` — коротко:
регистр учёта режет **деньги, а не факт работы**, а разрезав табель, вектор не
закроешь, он переедет на справочник сотрудников (тот режется по точкам, а не по
регистрам, T057) — 35 человек в справочнике против 31 в табеле дают тот же
список вычитанием. Плюс у табеля нет своего регистра: у смешанного человека часы
неделимы, и относить строку к регистру целиком значило бы выдумать данные.
Найдена и граница позиции: при `work_measure: fixed_amount` в табеле лежит сама
сумма выплаты (`timesheets.piece_value`, D032) — issue #85, проверено фактически.

### 2026-08-13 — T101: заморозка строки, расчёта которой роли не отдали

Записано вслед за задачей: агент, закрывший её (коммит `13da8a7`), был остановлен
исчерпанной квотой до того, как дошёл до журнала. Ниже — устройство по коду
задачи и то, что проверено заново.

**Что течёт.** У `payslips` политики `ledger_visibility` нет вовсе (есть у
компонентов, итогов и шагов следа) — срез по регистру на этом маршруте держало
приложение, и на нём его забыли. Бухгалтер с одним официальным регистром морозил
и размораживал строку внутреннего: `POST /payslips/<id>/freeze/` отвечал `302`, а
случайный uuid — `404`. Три следствия, и каждое отдельное: запись по невидимой
строке проходила; пара «302 против 404» работала оракулом существования (перебор
выясняет, какие строки лежат в скрытых регистрах); спорная строка исключается из
переноса разницы (T026) — то есть отметка меняла деньги в чужом регистре.
Нарушение D014: забытый фильтр обязан давать пустой результат, а не утечку.

**Как закрыто.** Тем же приёмом, что видимость итогов (T071): условие сделано
**свойством роли, а не строки** — морозит тот, кому видны все регистры учёта
(`app_sees_every_ledger`). Правило «можно морозить, если все регистры строки
видны» здесь не годится и отвергнуто с доводом: разрешение, зависящее от
содержимого строки, само называет людей — по тому, на какой строке ответ
меняется.
