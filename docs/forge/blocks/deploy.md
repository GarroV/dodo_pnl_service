# Блок: deploy

## Назначение

Продукт, поднятый там, где им можно пользоваться, и проверки, не дающие сломать его
незаметно. Выделен отдельно, потому что площадка накладывает свои ограничения:
домашний Windows-сервер с чужими соседями по портам и по Docker.

## API-контракт

Наружу отдаёт запущенный продукт и набор переменных окружения.

**Канонический список переменных — таблица в `README.md`** плюс `.env.example`
с именами и безопасными значениями. Здесь он намеренно не дублируется: копия
разъехалась с кодом ровно так, как предсказывает конституция (в ней не хватало
`DEV_LOGIN`, `DJANGO_DEBUG`, `DJANGO_ALLOWED_HOSTS`, `DODO_TEST_ADMIN_DSN` и
трёх `HEALTHCHECK_*`) — это и было задачей T046.

Для площадки из всего списка критичны три: `APP_PORT` (8030 на сервере, 8000
локально), `POSTGRES_HOST_PORT` (5440, только на `127.0.0.1`) и `DEV_LOGIN=0`,
без которого вход-заглушка пускает любого директором.

Ограничения площадки, которые нельзя нарушать:

- **свой compose-проект** из `C:\projects\_template`, свой Postgres-контейнер;
  существующий стек `supabase-*` принадлежит staging Swarm Brain и не трогается;
- заняты и не используются: 8020, 8043, 5433, 6543, 5678, плюс порты БД ботов;
- контейнер базы помечается `backup.pgdump=true`, чтобы попасть в существующую
  задачу резервного копирования сервера;
- GUI и долгие процессы не запускаются напрямую из ssh — только через задачу
  планировщика, иначе процесс убивается вместе с сессией.

## Зависимости

Блоки: `db` (миграции применяются при развёртывании), `web` (что именно поднимаем).

Внешнее: Docker Compose на MUSPELHEIM, GitHub Actions для проверок на pull request.

## Роли базы на площадке (T124, issues #66 и #50)

Ролей три, и каждая нужна:

| роль | кто ею ходит | зачем именно она |
|---|---|---|
| владелец схемы (`MIGRATION_DB_USER`) | служба `migrate`, разовые работы обслуживания (`seed_dev`) | право на DDL есть только здесь; сид пишет мимо контекста пользователя, и роль продукта политики не пустят |
| роль продукта (`APP_DB_USER`) | служба `app` | член `app_user`; DDL нет, очередь не читается — полезная нагрузка задач ей не нужна |
| роль очереди (`QUEUE_DB_USER`) | служба `worker` | член `app_user` **и** `queue_worker`: очередь читается соединением напрямую, а данные внутри задачи — через `set local role app_user` |

Права на таблицы `django_q_*` выдаёт **миграция** `0233_queue_worker_role`, а не
рука на площадке: сделанное руками до площадки не доедет. Роли-логины заводит
развёртывание — пароль в миграции появиться не может:

```sql
create role <app>   login password '…' nosuperuser nobypassrls nocreatedb nocreaterole in role app_user;
create role <queue> login password '…' nosuperuser nobypassrls nocreatedb nocreaterole in role app_user, queue_worker;
grant connect on database <база> to <app>, <queue>;
```

Если роли `app_user` и `queue_worker` в кластере уже есть (управляемый Postgres,
общий кластер), владелец схемы должен быть их администратором — иначе миграция
остановится с текстом «некому выдать роль»:

```sql
grant app_user, queue_worker to <владелец> with admin option;
```

Логин-роль веба членом `queue_worker` **не делается**. Иначе защита полезной
нагрузки (`0047_queue_privileges`) держалась бы на дисциплине кода — на том, что
каждый запрос не забыл `set local role app_user`, — а не на правах базы.

### 2026-08-07 — T035: локальный запуск через Docker Compose

Появились `Dockerfile`, `docker-compose.yml`, `.dockerignore`,
`docker/healthcheck.py`, раздел запуска в `README.md` и переписанный
`.env.example`. `src/` не тронут вовсе — маршрутов и экранов не добавлял,
это территория блока `web`.

Принятые решения и почему именно так:

- **Зависимости в образ ставятся установкой самого проекта** (`pip install .`),
  а не списком в `Dockerfile`. Дубль списка разъехался бы с `pyproject.toml`
  молча — при том что в образе всё бы собралось.
- **Внутри контейнера порт всегда 8000**, наружу публикуется `APP_PORT`
  (8000 локально, 8030 на площадке). Так порт в переменной ровно один и
  проверка здоровья не зависит от того, как продукт опубликован.
- **Порт базы прибит к `127.0.0.1`**: `"127.0.0.1:${POSTGRES_HOST_PORT}:5432"`.
  Без явного адреса Docker публикует на всех интерфейсах и обходит фаервол
  хоста — на площадке это означало бы базу с персональными данными наружу.
- **Миграции накатываются командой контейнера на старте**, после
  `depends_on: condition: service_healthy`. Отдельный шаг однажды забудут;
  `service_started` не годится — контейнер базы отвечает раньше, чем Postgres
  готов принимать подключения.
- **Обязательные переменные объявлены через `${VAR:?...}`**: пустой `.env` даёт
  внятную ошибку на `docker compose config`, а не приложение с пустым паролем.
- **`DATABASE_URL` контейнеру собирается из `POSTGRES_*` с хостом `db`**, а
  значение из `.env` описывает путь с хоста (`127.0.0.1:5440`) и нужно pytest
  и `manage.py` из venv. Одной строкой оба случая не описываются.
- Метка `backup.pgdump=true` на контейнере базы — проверена фактически:
  `docker inspect --format '{{json .Config.Labels}}'` отдаёт `"backup.pgdump":"true"`.
  Что она действительно попадает в ночную задачу сервера, проверяется в T036.

**Проверка здоровья и доказательство, что она не декоративная.**
`docker/healthcheck.py` ходит в две половины: HTTP-запрос к самому себе
(живым считается ответ со статусом меньше 500) и подключение к базе из
процесса приложения. Проверки только порта было бы недостаточно: сокет открыт,
пока жив процесс, даже если база лежит и всё отдаёт 500.

Проверено фактически, три состояния:

1. Продукт работает — `docker compose exec app python docker/healthcheck.py`
   печатает `здоров`, код возврата 0; оба контейнера в `docker compose ps`
   в состоянии `healthy`.
2. `docker compose stop db` (приложение живо, база лежит) — та же проверка:
   `нездоров: база недоступна (OperationalError: failed to resolve host 'db')`,
   код возврата 1. Сам Docker перевёл контейнер в `unhealthy` примерно за 30 с,
   в `docker inspect` три записи подряд с кодом 1. После `docker compose start db`
   вернулся в `healthy` — то есть проверка не залипает в красном.
3. Веб не слушает (`HEALTHCHECK_PORT=9999` на живой базе) —
   `нездоров: сервер не отвечает ... Connection refused`, код 1. После
   `docker compose stop app` запрос с хоста получает `curl: (7) Failed to connect`.

**Прогон с нуля по README** (после `docker compose down -v` и удаления образа):
`cp .env.example .env` → `docker compose up -d --build` → оба контейнера
`healthy` за ~16 с, миграции применились сами (11 штук core + служебные) →
`seed_dev` дал тенант `rs-dev`, 3 точки, 32 сотрудника → `GET /` вернул 200.
В базе с хоста: 32 сотрудника, 3 точки, 3 роли.

Тесты: **43 зелёных, 8 пропущенных** — прогон из venv с переменными из
`.env.example`. Заодно это проверка, что записанный там `DODO_TEST_ADMIN_DSN`
действительно работает против базы из compose. Временных баз после прогона
не осталось (`select datname from pg_database`). `ruff check .` — чисто.

Что осталось честно сказать:

- Приложение поднято **`manage.py runserver`** — это отладочный сервер Django,
  и он сам об этом предупреждает в логе. Для T035 (локальный запуск) этого
  достаточно, но **на площадку так выпускать нельзя**: в T036 команду надо
  заменить на нормальный WSGI-сервер (gunicorn или waitress под Windows),
  добавить его в зависимости и выставить `DJANGO_DEBUG=0`. При `DEBUG=0`
  статику `runserver` уже не отдаёт — понадобится `collectstatic` и
  `STATIC_ROOT`, которого в настройках пока нет.
- Проверка здоровья считает живым ответ 404: пока блок `web` не завёл
  маршруты, корень отдаёт стартовую страницу Django (200). Когда появится
  страница входа, проверку стоит перенацелить на неё — путь берётся из
  `HEALTHCHECK_PATH`, менять код не нужно.
- Правки внутри `src/` не делал ни одной, хотя одна напрашивается: **эндпоинта
  `/healthz` в приложении нет**, и проверка вынуждена опираться на корень.
  Это работа блока `web` или `auth`.
- **8000 по умолчанию конфликтует с разработкой.** Пока шла проверка, в соседней
  копии подняли `manage.py runserver 127.0.0.1:8000` — то есть на хосте
  одновременно оказались dev-сервер и опубликованный контейнером порт. Ошибки
  «адрес занят» при этом не было, и чей ответ приходит на `localhost:8000`,
  становится неочевидно. Дефолт оставлен 8000, как записано в контракте блока
  и в плане, но в README про это сказано прямо: занят — поменяйте `APP_PORT`
  в `.env`. Compose и dev-сервер одновременно на одном порту держать не стоит.

### 2026-08-08 — T058: схему накатывает роль, которая на это уполномочена

Работал блок-агент. Задачи в этот заход — T058 и T037; на MUSPELHEIM не ходил,
это по-прежнему T036 и отдельное «да» владельца. Все проверки — в своей копии
`dodo_pnl_service-dep`, стенд `COMPOSE_PROJECT_NAME=dodo-pnl-dep`, порты 8061/5471.

**Что было не так.** Контейнер приложения стартовал командой `migrate && runserver`.
Пока приложение ходит в базу владельцем схемы (локально это так: `POSTGRES_USER`
образа — суперпользователь), разницы не видно. На конфигурации площадки, ради
которой делался T052, роль приложения права на DDL не имеет — и первая же новая
миграция уронила бы контейнер приложения на старте, а выглядело бы это как
«продукт не поднимается» (issue #50).

**Что сделано.**

- Появилась одноразовая служба **`migrate`**: тот же образ, `restart: "no"`,
  команда `python manage.py migrate --noinput`, роль подключения — своя
  (`MIGRATION_DB_USER`, владелец схемы). Окружение берётся из общего куска
  `x-app-env` через `<<: *app-env`, переопределяется ровно одна строка —
  `DATABASE_URL`. Списки переменных на этом проекте уже дважды разъезжались,
  поэтому второй копии окружения здесь нет.
- `app` и `worker` стартуют по `depends_on: migrate: service_completed_successfully`.
  Забыть про схему невозможно: не накатилась — продукт не поднимается вовсе,
  а не едет на старой схеме. Из команды `app` `migrate` убран.
- Роль продукта вынесена отдельно: `APP_DB_USER`/`APP_DB_PASSWORD`. Обе пары
  переменных в `.env.example` пустые и берут значения из `POSTGRES_*` —
  локально роль одна и вторую заводить незачем, на площадке они разводятся.
- `worker` больше не ждёт живости `app` (прежняя причина «схему накатывает веб»
  исчезла), а ждёт завершения `migrate`.

**Как проверено — запуском, а не рассуждением.**

1. `docker compose up -d --build` с нуля: `migrate` отработал и вышел с кодом 0,
   `app` и `worker` — `healthy`.
2. Заведена пробная миграция `0100_probe_ddl` (`create table probe_ddl_t058`).
3. Ролью продукта без DDL (`probe_app`: `login nosuperuser nobypassrls nocreatedb
   nocreaterole in role app_user`) — воспроизведён ровно дефект #50:
   `django.db.utils.ProgrammingError: permission denied for schema public`,
   `LINE 1: create table probe_ddl_t058 (x int);`
4. Штатным путём: `Applying core.0100_probe_ddl... OK`, код выхода `migrate` — 0,
   в базе `to_regclass('probe_ddl_t058')` не пуст, в `django_migrations` запись есть,
   `app` и `worker` снова `healthy`.
5. Смоук продукта на своём порту: `GET /` → 302, `GET /login/` → 200, обе проверки
   здоровья говорят «здоров». Сид гоняется ролью владельца через ту же службу:
   `docker compose run --rm migrate python manage.py seed_dev` — четыре учётки на месте.
6. **Пробная миграция убрана из репозитория** — продукту она не нужна, заводилась
   только ради проверки. Заодно выяснилось, что просто так временную таблицу не
   заведёшь: `test_force_rls_on_every_domain_table` на неё честно упал
   («RLS не принудительная на: ['probe_ddl_t058']»). Сторож работает.

**Побочная находка, поймана фактически.** Три службы собирали три отдельных
образа из одного Dockerfile. Частичная пересборка (`docker compose build app`)
оставляла схему и продукт на разных сборках кода — молча: контейнеры поднимались,
а `migrate` шёл старым образом и говорил «No migrations to apply». Теперь у всех
трёх один тег `${COMPOSE_PROJECT_NAME:-dodo-pnl}-app`; имя проекта в теге — чтобы
параллельные рабочие копии не перетирали образы друг другу (issue #51).

**Что осталось честно сказать — и это работа T036.** Роль продукта не может быть
ролью «совсем без привилегий»: рабочий процесс очереди этой ролью не работает.

### 2026-08-08 — T037: проверки на каждый pull request

Появились `.github/workflows/ci.yml` и `.github/scripts/check_skips.py`. Три

  печатает «ни одного пройденного теста в: test_schema_access, test_plain_owner».
  То есть зелёный прогон без базы CI не пропустит;
- `docker build -t dodo-pnl-app:ci .` → успешно (образ после проверки удалён);
- `docker compose --env-file .env.example config --quiet` → код 0;
- «падающий тест валит работу» видно на настоящем красном прогоне того же

  возврата 1 — шаг в CI на таком коде красный.

**Чего проверить не удалось и что для этого нужно.** Сам GitHub Actions на этом
файле ни разу не запускался: для этого нужен push ветки, а блок-агент наружу
ничего не публикует. Не проверены поэтому: доступность образа `pgvector` для
службы в раннере, версии действий (`actions/checkout@v4`,
`actions/setup-python@v5`, `actions/upload-artifact@v4`) и время прогона. Файл
разобран как YAML и по структуре сверен (три работы, шаги на месте), но это не
замена запуску.

**И главное, что нельзя сделать файлом.** «Падающий тест блокирует слияние» —
наполовину настройка репозитория, а не конфигурация в нём. Проверено:
`gh api repos/GarroV/dodo_pnl_service/branches/master/protection` отдаёт
`404 Branch not protected` — то есть сейчас слить можно что угодно, даже с
красным CI. Включает это владелец, одной командой, после первого удачного
прогона (раньше нельзя: проверок с такими именами GitHub ещё не видел):

```bash
gh api -X PUT repos/GarroV/dodo_pnl_service/branches/master/protection \
  -H "Accept: application/vnd.github+json" \
  -f 'required_status_checks[strict]=true' \
  -f 'required_status_checks[contexts][]=Линт' \
  -f 'required_status_checks[contexts][]=Тесты' \
  -f 'required_status_checks[contexts][]=Сборка образа' \
  -F 'enforce_admins=false' -F 'required_pull_request_reviews=null' \
  -F 'restrictions=null'
```

Осознанно не включено блок-агентом: защита ветки запрещает и прямой push в
`master`, а стройка сливает ветки блоков локально — включение посреди стройки
остановило бы диспетчера. Это решение владельца и момент после стройки.
