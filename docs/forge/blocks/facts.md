# Блок: facts

## Назначение

Центральная таблица фактов — единственное место, куда стекаются все первичные
финансовые события: выручка из Dodo IS, сырьё и списания, фактуры поставщиков,
зарплата, наличные из кассы, переводы, налоги. Каждый следующий модуль третьей
очереди (ручной ввод, разнесение, выгрузка) пишет сюда, а не заводит своё
хранилище.

Блок начал с фундамента: схема, разграничение доступа и модели Django (T107).
Дальше к нему добавились экраны, которыми этим пользуется человек: справочник
статей расходов (T108), внесение расхода из кассы (T109), список расходов с
правкой и удалением (T110) и разнесение расхода без точки по правилу статьи
(T111). Дальше расходы вышли наружу: те же сценарии запросом, а не экраном
(T112), и выгрузка вместе с демо (T113).

## Контракт

**Таблицы.** `facts` (строка факта = позиция документа), `source_documents`
(первичный документ, прослеживаемость), `fact_batches` (партия загрузки).

**Типы.** `fact_source`, `document_kind`, `fact_allocation`, `batch_status`.
Плюс `pnl_items.kind` получает четвёртое значение — `transfer`.

**Представления** (все `security_invoker = true`, то есть RLS действует):

| представление | что отдаёт |
|---|---|
| `pnl_lines` | действующие факты с раскрытыми справочниками; `split` исключён |
| `pnl_by_unit` | суммы по точке и статье, без переводов |
| `pnl_by_network` | то же без разреза по точкам |
| `facts_unallocated` | суммы без точки — что мешает закрыть месяц |

**Функции записи и разнесения.**

```
upsert_fact(jsonb) -> (fact_id uuid, action text)   inserted | updated | unchanged
upsert_document(jsonb) -> uuid
supersede_fact(uuid, uuid default null) -> void
allocation_plan(uuid) -> setof (unit_id, share, amount, amount_report, rule_id)
allocate_fact(uuid) -> int
reallocate_period(tenant uuid, period date) -> int
fx_rate_on(base text, quote text, on date) -> numeric
fill_report_amounts(tenant uuid, period date) -> int
pnl_report(tenant uuid, period date, unit uuid default null) -> setof строк дерева
```

**Модели Django** — `Fact`, `SourceDocument`, `FactBatch` в `src/core/models.py`:
экраны следующих задач ходят ORM, а не сырым SQL.

**Статьи расходов (T108).** Таблица `expense_items` — то, чем человек называет
трату, — и колонка `facts.expense_item_id`, которой выбранное запоминается.
Статья **ссылается** на строку P&L, а не заменяет её: строк отчёта единицы,
статей у бухгалтера десятки. Названия — словарём по кодам языков интерфейса.
Ведёт справочник тот, у кого `directory.manage`; читают все, кто вносит расходы.

**Правило разнесения по статье (T111).** У `allocation_rules` два возможных
ключа, и ровно один заполнен: `counterparty_id` (фактура поставщика) или
`expense_item_id` (расход из кассы, у которого контрагента нет). Правило
версионируется по датам, ведётся в карточке статьи, а разносить по нему вправе
только тот, кто ведёт все точки партнёра, — иначе план строился бы по половине
точек и молча клал бы всю сумму сети на одну.

**Экраны (T108–T111).**

| адрес | что делает |
|---|---|
| `/directory/expense-items/` | список статей; заведение и правка |
| `/directory/expense-items/<id>/` | статья и её правило разнесения с историей версий |
| `/expenses/` | список расходов с фильтрами и итогом |
| `/expenses/new/` | форма внесения расхода из кассы, включая расход на всю сеть |
| `/expenses/<id>/` | карточка расхода: правка и удаление |
| `/expenses/unallocated/` | суммы без точки и пересчёт разнесения |

**Разграничение доступа.** Три ограничения на `facts`, все по образцу
зарплатных таблиц: `tenant_isolation` (пермиссивная), `ledger_visibility` и
`unit_visibility` (обе `as restrictive`, то есть сужают через AND). На
`source_documents` и `fact_batches` — только изоляция тенанта: ни регистра, ни
точки у этих строк нет.

## Зависимости

Блок `db` (тенанты, точки, юрлица, статьи, контрагенты, правила разнесения,
периоды) и его функции контекста: `app_user_id()`, `app_tenant_ids()`,
`app_visible_ledgers()`, `app_unit_is_visible()`, `app_sees_every_ledger()`.
Внешнего ничего.

**Решение 1: правило разнесения ищется по паре «контрагент + регистр».** Это
единственная правка смысла против исходника. Он искал правило по контрагенту и
брал `limit 1` по дате; с тех пор у `allocation_rules` появилось ограничение
`allocation_rules_no_overlap`, куда входит регистр, — то есть у одного
поставщика **законно** есть два действующих правила, официальное и внутреннее
(один поставщик может оплачиваться и по счёту, и из кассы). Без фильтра по
регистру `limit 1` выбирал бы произвольное из двух и молчал об этом. Такая
конфигурация уже живёт в тестах (`test_ledger_visibility_applies_to_allocation_rules`
заводит ровно два таких правила), то есть это не гипотетический случай.

**Решение 2: `post_payroll_facts` не переносится.** Функция читала
`payslips.tax` и `payslips.contributions` — колонок больше нет, итоги вынесены в
`payslip_totals` (T050) и видны только роли, которой видны все регистры (T071).
Перенести «как есть» нельзя, а переписать — значит сочинить правило о том, что
делать, когда проводящий не видит всех регистров: молча провести зарплату без
налогов было бы худшим из ответов. Работа отнесена к T113, где расходы встают в
выгрузку рядом с зарплатными строками; исходник в истории git.

**Найденный дефект исходника: `upsert_document` не мог завести новый документ.**
`insert ... select (v_new).*` подставляет **явный** null в каждую колонку,
которой не было в jsonb, а умолчание базы при явном null не срабатывает — падало
на `not null` первичного ключа. В `upsert_fact` это сделано правильно
(`coalesce(v_new.id, gen_random_uuid())`), в `upsert_document` забыто. То есть
проверка исходника на живой базе документов не заводила ни разу. Исправлено в
`0230_facts`, поймано тестом `test_document_is_upserted_by_external_id`.

#### T108: что решено и почему

**Статья расходов — не строка P&L.** `pnl_items` это отчёт («Коммунальные»), а
статья — то, чем оперирует бухгалтер, внося трату («вода», «электричество»,
«вывоз мусора»). Их несколько на одну строку отчёта. Один справочник на оба
смысла означал бы выбор между раздутым до сотни строк P&L и потерянной
подробностью внесения. Поэтому `expense_items.pnl_item_id` — ссылка, а не
замена.

**Справочник поставляется пустым — это решение, а не недоделка (Q015).** Список
статей придёт с файла бухгалтера Сербии. Выдуманный список дал бы разные
названия одной трате у нас и у неё, и вскрылось бы это на первой сборке P&L,
когда сходиться уже поздно. Пустое состояние экрана говорит об этом словами и
не предлагает «завести первую статью» как следующий шаг.

**Названия — словарём по кодам языков, а не тремя колонками.** Это исключение из
правила «данные не переводятся» (`web/i18n.py`), и оправдано оно составом
читателей: одну статью выбирает сербский бухгалтер и читает русскоязычный
оперативный директор. Название точки такой пары читателей не имеет, а статья
имеет. Ключи — коды из `settings.LANGUAGES` как есть; второй список языков рядом
с настройками разошёлся бы с ними молча.

**Правка задним числом.** Привязка статьи к строке P&L версий по датам не имеет —
она одна на всю историю статьи, — поэтому её смена при утверждённом месяце
отклоняется `refuse_if_unversioned_touches_closed_month`: тем же отказом, что
схема расчёта группы, и **без выдуманной даты** `0001-01-01` (T103 уже стоил
этого дефекта). Даты `valid_from` и `valid_to` отклоняются обычным отказом с
датой — совет «возьмите дату позже» здесь выполним, поле даты у человека перед
глазами. Правка одних названий проходит всегда: название денег не двигает.

#### T109: три правила и как каждое проверено

**1. Точку отвергает база, а не форма (D014).** Представление точку **не
фильтрует**: пришедшее в запросе уходит в `upsert_fact` как есть, а отвергает
его политика `unit_visibility` на `facts`. Список точек в форме — удобство для
того, у кого их несколько, а не защита. Проверено подменой: в POST кладётся id
чужой точки. Отказ один и тот же для чужой, несуществующей и точки чужого
партнёра — по ответу нельзя понять, что точка существует (D023).

**Найдено по ходу и починено: выдуманный номер точки давал 500, а не отказ.**
Внешние ключи Django объявляет отложенными, то есть проверяет их **на коммите** —
за пределами точки сохранения, в которой ловится отказ. Роли без ограничения по
точкам (`app_unit_is_visible` отвечает «да» тому, у кого все точки) политика
пропускает любой uuid, и запрос обрывался. Лечится `set constraints all
immediate` сразу после записи: отказ приходит на месте и теми же словами, что у
чужой точки. Отдельный тест — `test_a_made_up_unit_is_refused_in_words_even_to_a_role_without_limits`.

**2. Закрытый месяц не двигается ни на копейку.** Закрытый период не принимает
записей вовсе — это свойство схемы (`facts_guard`), а не решение экрана: триггер
отвергает вставку, правку и удаление для всех, включая суперпользователя. Значит
расход, датированный внутри утверждённого месяца, деть в него некуда, и вариантов
два: отказать или положить рядом. Кладём рядом — по D020: запись уходит в
**текущий** период, а `doc_date` остаётся исходной датой. Ссылка на исходный
месяц не текстом в примечании, а строением строки: «за июнь, учтено в августе»
читается запросом, а не словами, которые никто не разберёт. Человеку при этом
сказано словами — «Месяц Июнь 2026 закрыт, поэтому расход записан в Август 2026».

Отказ вместо переноса остаётся ровно в одном случае: закрыт и текущий месяц.
Класть расход в произвольный третий значило бы выдумать за человека, к чему он
относится.

**3. Повторная запись идёт заменой, а не правкой на месте.** У формы есть ключ
записи (`entry_key`), он же ключ идемпотентности факта. Тот же ключ с теми же
данными не пишет ничего — двойное нажатие «Сохранить» не превращает один расход
в два; тот же ключ с другими данными заводит новую версию: старая помечается
`superseded_at`/`superseded_by`, `revision` растёт, действующей остаётся одна.
Ключ случайный, а не выведенный из содержимого: две одинаковые траты в один день
по одной статье — обычное дело, и общий ключ склеил бы их в одну, потеряв
половину денег.

**Регистр расхода (Q013) — оба варианта.** Поле есть, умолчание `official`,
список — только видимые роли. Тому, кто про регистры не думает, делать ничего не
нужно; механизм при этом на месте и ничего не стоит. За владельца вопрос не
решён.

### 2026-08-14 — T110, список расходов с правкой и удалением

Ведётся по ходу работы. Кто что делал:

| задача | кто | почему так |
|---|---|---|
| тесты списка (контракт задачи) | **сам** | тест здесь и есть приёмка: срез роли, итог и правило замены — это определение готовности |
| правила правки и удаления (`web/cash.py`) | **сам** | деньги и закрытый месяц |
| экран списка и карточка (`web/expenses_views.py`, шаблоны) | **сам** | срез роли и итог неотделимы от выборки; отдавать по частям было нечего |
| переводы на английский и сербский | **исполнитель** | механическая раскладка по готовой процедуре `tools/translations/README.md`, приёмка — четыре теста каталога |

#### Четыре решения экрана

**Срез роли делает база, а не выборка.** В `_rows` нет ни одного условия про
права: ни `unit_id__in`, ни проверки в цикле. Что видно — решают политики
`facts` (D014). Отсюда же поведение фильтров: пришедшие в адресе `?unit=` и
`?item=` уходят в выборку **как есть**, и чужая точка даёт пустой список, а не
отказ и не подсказку. Проверено сравнением двух ответов слово в слово: чужая
точка и выдуманный номер отвечают одинаково (D023).

**Итог — сумма показанных строк.** Считается прямо по тому списку, который ушёл
в разметку, а не вторым запросом `sum(amount)`. Второй запрос был бы вторым
источником истины и разошёлся бы с таблицей молча — тот же довод записан в
`payrun/sheet.py`. У строки есть машиночитаемая сумма (`data-amount`) и
состояние (`data-state`): по ним приёмка сверяет, что итог — это сумма именно
показанных действующих строк. Сумма отдаётся **строкой**, а не числом: числа
Django локализует, и приёмка сверяла бы деньги с языком страницы.

**Удаление — пометка, а не `delete`.** Строка остаётся в списке с состоянием
«удалён» и выходит из итога. Заменённая версия видна как «заменён». Расход,
исчезнувший бесследно, через месяц не проверить ничем.

**Правка закрытого месяца — сторно и новая строка в текущем.** Строку закрытого
месяца нельзя тронуть физически: `facts_guard` отвергает и `update`, и `delete`,
в том числе суперпользователю, — то есть механизм замены версии (`revision`,
`superseded_at`), которым идёт правка открытого месяца, здесь неприменим. Молча
отказать значило бы оставить бухгалтера с неверным числом навсегда. Поэтому
исходная строка остаётся нетронутой, а в текущий месяц ложатся две: сторно на её
сумму и исправленная запись (D020).

Почему пара строк, а не одна дельта: правка меняет не только сумму — у расхода
могут поменяться статья, точка и регистр. Дельта верна только при правке суммы,
в остальных случаях она молча ставит деньги не в ту статью. Пара «минус старое,
плюс новое» верна всегда. Ключи исправлений выводятся из ключа исходной записи
(`…#storno`, `…#fix`), а не случайные: повторная отправка той же правки не
должна давать второе сторно.

### 2026-08-14 — T111, расход без точки и его разнесение по правилу

Ведётся по ходу работы. Кто что делал: **всё сам** — задача целиком про
миграцию, политики и деньги (правило разнесения решает, на чьи точки лягут
чужие суммы), то есть ровно то, что бриф запрещает отдавать исполнителю.
Механический кусок в задаче ровно один — раскладка переводов, и она отдана
**исполнителю** по процедуре `tools/translations/README.md`.

#### Главное решение: у правила разнесения появился второй ключ

Механизм разнесения в схеме был с T107, но найти правило он умел **только по
контрагенту**: так приходят фактуры поставщиков. У расхода из кассы контрагента
нет и взяться ему неоткуда — справочника контрагентов продукт не ведёт, фактур
не принимает. Человек, внося трату, выбирает **статью расхода**, и именно она
отвечает на вопрос «аренда офиса — как её разложить по точкам».

Поэтому `allocation_rules` получила второй ключ — `expense_item_id`, — и ровно
один из двух у правила заполнен (`allocation_rules_one_key`). Отдельной таблицы
не заводилось: правило — это метод, точка для `fixed_unit`, регистр и период
действия независимо от того, чем оно вызвано, а две таблицы означали бы две
копии версионирования по датам и два места, куда смотрит `allocation_plan`.

Непересечение версий пришлось выразить **вторым** ограничением: `=` считает
`null = null` за «не совпало», поэтому старое `allocation_rules_no_overlap`
правила по статье между собой не сравнивает вовсе.

Ведётся правило в карточке статьи расходов, а не отдельным разделом: человек
думает о нём именно так — «аренда разносится поровну». Седьмой справочник развёл
бы по двум экранам одно решение. История версий показана там же: по ней видно,
каким правилом посчитан закрытый месяц, — а это первое, что спрашивают при
расхождении в отчёте.

#### Два дефекта, найденные задачей

**1. Разнесение теряло статью расхода.** `allocate_fact` и `reallocate_period`
собирают ребёнка из полей родителя списком, а колонка `facts.expense_item_id`
появилась позже них (T108). Разнесённый расход становился безымянным в списке
расходов и переставал находиться фильтром по статье — молча, потому что строка
P&L оставалась на месте и отчёт сходился. Обе функции переписаны целиком; тест —
`test_the_children_keep_the_expense_item`.

**2. Разнесение зависело от того, кто его запустил.** `allocation_plan` читает
`units` под политиками вызвавшего. У управляющего список точек короче, и план
выходил не половинным, а **правдоподобным**: вся сумма сети ложилась на его
единственную точку, и никакой ошибки при этом не возникало. Два человека,
нажавших одну и ту же кнопку, получали бы разные числа и не узнали бы об этом.
Найдено тестом (`test_the_manager_cannot_spread_an_expense_over_other_units`
показал 100.01 на NS1 вместо отказа).

Закрыто в базе, а не на экране: `allocate_fact` и `reallocate_period` отвергают
вызов, если у вызвавшего список точек урезан (`app_unit_ids(tenant) is not
null`) — с кодом `42501`, тем же, каким отвечает политика. Условие спрашивает и
про контекст: без контекста ходит владелец схемы (обслуживание, миграция
данных), у которого список не урезан вовсе. Продукт переводит отказ в слова:
«разнести его по точкам может тот, кто ведёт все точки».

**3. `seed_dev` снова перестал быть идемпотентным** — ровно как в T109, только
теперь на правиле разнесения: ссылка правила на статью `PROTECT`, а статьи
убирались раньше правил. Сид падал `ProtectedError` на любом стенде, где правило
хоть раз завели с экрана, — то есть ломался способ чинить стенд, а не продукт.
Найдено **смоуком** (уборка за собой), тестами не ловилось и не могло. Тест —
`test_seed_survives_an_allocation_rule`.

Задача делалась в два захода: первый агент оборвался (сторож не увидел движения

Кто что делал:

| задача | кто | почему так |
|---|---|---|
| эндпоинты, маршруты, тесты сравнения, смоук | **первый агент, сам** | доступ и деньги: обёртка не имеет права дать больше, чем экран |
| прогон всего набора, линт, проверка порчей, повторный смоук | **сам** | приёмка; на спасённой работе она не гонялась ни разу |
| раскладка переводов (11 строк) | **исполнитель** | механическая раскладка по готовой процедуре `tools/translations/README.md`, приёмка — тесты каталога |

#### Главное решение: у эндпоинта нет ни одного своего правила

`src/web/api.py` не содержит ни одной проверки прав, ни одного правила о
деньгах и ни одной своей выборки. Разбор формы — `cash_views.parse_expense`,
запись — `cash.*`, строки списка — `expenses_views`. Тело JSON кладётся в
`request.POST` и дальше идёт **тем же** разбором, что форма. Если бы здесь
появилась вторая копия хоть одного правила, у продукта стало бы два ответа на
вопрос «что видно и что можно записать», и разошлись бы они молча: экран
проверяется смоуком, а вызов — нет.

Отсюда способ приёмки: каждый сценарий гоняется **дважды**, экраном и запросом,
и ответы сравниваются построчно и до копейки (`tests/test_expenses_api.py`).
Проверка «эндпоинт вернул 200» зелена и у обёртки, которая отдаёт больше экрана.

Пять условий спеки (`spec.md`, «API и будущая MCP-обёртка») и что им отвечает:

| условие | как выполнено |
|---|---|
| роль и тенант — контекстом базы | выражено **отсутствием кода**: срез никто не собирает, его делают политики `facts` |
| срез по регистру — параметр запроса | `?ledger=` сужает и никогда не расширяет |
| запись только POST | GET на запись — 405 с `Allow`, причина уезжает в строку тем же полем, что у формы, автора ставит база |
| отказ по невидимому неотличим от несуществующего | чужая точка, чужая статья, чужой расход отсекаются политиками до представления — отличаться им физически нечем |
| долгие операции отвечают идентификатором работы | долгих у расходов нет: список ограничен окном, пересчёт принимает **один** месяц за вызов |

Про последнее подробнее: кнопка на экране обходит все ждущие месяцы сама — она
отвечает человеку, который смотрит на страницу и видит, что работа идёт. Вызову
держать соединение неограниченным обходом нельзя, а заводить идентификатор
работы не за чем: пересчёт месяца — один оператор в базе. Поэтому месяц
обязателен, и его отсутствие — отказ, а не умолчание.

Деньги отдаются **строками**, а не числами: двоичная дробь превращает 80756.32 в
80756.32000000001 на первом же потребителе, а локализация — в «80 756,32».

#### Проверка порчей

### 2026-08-14 — T136, отказ базы по ограничению вместо белой страницы

Ведётся по ходу. Стенд — `dodo-pnl-fix1`, порты 8090 (продукт), 8100 (демо),
5500 (база). Задача сделана **сам**: механическим её нельзя было отдать —
главное решение здесь не код, а граница «что переводится в слова, а что обязано
падать громко», и подобрана она чтением каталога ошибок Postgres против того,
как в этом продукте устроен ввод.

**Что было.** Администратор заводил статью расходов с уже занятым кодом и видел
белую страницу 500: `duplicate key value violates unique constraint
"expense_items_tenant_code_uniq"` (issue #109). Соседние проверки той же формы
(пустое поле, неверный выбор, дата в закрытом месяце) отвечали понятным текстом
и 400 — выбивался ровно этот случай. Того же класса issue #98: отложенные
внешние ключи Django проверяются на коммите, за пределами `try` представления, и
выдуманная ссылка тоже давала 500; там это закрыли на одном экране (`web/cash.py`).

**Почему нельзя было починить экран.** У каждой таблицы справочника свои
уникальные ключи и свои ссылки: код статьи, код точки, код группы, юрлицо у
точки — четыре разных ограничения в четырёх формах. Починка одного экрана
оставляет остальные и выглядит как решение.

**Решение — `src/web/dbrefusal.py`, один помощник на все формы.** `saving()`
делает три вещи, и без каждой из них 500 возвращается: точка сохранения (иначе
отказ обрывает транзакцию всего запроса), `set constraints all immediate`
(иначе отложенный внешний ключ проверяется на коммите — уже негде объяснять) и
перевод отказа в слова формы. Колонки ограничения спрашиваются **у каталога
базы**, а не выводятся из имени: большинство наших ограничений написано руками
в миграциях и именам Django не подчиняется.

**Что переводится и почему не всё.** Ровно три класса: `23505` (ключ занят),
`23503` (ссылка в никуда), `23P01` (пересечение периодов). Это те отказы,
которые возможны при исправном коде и правильном вводе кого-то другого. Всё
остальное — пустое обязательное поле (`23502`), проверка (`23514`),
сторож-триггер (`P0001`) — падает как падало: вежливое «поправьте ввод» на месте
дефекта прячет поломку в журнал, и она живёт там месяцами. Отдельная проверка
стоит именно на этом (`test_a_constraint_broken_by_a_defect_still_falls_loudly`).

`BadInput` переехал из `directory_views` в этот же модуль (отказ базы — его
частный случай, а модуль экранов импортировать оттуда нельзя). Прежний адрес
рабочий: экраны берут класс отсюда и отдают дальше, поэтому все
`from .directory_views import BadInput` получают **тот же** класс, а не второй
такой же. Новый `ConstraintRefused` — наследник: его уже ловят все формы, вызов
по HTTP и разбор ввода расхода, а своё имя нужно, чтобы формы, отвечающие на
обычный `BadInput` кодом 200 (точки, юрлица), отдавали на отказ базы честные 400.

Применён на шести формах: статьи расходов, сотрудники (карточка и условия
найма), группы, точки, юрлица, календарь.

**Тесты** — `tests/test_constraint_refusal.py`, 6 штук. Повторный код проверяется
**на трёх разных экранах** параметризацией: проверка на одном зеленела бы и на
починке «по одному», ради которой issue и заведена. Плюс: отвергнутая форма не
оставляет за собой строку; отложенный внешний ключ отвергается на месте (внешний
`atomic` изображает `ATOMIC_REQUESTS` — без `set constraints` тест падает на «не
поднято ни одного исключения»); дефект по-прежнему падает громко.

Порча (обе пойманы):

| Что сломано | Кто поймал |
|---|---|
| убран `set constraints all immediate` | проверка отложенного ключа: DID NOT RAISE |
| `23505` исключён из переводимых | 4 проверки, все три экрана |

**Проверено на живом стенде** (не только тестами): администратором в браузерной
сессии заведена статья `voda-smoke`, повторная отправка той же формы — **400** и
«Такая запись уже есть: «Код» не повторяется. Задайте другое значение.»,
введённое в поле сохранено, `Traceback` в ответе нет. Точка с занятым кодом
`NS1` — то же самое, 400 и тот же текст. Статья за собой убрана.

**Что осталось следующему.** Приём применён к справочникам; экран правил
(`web/rules_views.py`, ограничение `rule_overrides_no_overlap`) и запись по HTTP
через него не проходят — там свой разбор отказов и чужой блок. Одна строка
`with saving():` плюс `except ConstraintRefused`, но делать это должен владелец
экрана.

**Английская страница проверена отдельно, и она нашла свой дефект.** Кавычки

вместе с фразой, — и англичанин читал `already exists: «Code» cannot repeat`

Проверено на стенде обоими языками: `"Code" cannot repeat` и «Код» не
повторяется».

#### T146. Сумма документа и ставка порознь (D042)

Ответ владельца: «НДС нужен, да… хотя вообще в итоговом ПНЛ мы обычно не
показываем НДС». Это два разных требования, и они разведены:

| требование | как сделано |
|---|---|
| хранить | у факта `vat_rate` (ставка) и `vat_amount` (сумма налога **внутри** `amount`) |
| показывать без налога | у отчётов появилась колонка `amount_net`, и выгрузка P&L берёт её **по умолчанию** |
| но не только без налога | тот же файл по `?vat=gross` отдаёт полные суммы документа |

**`amount` остался суммой документа** — тем числом, что человек видел в чеке.
Сменить его смысл на «без налога» означало бы тихо переоценить все уже
записанные строки и все отчёты, которые на него смотрят.

**Сумму налога считает база, одним местом.** Функция `vat_of(amount, rate)`,
вызывается из `upsert_fact`. Python не считает её нигде: правило округления,
живущее в двух местах, разъезжается на первой правке — и разъезжается в деньгах.
Явно присланный `vat_amount` уважается как есть (так однажды придёт фактура, где
налог указан суммой).

Из этого же вышло и сторно: оно шлёт **ставку и не шлёт сумму**, база считает
налог от отрицательной суммы и получает отрицательный налог. Копия
положительного отменяла бы сумму документа и **добавляла** налог — то есть
уводила бы месяц на два налога вместо нуля. Проверка на это отдельная.

**Дети разнесения делят налог тем же приёмом, что и сумму** (накопленная сумма
минус предыдущая, в `allocation_plan`). Иначе 1200 с 20% на три точки дали бы у
детей 66,67 × 3 = 200,01 против 200,00 у родителя. Это не теория: порча, при
которой ребёнок считает налог сам, красит проверку ровно этой копейкой.

Ставка ограничена **базой** (`facts_vat_rate_range`, 0–100), а не только формой:
150% не бывает нигде, и запись такого по HTTP — дефект, а не ввод, который надо
вежливо поправить.

**Кнопка «Строки для P&L с НДС» появляется, только когда НДС в периоде есть**
(`vat_exists`). Тот же довод, что у налоговой части файла (T141): кнопка,
отдающая ровно тот же файл, обещает разницу, которой нет.

Тесты — `tests/test_vat.py`, 12 штук. Порчи (все три пойманы):

| Что сломано | Кто поймал |
|---|---|
| `collect_expenses` берёт `l.amount` вместо `l.amount_net` | файл по умолчанию приехал с 1200 вместо 1000 |
| `pnl_lines.amount_net` = `f.amount` (налог не вычитается) | та же проверка |
| ребёнок разнесения считает налог сам от своей доли | сумма налога детей 200,01 против 200,00 у родителя |

### 2026-08-16 — T154, деньги оставались в P&L после удаления (находка Н3 сверки 8)

Сделано **самим блок-агентом**, не исполнителем: правка про деньги, и решать в
ней приходилось, что именно снимать при удалении, — контракта на такую задачу
не напишешь заранее.

**Что было.** Расход закрытого месяца сначала правят (продукт честно кладёт в
текущий месяц сторно и исправленную строку), потом решают, что расхода не было
вовсе, и жмут «Удалить расход». Ответ — 302 и возврат в список без единого
слова, а исправленная строка на 700,00 продолжает жить в открытом августе. Это
единственный случай за всю сверку, когда деньги остаются в P&L после того, как
человек их удалил.

Причина: `remove_expense` звал `storno_expense` с ключом `…#storno`, который
правка уже создала. `upsert_fact` видел ту же строку и не делал ничего —
идемпотентность, задуманная против двойного нажатия, сработала на другом
действии, — а `#fix`-строку никто не снимал.

**Что снимается, а что остаётся, и почему именно так.** Снимается исправленная
строка (`#fix`), сторно **остаётся**: только оно отменяет нетронутую строку
закрытого месяца. Снять оба значило бы вернуть в P&L исходные 500,00 — то есть
починить молчание и оставить деньги. Считается это числом, а не словами: сумма
действующих фактов партнёра после удаления обязана стать такой же, как если бы
расхода не вносили вовсе (`test_deleting_a_revised_expense_takes_the_money_out_of_the_pnl`).

Если месяц исправленной строки успел закрыться, снять её пометкой нельзя
(`facts_guard` не даёт), и тогда она сторнируется ключом `…#fix#storno` в
текущий месяц. Некуда и это (текущий месяц тоже закрыт) — приходит отказ словами
из `landing_for`, а не тихий возврат в список: карточка показывает его тем же
местом, что и отказ формы.

**Молчания на кнопке удаления больше нет ни в одном случае.** `remove_expense`
возвращает `Removal` с состоянием (`marked` / `stornoed` / `already`), а список
расходов превращает его в слова. Признаки едут адресом (`?removed=…&month=…`),
как и у пересчёта разнесения: готовую фразу в адрес не положить — её не
перевести и подставить в неё можно что угодно. Заодно список научился читать
`?saved=` от правки: карточка уводила сюда с ним и раньше, а список параметр не
разбирал — подтверждения «правка легла в август» человек не получал вовсе
(мелочь, замеченная той же сверкой рядом с Н3).

**Вызов по HTTP исправлен вместе с экраном.** `POST /api/expenses/<id>/delete/`
отвечает состоянием `removed | storno | already | replaced` и признаком
`correction_withdrawn`; поле `storno` теперь месяц учёта и месяц-источник, а не
слепок записи (у удаления своего факта нет). Дверь одна, ручки две: починка
только на экране оставила бы деньги в P&L у всех, кто ходит вызовом.

**Проверки** — `tests/test_expense_delete_after_revision.py`, 6 штук: деньги
(главная), неподвижность закрытого июня, состав оставшихся строк, слова после
удаления, повторное удаление, вызов по HTTP. До правки красными были 4 из 6.

**Порча.** `_withdraw_correction` заставили возвращать «снимать было нечего» —
покраснели ровно три проверки, включая обе денежные и HTTP. Порча откачена,
`grep ПОРЧА` пуст.

**Переводы** — `tools/translations/t154-expense-delete.json`, 7 строк на оба
языка. Четыре из них `makemessages` пометил `fuzzy`, подставив текст соседней
похожей фразы про правку: показывать их gettext не стал бы вовсе, а после
снятия пометки они врали бы про удаление словами про правку. Пометки сняты

#### Календарь: «Завести месяц» больше не переписывает заведённый

Производственный календарь был единственным справочником продукта, где занятый
ключ не отказ. Точка, касса, группа и статья на повторный код отвечают 400 и
«Такая запись уже есть» (приём T136), а форма «Новый месяц календаря» на уже
заведённый месяц отвечала 302 и молча заменяла 176/22 на 99/9. Прежних чисел
человек не видел ни до, ни после.

Причина — один `update_or_create` на обе формы сразу: и на «завести», и на
«поправить». Теперь заведение именно заводит (`create`), а занятый ключ
отвергает **база** — уникальное ограничение `calendars_country_period_uniq`, —
и человек читает тот же текст, что на остальных справочниках. Правка
существующего месяца осталась правкой: у неё своя форма, свой адрес и свой
`update_or_create`, иначе норму часов закрытого месяца стало бы нечем поправить
(T121, D020).

**Деньги при этом не трогались и не двигались** — и это записано в тесте
отдельной строкой, потому что соблазн переписать находку в «поменял календарь —
поехала зарплата» велик. Норму по каждому сотруднику держит
`timesheets.norm_hours`, необлагаемый минимум движок берёт из пресета страны;
сверка проверила это пересчётом периода до и после подмены.

**Мелочью рядом** (из той же находки): форма принимала 40 рабочих дней в июне с
302 и без вопросов. Верхняя граница теперь считается по самому месяцу
(`monthrange`), а не константой 31, — тогда февраль отличается от января.

#### Загрузка статей: дата из файла читается или называется

В файле бухгалтера `01.06.2026`, в базе `2020-01-01` — умолчание формы.
`date.fromisoformat` такую запись не принимает, а `_date_or` возвращал на неё
то же самое, что на пустую ячейку. Пусто и нечитаемо — разные события: в первом
случае человек ничего не написал, во втором написал, и его не поняли. Соседняя
негодная ячейка того же файла (строка P&L) при этом называется поимённо, то есть
две ошибки одного класса обрабатывались противоположно.

Разбирается теперь ISO и привычная запись Сербии и России — `01.06.2026`,
`1.6.2026` и она же с точкой на конце, как её печатает сербский Excel.
Нечитаемая ячейка **пропускает строку и называет её**, как и неопознанная строка
P&L.

Слэшей в списке нет намеренно, и на это стоит отдельный тест: `01/06/2026` — это
и 1 июня, и 6 января, и выбрать можно только предположением о стране автора
файла. Угаданная не туда дата выглядит как прочитанная из файла — то есть это та
же молчаливая подмена, только на шаг хитрее.

Почему это не косметика: `cash.items_on` отбирает статьи по дате, и статья,
заведённая бухгалтером с июня, после загрузки предлагалась и принималась для
трат за любой прошлый месяц.

это перед нажатием, искал помеченную строку в июне и не находил, а изменение в
августе со своим действием не связывал.

Теперь текст приходит из представления (`delete_notice`) и называет оба месяца
поимённо; если от прежней правки в текущем месяце лежит исправленная строка,
добавляется, что снимется и она (T154). Само поведение при этом не менялось —
оно и было правильным.

#### Инструкция к загрузке справочника (Н8)

Перевод называл колонки **русскими** словами на английской и сербской странице:
`Proizvod traži kolone po nazivu — «Название», «Код», «Строка P&L»`. Это не
непереведённая строка, а переведённая, дающая неверный совет: бухгалтер Сербии,
ради файла которой заведена вся загрузка, переименовала бы рабочие `Naziv` и
`Šifra` в кириллицу, которую у себя не наберёт, — при том что разбор принимает
все три языка сразу.

Исходная строка переписана так, что перечисляет все три написания каждой
колонки (тот же приём, что уже был в тексте отказа по файлу), и заодно называет
колонку даты — после T155 она читается из файла. Переводы переписаны, в них
названия стоят своим языком вперёд.

Проверка (`tests/test_upload_hint_names_real_columns.py`) сделана не «нет
кириллицы», а **сверкой с кодом**: все названия в кавычках вынимаются с живой
страницы на всех трёх языках и нормализуются тем же `_norm`, каким их сверяет
разбор, — то есть тест краснеет и тогда, когда инструкция советует заголовок,
которого `COLUMNS` не знает. Вторая проверка требует, чтобы на английской и
сербской странице был назван хотя бы один заголовок на языке страницы.

**Мелочь, найденная живой проверкой и починенная тут же:** отказ календаря на
занятый месяц называл поля «Страна» и «Месяц», хотя поля «Страна» на форме нет
вовсе — она приезжает от партнёра. `country_code` добавлен в
`NOT_TYPED_BY_A_HUMAN` (`web/dbrefusal.py`); других уникальных ключей с этой
колонкой в схеме нет — проверено запросом к каталогу базы, а не по памяти.
