# Блок: suppliers — платежи поставщикам (четвёртая очередь)

Стенд: `dodo-pnl-sup`, продукт 8095, демо 8105, база 5505.

## Назначение

Деньги, уходящие поставщикам, — самая большая дыра в P&L после зарплаты и
наличных. Блок закрывает три вещи: справочник контрагентов (чтобы траты одного
поставщика складывались, а не рассыпались по написаниям), счёт и платёж как
**разные события с разными датами**, и инбокс классификации — очередь строк, для
которых продукт не смог сам назначить статью и точку.

Выделен в отдельный блок, потому что это новая предметная область поверх уже
готовой схемы фактов, а не правка существующей: `counterparties`,
`source_documents`, `facts` с `doc_date`/`period` и `facts_unallocated` уже есть —
строить надо **поверх них**, а не рядом.

Полная спека очереди — `docs/forge/spec-suppliers.md`. Читать её целиком до
первой строки кода: там сценарии, user stories и границы.

## Задачи

| Задача | Что закрывает |
|---|---|
| T150 | Контрагенты справочником: название, идентификатор у партнёра, действует с даты; ведёт администратор сети, остальные читают |
| T151 | Счёт и платёж — разные события: дата документа, дата денег, период учёта отделены друг от друга |
| T152 | Инбокс классификации: строки без статьи одним списком с суммой, разбор прямо в нём |
| T153 | Траты в выгрузке, HTTP-эндпоинты по условиям спеки API, демо: контрагенты, неоплаченный счёт, непустой инбокс |

## API-контракт

**Страницы** (веб — основной интерфейс, `src/web/`):

| Путь | Кто видит | Что делает |
|---|---|---|
| `/directory/counterparties/` | все роли (правит администратор сети) | список контрагентов, поиск |
| `/directory/counterparties/new/`, `/<id>/` | администратор сети | заведение и правка, версионирование по дате |
| `/invoices/` | бухгалтер, оперативный директор, управляющий (своя точка) | счета за период: контрагент, суммы, оплачено/нет |
| `/invoices/new/`, `/<id>/` | те же | внесение счёта: контрагент, статья, точка, период учёта, дата документа |
| `/invoices/<id>/pay/` | те же | отметка оплаты отдельным событием с собственной датой |
| `/payments/new/` | те же | оплата без счёта (мелкая покупка) |
| `/inbox/` | бухгалтер, оперативный директор | строки без статьи: сумма сверху, назначение статьи и точки прямо в списке |

**HTTP** — по тем же условиям, что уже действуют для расходов (смотреть, как
сделано в третьей очереди, и повторять форму, а не изобретать): те же коды
отказа, та же идемпотентность по ключу источника, тот же формат ошибок.

## Зависимости

Схема фактов (`0230_facts` и далее), справочники, роли и политики RLS — всё уже
построено. Внешних сервисов блок не добавляет.

**Ключ сопоставления с Dodo IS.** У Dodo IS свой справочник поставщиков
(`Accounting → Vendor List`, `Supplies → Raw material receipts`) — при заведении
контрагента сразу предусмотреть поле для их идентификатора, пустое до шестой
очереди. Искать соответствие потом по названию — гарантированная ручная работа.
Подробности — `docs/dodo-is-api.md`.

## Открытые вопросы владельца — не решать за него

`Q017` (считаем ли обязательства или только оплаченное), `Q018` (авансы и оплата
нескольких счетов), `Q019` (отдельный регистр для трат мимо официального
контура). Ответов нет.

По принципу проекта **поддерживаются оба варианта**, а не выбирается один:
счёт и платёж хранятся как разные события в любом случае, поэтому «только
оплаченное» — это фильтр представления, а не другая схема. Регистр строки
следует из источника денег, как решено для кассы в D039. Если по ходу
упрёшься в развилку, которую так не обойти, — скажи диспетчеру, не выбирай.

## Как это ложится на уже построенное (решено блок-агентом до первой строки кода)

Прочитано целиком: `spec-suppliers.md`, `CLAUDE.md`, `decisions.md` (D014, D020,
D023, D031, D036, D039, D040, D042), `docs/dodo-is-api.md`, третья очередь
(`web/cash.py`, `web/cash_views.py`, `web/expenses_views.py`, `web/api.py`,
`web/dbrefusal.py`, `web/tills_views.py`), схема фактов (`0230_facts`, `0233`,
`0236`, `0239`, `0240`), демо (`demo/dataset.py`, `demo/seed.py`), приёмка
(`tests/conftest.py`, `tests/test_facts_access.py`, `tests/test_i18n*.py`).

**Ничего нового рядом с фактами не строится.** Счёт, платёж и строка инбокса —
это `facts` и `source_documents`, которые уже есть. Отсюда бесплатно приезжают
идемпотентность (`upsert_fact` по `dedup_key`), версионирование заменой, защита
закрытого месяца (`facts_guard`), RLS по тенанту, точке, регистру и кассе,
разнесение по правилу (`allocation_plan` умеет ключ «контрагент») и выгрузка
(`pnl_lines` → `collect_expenses`). Второй путь записи обошёл бы всё это разом.

| Событие | Чем выражено |
|---|---|
| Счёт | `source_documents (kind='invoice')` — шапка: номер, дата документа, контрагент, итог. Позиции — `facts` с `document_id`, `doc_date` = дата счёта, `period` = период учёта |
| Платёж по счёту | `facts` со **служебной** строкой P&L `supplier_payment` (`kind='transfer'`), `doc_date` = дата денег, `document_id` = счёт. В P&L не попадает (переводы исключены по `kind`) — расход уже признан счётом |
| Оплата без счёта | обычный расходный `facts` с контрагентом: расход признаётся в момент оплаты, потому что документа нет |
| Строка без статьи | `facts` со служебной строкой P&L `unclassified` (`kind='expense'`) и пустым `expense_item_id` |

**Почему у строки без статьи служебная статья, а не пустое поле.** `pnl_item_id`
у факта `not null`, и сделать его пустым нельзя: `pnl_lines` соединяется со
статьёй внутренним соединением — строка без статьи **исчезла бы из P&L молча**,
а это ровно то, чего требует не допускать DoD («видна числом, а не пропадает»).
Служебная статья вида «расход» оставляет сумму в итоге по сети и в выгрузке,
а инбокс собирается по ней же.

**Три даты разведены полями, которые уже есть:** дата документа — `doc_date`
счёта, дата денег — `doc_date` платежа (это отдельная строка), период учёта —
`period`. Новой колонки «оплачено» у счёта нет намеренно: она была бы вторым
ответом на вопрос, на который отвечает сумма платежей, и разошлась бы с ней.

**Открытые вопросы владельца не решаются** (Q017, Q018, Q019): счёт и платёж —
разные строки всегда, поэтому «только оплаченное» это фильтр списка, а не другая
схема; аванс — платёж без счёта; частичная оплата и оплата нескольких счетов —
несколько платежей; регистр платежа приезжает из кассы (D039), регистр счёта по
умолчанию официальный и выбирается из видимых роли.

## Журнал

### T150 — контрагенты справочником (сделано **сам**)

Не отдано исполнителю: у экрана есть правило, которого нет ни в одном соседнем
справочнике — **список читают все роли, а ведёт одна**, — плюс миграция и три
политики RLS. Механическим по готовому образцу это не было.

Что сделано:

* `0242_counterparties` — `external_id` (ключ Dodo IS, пустой до шестой очереди),
  `valid_from`/`valid_to`, `created_by`; одно название на партнёра; частичная
  уникальность ключа Dodo IS; проверка порядка дат; три ограничивающие политики
  `directory.manage` на запись (чтение открыто всем — иначе счёт не на кого
  выписать). Существующим строкам дата начала проставлена из `created_at`.
* `web/counterparties_views.py` + маршруты `/directory/counterparties/…`, раздел
  в оглавлении справочников, поиск по названию, написаниям и номерам.
* `templates/web/directory/list.html`: ссылка возврата стала переопределяемой —
  общая вела бы половину читателей на отказ.

Чем проверено:

* `tests/test_counterparties.py` — 13 проверок **ролью `app_user`** (изоляция
  партнёров, право вести, уникальность названия и ключа, порядок дат).
* `tests/test_counterparties_screen.py` — 13 проверок настоящими запросами
  (кто читает, у кого кнопка, отказ словами, поиск по написанию).
* **Порча:** `with check (true)` вместо права → краснеют обе проверки права;
  ключ Dodo IS в составном уникальном ключе → краснеет проверка ключа; снятое
  ограничение дат → краснеет проверка дат. Порча откачена.
* `pytest -q` целиком: 1450 прошло, 8 пропущено, красных из-за блока нет
  (i18n-каталоги и число тестов в README поправлены следом).

Переводы: 23 строки заведены руками в оба каталога и собраны; `makemessages` по
рабочему дереву не запускался — извлечение шло в копии репозитория, в настоящие
каталоги перенесены только новые записи. Таблица — `tools/translations/t150-counterparties.json`.
Поле примечания названо «Примечание», а не «Заметка»: сторож каталога
(`test_i18n_catalog`) поймал два русских слова с одним английским переводом.
