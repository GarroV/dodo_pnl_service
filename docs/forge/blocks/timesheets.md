# Блок: timesheets

## Назначение

Ввод часов — то место, где продукт либо экономит бухгалтеру время, либо не нужен ему
вовсе. Два равноправных пути: сетка в интерфейсе и загрузка привычной таблицы.
Выделен отдельно от расчёта, потому что часы живут своей жизнью: их вводят, правят и
закрывают по точкам до того, как считается зарплата.

## API-контракт

```python
timesheet_for(employee_id: UUID, period: date) -> Timesheet
    # собирает из подневного хранения то, что принимает движок:
    # hours по типам, insured_hours, norm_hours

import_partner_table(file, tenant_id: UUID, period: date) -> ImportResult
    # ImportResult: matched: int, created: int, unchanged: int,
    #               unmatched_rows: list[Row], warnings: list[str]
    # идемпотентно: повторная загрузка того же файла ничего не меняет
```

```
GET  /timesheets/<uuid:period_id>/         сетка «сотрудник × тип часа»
POST /timesheets/<uuid:period_id>/cell/    обновление одной ячейки (htmx-фрагмент)
POST /timesheets/<uuid:period_id>/piece/   сдельная величина строки (T075)
POST /timesheets/<uuid:period_id>/import/  загрузка таблицы партнёра (T020)
POST /timesheets/<uuid:period_id>/close/   закрыть часы точки за месяц (T022)
POST /timesheets/<uuid:period_id>/reopen/  открыть часы точки заново (T022)
```

Закрытие и открытие — разные адреса, а не значение поля в общей форме: два
действия с разными последствиями не должны отличаться содержимым скрытого поля.

Период адресуется id, а не датой: так же, как во всём остальном интерфейсе
(`/periods/<uuid>/`).

**Хранение подневное**, даже когда вводится итог за месяц: иначе разнесение по точкам
при переводе сотрудника посреди месяца потребует миграции данных. Ввод итогом
раскладывается по рабочим дням календаря.

## Зависимости

Блоки: `web` (каркас и компоненты), `db` (таблицы табелей и календарей).

Внешнее: openpyxl (уже используется существующим импортёром).

## Definition of Done блока

- [x] Сетка вводится с клавиатуры без мыши: перемещение, ввод, сохранение
- [x] Изменение ячейки сохраняется без перезагрузки страницы и не теряется при
      случайном уходе со страницы
- [ ] Загрузка эталонной таблицы июня 2026 даёт корректный табель на 30 сотрудников
- [ ] Повторная загрузка того же файла ничего не меняет — тест на идемпотентность
- [ ] Испорченный файл (лишний лист, переименованная колонка, текст вместо числа)
      не молчит: строки попадают в `unmatched_rows`, пользователь видит отчёт
- [ ] Подсказки о подозрительном: часов больше нормы, сотрудник без часов,
      отрицательное значение, часы у уволенного
- [x] Закрытие часов по точке отдельно от других точек
- [x] Тест: управляющий не видит и не может править часы чужой точки

## Журнал

### 2026-08-07 — T019, сетка ввода часов

**Что строится.** Экран табеля: строки — сотрудники периода, колонки — типы часов
из пресета страны. Ячейка сохраняется сразу, без кнопки «сохранить всё».
Импорт (T020), отчёт проверок (T021) и закрытие по точке (T022) — третья очередь,
здесь их нет.

**Решение 1: подневная таблица — детализация к строке табеля, а не замена ей.**
D011 требует подневного хранения. Прямолинейный вариант — переделать `timesheets`
в подневную таблицу — сломал бы вход движка: `payrun.calc.collect_cases` читает
`timesheets.hours` как готовый месячный итог, а приёмка второй очереди снята на
конкретных числах. Поэтому заведена `timesheet_days`, ссылающаяся на строку
`timesheets`:

- `timesheets` остаётся тем, что читает движок: месячный итог по типам часов плюс
  поля, которых у дня нет и быть не может — `insured_hours`, `norm_hours`,
  `deduction`, `cash_payout`, `manual_correction`;
- `timesheet_days` — из чего этот итог сложился: дата, тип часа, часы.

Инвариант: `timesheets.hours[тип]` равно сумме дней этого типа. Держится
единственной точкой записи (`timesheets.store`), не формой и не триггером.

Почему это выполняет D011, а не имитирует его. Смысл требования — не переносить
данные, когда сотрудника переводят между точками посреди месяца. Точка стоит на
строке `timesheets` (её ключ — `tenant + employee + period + unit`), то есть
человек на двух точках это две строки. Переезд без подневных данных потребовал бы
угадать, какие часы куда; с ними строка режется по датам механически. Дублировать
точку ещё и на дне не стали: два места для одного факта разъезжаются.

**Решение 2: месячное число раскладывается поровну по рабочим дням.** Партнёр
вводит итог за месяц (D011) — какие именно дни за ним стоят, продукт не знает и
знать не может. Раскладка ровная, по рабочим дням производственного календаря
страны (`calendars.holidays` минус выходные); календаря на месяц нет — пятидневка.
Копейки часа распределяются по остатку: сумма дней **точно** равна введённому
числу, иначе итог поехал бы от самого факта хранения. Каждый день помечен
`source='spread'` — когда придут настоящие подневные данные из Dodo IS, ровную
раскладку будет видно и можно будет отличить от факта.

**Решение 3: строка переходит на подневное хранение целиком и один раз.** Строки
сида и импорта содержат месячные итоги без дней. При первой же правке любой ячейки
строки раскладываются **все** её типы часов, а не только правленый: иначе строка
осталась бы наполовину подневной, и «сумма дней равна итогу» перестало бы быть
проверяемым утверждением. Раскладка сумму сохраняет, поэтому расчёт после неё даёт
те же числа — на это есть тест.

**Решение 4: `insured_hours` сетка не трогает.** Это база для взносов, она не
равна сумме часов (у схем с половиной ставки — своя). По какому признаку сотрудник
попадает в такую схему — открытый вопрос Q005. Пересчитывать её от введённых часов
значило бы придумать правило за бухгалтера и получить правдоподобно неверный
расчёт. Поле остаётся тем, чем его заполнил импорт; в сетке показано отдельной
колонкой только для чтения, чтобы расхождение было видно, а не пряталось.

**Решение 5: грид не подключается.** D017 разрешает Tabulator, но велит начинать с
самого дешёвого. Дешевле некуда: обычные `<input>` в обычной таблице. Tab-порядок,
фокус, доступность и ввод с клавиатуры у браузера уже есть — грид их сначала
отнимает, потом возвращает своим кодом за 400 КБ. Стрелки между ячейками — 40 строк
своего JS. Что из Tabulator реально понадобится (вставка из буфера обмена,
диапазоны) — вопрос импорта, то есть T020, и решать его заранее нечем.

**Решение 6: htmx 2.0.10, файлом в пакете.** Пин версии обязателен (D017): в npm
уже лежит `4.0.0-beta6`, и CDN без пина однажды подменил бы библиотеку молча.
Файл лежит в `src/timesheets/static/` — то есть внутри пакета, а не в корневом
`static/`: в образ копируется только `src/`, и статика в корне до контейнера бы не
доехала. Контрольная сумма файла записана рядом в шапке.

**Решение 7: «не теряется при уходе со страницы» — два пути, не один.** Обычный —
`hx-trigger="change"`: значение уходит на сервер при уходе фокуса с ячейки, то есть
при любом переходе к следующей. Но если человек закрывает вкладку прямо из
поля, браузер вправе оборвать незавершённый запрос. Поэтому ячейки, ответ по
которым ещё не пришёл, досылаются на `pagehide` через `navigator.sendBeacon` —
запрос, который браузер обязан доставить после ухода со страницы. Без второго пути
критерий задачи выполнялся бы «обычно», а обнаруживалось бы это потерянными часами.

**Решение 8: сетка показывает только свои точки.** Управляющий с непустым
`unit_ids` видит и правит строки только своих точек — и на странице, и на записи
ячейки. Это не T022 (закрытие часов по точке) и не T044 (фильтр в ведомости):
это отказ строить редактируемый экран с заведомо открытой дырой. Полное
разграничение по точкам в базе — задача T022.

**Отклонение от контракта блока.** В контракте маршрут записан как
`/timesheets/{period}`; фактически `/timesheets/<uuid:period_id>/`, потому что
периодами весь остальной интерфейс адресуется по id (`/periods/<uuid>/`), а не по
дате. Контракт выше поправлен.

### 2026-08-07 — что осталось незакрытым и почему

* **Кто правил ячейку — не пишется.** След есть только у ручной правки
  бухгалтера (`manual_correction`), у обычного ввода часов автора нет.
  Придумывать под это колонки на ходу — расширение скоупа; но назвать пробел
  надо: когда табель начнут закрывать (T022) и утверждать (T023), «кто поставил
  эти 176» станет вопросом, на который система не ответит.
* **Разграничение по точкам живёт в представлении, не в базе.** Экран чужие
  строки не показывает и не принимает, но политика `timesheet_days` и
  `timesheets` точку не смотрит: прямой запрос ролью `app_user` под управляющим
  видит все точки тенанта. Это ровно то, что должна закрыть T022; на текущее
  поведение стоит тест, который обязан упасть, когда T022 будет сделана.
* **Ровная раскладка — не факт, а следствие ввода одним числом.** Дни помечены
  `source='spread'`, но продукт нигде не показывает, что даты за ними условные.
  Когда появится подневный источник (Dodo IS), это придётся объяснить на экране.

### 2026-08-07 — найдено по ходу: рабочие копии делят один docker-стек

`docker-compose.yml` жёстко задаёт `name: dodo-pnl`. Имя проекта Compose при этом
одно на машину, а не на каталог, — значит **все рабочие копии репозитория
работают с одними и теми же контейнерами и томами**. Проверено фактически, а не
предположено: посреди этой работы параллельный блок поднял стек из своей копии
(порт приложения сменился с 8039 на 8036), а затем снёс его вместе с томом —
моя база с сидом исчезла в середине смоука.

Последствия шире неудобства: `docker compose down -v` из любой копии уничтожает
базу соседа, а `up` молча меняет ему порты. При параллельной стройке это не
редкая случайность, а поведение по умолчанию.

Обход, которым доделана эта работа: задавать имя проекта своим —
`COMPOSE_PROJECT_NAME=dodo-pnl-timesheets docker compose up -d`. Починка — либо
убрать `name` из файла (тогда Compose возьмёт имя каталога и копии разойдутся
сами), либо параметризовать его переменной с умолчанием. Сам файл не трогал: он
общий, а править общее из блока — ровно тот способ терять чужие изменения,
против которого стройка и разведена по копиям.

### 2026-08-07 — починки после сверки со спекой (T061, T062, T066)

Свежий взгляд прошёл продукт как пользователь и нашёл три вещи в этом блоке.
Первая — серьёзная: ввёл 8,5 праздничных часов, «Итого» стало 96,50, а «База
взносов» осталась 88,00, и период посчитался без единого предупреждения.

**Решение 9: база взносов идёт за часами там, где она за ними шла, а где не
шла — расчёт останавливается.** Это оба пути задания сразу, и вот почему ни
один по отдельности не годится.

Пересчитывать базу всегда нельзя. В таблице бухгалтерии это **отдельная
колонка** (`UKUPNO SATI ZA OBRACUN DOPRINOSA`), а не сумма часов, и по какому
признаку человек попадает в схему с минимальной базой — открытый вопрос Q005.
Считать её от введённых часов у всех значило бы придумать правило за
бухгалтера. Решение 4 прошлого захода в этой части остаётся в силе.

Но и оставить как было нельзя: `insured_hours` — вход движка наравне с часами
(`engine.gross_up` и `engine.contributions` читают её в трёх методах), и
устаревшая база даёт правдоподобно неверный расчёт без падения. Конституция,
принцип 1.

Поэтому правило узкое и проверяемое: **сохраняется связь, которая была.** Перед
записью ячейки сравнивается, равнялась ли база сумме часов тех типов, что
пресет помечает `insured: true`. Равнялась — значит база шла за часами, и после
правки она идёт за ними дальше. Не равнялась — значит она задана независимо, и
трогать её нечем: строка помечается в сетке, а `payrun.calc.check_insured_base`
отказывается считать период, называя людей поимённо.

Два следствия, которые стоит знать дальше:

* Флаг `insured` у типов часов был объявлен в пресете с самого начала и не
  читался никем. Теперь у него есть потребитель — `payroll.insured_base`.
  Правило «какие часы входят в базу» осталось в пресете, а не переехало в
  интерфейс.
* Проверка при расчёте смотрит только те схемы, которые базу читают
  (`payroll.uses_insured_hours`). У курьеров (`direct`) и временных работ
  (`temporary`) её нет ни в одной формуле — блокировать их из-за неё было бы
  отказом на пустом месте. Проверено тестом.

Чего это **не** решает: если у партнёра база и правда должна отличаться от
отработанного (контрактные застрахованные часы), человек упрётся в отказ и не
сможет его снять из интерфейса. Снять его правильно нельзя, пока нет ответа на
Q005: пришлось бы либо разрешить любое число (тогда проверка бессмысленна),
либо завести пометку «подтверждено бухгалтером», то есть колонку в схеме и
миграцию — выдумывать её под неизвестное правило рано. На данных сида и июня
2026 расхождений нет ни у кого, так что сегодня отказ не срабатывает ни разу.

**Решение 10: табель отказывает так же, как страница периода.** Колонки сетки —
это типы часов страны, то есть те же правила, на которых стоит расчёт. Нет
правил на месяц — `PayrunRefused` вылетал наружу из представления, и при
`DJANGO_DEBUG=0` человек видел «Server Error (500)». Теперь тот же отказ
показывается плашкой с той же командой (`python manage.py load_presets`) и тем
же кодом ответа 409, что на странице периода. Проверено на поднятом стенде с
`DJANGO_DEBUG=0`.

**Решение 11: объяснение отказа живёт у ячейки, а значение возвращается из
базы.** Три отдельные вещи, и каждая была своим дефектом:

* Подсказка была `<p>` внизу документа. При 35 строках низ страницы за экраном
  (сверка намерила `top=1571` при высоте окна 900), то есть видимый отказ был
  видимым только на бумаге. Теперь это фиксированный блок, который скрипт
  ставит у самой ячейки; в окне 1440×900 он оказывается в 22 px от неё.
* Пометка ячейки была бледной заливкой, неотличимой от соседних. Отказ —
  единственное состояние, ради которого стоит нарушить правило «полоска, а не
  заливка»: рамка, цвет текста и жирное начертание. Ячейку видно в столбике.
* В поле оставался введённый мусор. Теперь сервер и при отказе возвращает
  заголовком то, что **осталось в базе**, и поле возвращается к нему. Правило
  экрана одно и то же в обе стороны: показано ровно то, что подтвердила база.

### Что T020–T022 стоит знать про эту модель

* Импорт (T020) должен писать **через `timesheets.store`**, а не прямым
  `update` месячного итога: иначе итог разойдётся с днями, и инвариант,
  на котором стоит вся конструкция, перестанет действовать. Функция
  `set_cell` для этого годится как есть, `materialize` — тоже.
* Идемпотентность импорта модель не ломает: запись одного и того же числа
  дважды даёт те же дни (тест `test_repeated_save_changes_nothing`).
* Закрытие часов по точке (T022) режется по строке `timesheets` — точка стоит
  на ней, а не на дне. Разнесение часов при переводе внутри месяца делается
  разрезанием дней по дате на две строки; переносить данные не нужно.

| что | зачем |

**Стенд.** Копия `…-ts4`, ветка `feat/ts4`, порты 8052/5460, имя compose-проекта

Предыдущая попытка T022 отброшена целиком: код был написан, но ни разу не
запущен. Замысел ниже — переоценённый, а не унаследованный.

**Что закрывается.** Две дыры и одно новое действие:

1. *Дни чужой точки видны.* На `timesheets` политика по точкам стоит (T044), на
   `timesheet_days` — нет: у дня своей точки не бывает, а через родителя условие
   не проверялось. Прямой запрос ролью `app_user` под управляющим отдаёт дни всех
   точек тенанта. На это стоит тест, который сегодня утверждает дыру и обязан
   быть переписан (`test_manager_cannot_read_days_of_another_unit`).
2. *Закрытия часов нет вовсе.*
3. Право `unit.close` в ролях есть с самого начала и ничего не решает
   (миграция `0022` называет это прямо: политика без экрана — догадка). Теперь у
   него появляется экран, значит появляется и политика.

**Форма.** Миграции `0030` (видимость дней) и `0031` (закрытие). Номера с 0030
— диапазон `0040+` занят блоком payrun, два листа в графе Django ломают слияние.

**Закрытие — строка в таблице, а не колонка статуса у точки.** Точка живёт
годами, закрытие относится к паре «точка + месяц»: колонка на `units` не смогла
бы выразить «июнь закрыт, июль открыт». Отсюда `unit_closures` с ключом
`tenant + unit + period`.

**Открытие обратно — тем же правом и без причины.** Причина обязательна при
откате утверждённого периода (T025): там переписывается уже выданная ведомость.
Здесь закрытие — операционная отсечка «я закончил вводить», и человек, нажавший
её по ошибке, не должен ждать бухгалтера. Действующим закрытием считается строка
с пустым `reopened_at`, а не удалённая строка: история закрытий — единственный
ответ на вопрос «когда точка была готова», и удаление стирало бы его.

**Запрет — политиками, а не проверкой в Python.** Та же логика, что у видимости
точек (T044) и прав роли (T064): приложение объясняет словами, база гарантирует.
Форма политик взята у `0022`: `for insert/update with check` — отказ громкий;
тихого «изменено 0 строк» здесь допустить нельзя, иначе гонка (точку закрыли
между открытием страницы и досылкой ячейки) выглядела бы как удачная запись.

**Как это сочетается с заморозкой утверждённого периода (T023).** Проверено по
коду `0041`, а не предположено: заморозка стоит на `payruns`, `payslips`,
`payslip_totals`, `pay_components` и табеля **не трогает** вовсе (правка входных
данных задним числом — T026). Пересечения по таблицам нет, поэтому один и тот же
отказ двумя разными словами не объясняется: на пути записи в табель запрет ровно
один — закрытие точки, а на пути записи в расчёт — ровно один, утверждение.
Разница в механизме намеренная и объяснимая: утверждение — юридическая
заморозка, её обязан соблюдать и суперпользователь, поэтому триггер; закрытие —
операционная отсечка внутри партнёра, её соблюдают пользователи приложения,
поэтому политика (обслуживание и сид обязаны иметь возможность писать).

**Порядок работ:** тесты (ролью `app_user` и через экран) → `0030` → `0031` →
приложение и экран → смоук в живом браузере.

### 2026-08-08 — T022: как сделано и что решено по ходу

**Решение 12: закрытие — своя таблица, а не колонка статуса.** `unit_closures`
из прошлого замысла названа `timesheet_closures`: у `units` уже есть `closed_at`
в смысле «пиццерия закрылась совсем», и два «закрыто» рядом читались бы как одно.
Ключ — «тенант + точка + месяц», действующее закрытие это строка с пустым
`reopened_at`, частичный уникальный индекс держит «одно действующее на точку и
месяц». Открытие заново не удаляет строку, а помечает её: закрывать и открывать
можно много раз, и «когда точка была готова» — вопрос, на который система обязана
отвечать.

**Решение 13: запрет — политиками, заморозка расчёта — триггерами, и это не
противоречие.** Разобрано по коду `0041`, а не предположено: заморозка
утверждённого расчёта стоит на `payruns`, `payslips`, `payslip_totals`,
`pay_components` и табеля **не трогает вовсе** (правка входных данных задним
числом — T026). Пересечения по таблицам нет, поэтому один и тот же отказ двумя
словами не объясняется: на пути записи в табель запрет ровно один — закрытие
точки; на пути записи в расчёт — ровно один, утверждение.

Разница в механизме намеренная. Утверждение — заморозка уже выданной ведомости,
её обязан соблюдать и суперпользователь, поэтому триггер. Закрытие часов —
операционная отсечка внутри партнёра: её соблюдают пользователи приложения, а
обслуживание (сид, восстановление из дампа) обязано мочь писать. Поэтому
политики, там же, где вся остальная изоляция (D014, T044, T064).

**Решение 14: закрыты обе таблицы табеля, и запрет читается через родителя.**
Месячный итог собирается из дней (`store`), поэтому закрыть `timesheets` и
оставить `timesheet_days` значило бы запереть парадный вход, оставив чёрный.
У дня своей точки нет — она у строки-родителя; правило живёт в одной функции
`timesheet_row_closed()`, а не повторяется условием на каждой таблице.

Обе функции — `security definer`. Иначе политика запрета читала бы закрытия
глазами того, кого она ограничивает, и невидимое закрытие означало бы «не
закрыто»: запрет снимался бы сам собой у того, кто его не видит.

**Решение 15: у права `unit.close` наконец появился потребитель.** Оно стояло в
ролях с самого начала и ничего не решало — `0022` называет это прямо: политика
без экрана есть догадка. Теперь есть экран, поэтому есть и политика. Право не
подразумевается из других: у директора сида его нет, и его не пускает ни
интерфейс (кнопки нет, сказано почему), ни база.

Побочное следствие, которое стоит знать: **закрыть точку сегодня может только
управляющий**. Так устроен сид ролей, и это соответствует спеке («управляющий
вводит и закрывает часы по своей точке»), но директор, желающий закрыть точку за
уехавшего управляющего, этого не сможет. Права ролей ведёт блок db/auth — менять
их из этого блока значило бы править чужое; названо здесь, чтобы не потерялось.

**Решение 16: загрузка таблицы отказывает построчно, а не падает.** Транзакция у
импорта одна на файл, и одна закрытая точка уносила бы вместе с собой все
остальные листы, а человек прочитал бы «файл не удалось прочитать как книгу
Excel» — неправду о причине. Теперь строки закрытой точки попадают в отчёт
поимённо, остальное загружается.

**Граница, названная честно.** Политика правки — `with check` без `using`
(форма из `0022`, чтобы отказ был громким, а не тихим «изменено 0 строк»).
Следствие: `update`, **переносящий** строку табеля из закрытой точки в открытую,
политикой не ловится. Сегодня такого пути нет ни в интерфейсе, ни в импорте —
точка строки берётся из условий найма и не меняется; разнесение при переводе
внутри месяца делается разрезанием дней, и запрет для него надо писать вместе с
ним, а не угадывать сейчас. Тихий отказ здесь был бы хуже: точку могут закрыть
между открытием страницы и досылкой ячейки, и «изменено 0 строк» приложение
приняло бы за удачную запись.

**Строки без точки не закрываются никогда.** `unit_id` обнуляется при удалении
пиццерии, такая строка не принадлежит ни одной точке: закрыть её нечем, а прятать
от правки значило бы потерять часы молча.

### T075 — курьеры: часы и сдельная величина как два равноправных пути

Основание — D032, ответ владельца на Q011. Чем в Сербии платят курьерам,
бухгалтер не ответил, поэтому поддержаны оба способа, а выбор сделан **правилом**
`groups.<код>.work_measure`, а не веткой в коде.

**Состояние на входе.** Задачу вёл предыдущий агент, остановленный исчерпанной
квотой. Три коммита: движок (`1b0c385`), порядок импортов (`5dee0fb`) и
спасённые диспетчером правки схемы, расчёта и экрана (`1f609d9`) — последние **ни
разу не запускались**. Первым делом влит master и прогнан весь набор:

| красные | все четыре — `tests/test_i18n.py`: семь новых строк экрана без перевода и `.mo` не собран |

То есть спасённый код оказался рабочим, а незакрытыми остались хвосты. Их два, и

**Дыра, найденная прогоном: `check_measures` была написана, но не вызвана.**
Функция отказа по неизвестной мере работы стояла в `payrun/calc.py` мёртвым

объяснения. Тест написан до правки, красный получен именно на `ValueError`,
после правки — зелёный.

**Правки движка** (их две, обе от предыдущего агента, обе объясняю здесь, потому
