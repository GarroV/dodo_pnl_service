# Блок: web

## Назначение

Каркас интерфейса: шаблоны, навигация, формы, локализация на три языка, админка
справочников. Выделен отдельно, чтобы экраны табеля, периода и отчётов строились на
готовом основании, а не каждый по-своему.

## API-контракт

Отдаёт другим блокам:

- базовый шаблон с навигацией, переключателем языка и индикатором тенанта и роли;
- набор компонентов оформления: таблица с итогами, форма, диалог подтверждения,
  плашка ошибки, метка регистра учёта;
- соглашение по htmx: частичные обновления возвращают фрагмент шаблона, а не JSON;
  атрибуты `hx-*` только в шаблонах, свой JavaScript — только в островке табеля;
- функции локализации: строки через штатный механизм переводов Django, файлы
  переводов в репозитории.

Соглашение по числам, обязательное для всех экранов: деньги выравниваются по правому
краю моноширинным начертанием, разделители — по локали, ноль отличается от пустого
значения визуально.

## Зависимости

Блоки: `auth` (текущий пользователь, права).

Внешнее: Django 6.1 (шаблоны, `django.contrib.admin`, механизм переводов),
htmx 2.x — версия зафиксирована, файл лежит в `static/`, не тянется с CDN.

## Definition of Done блока

- [ ] Интерфейс переключается между русским, английским и сербским; непереведённых
      строк на экранах нет
- [ ] Демо всегда открывается на английском независимо от языка пользователя
- [ ] Админка ведёт справочники: сотрудники, группы, точки, юрлица, календарь
- [ ] Экраны не разъезжаются на ширине от 1280 и не ломаются на 768
- [ ] Клавиатурная навигация по формам работает, фокус виден
- [ ] htmx и грид лежат в `static/` с зафиксированной версией; ни одной внешней
      загрузки со стороннего домена
- [ ] Ошибка сервера показывается человеку понятной плашкой, а не белым экраном

Что в этот заход **не** делается (следующие очереди, не мой скоуп):
локализация ru/en/sr, настоящий вход и права, админка справочников, htmx-грид
табеля, оформление, ведомость и расчёт (T042). DoD блока выше написан на весь
блок целиком — в T041 закрывается только каркас.

Найденное по коду, что определяет решения:

- Пользователей сида в базе нет как записей `auth_user` — есть только
  `memberships.user_id` (голый uuid, детерминированный `det_id('user', code)`
  в `seed_dev`). Значит dev-вход — это выбор uuid, а не логин Django.
- `ATOMIC_REQUESTS = True` оборачивает в транзакцию **только вызов
  представления**, а не middleware. `set local role` из обычного middleware
  ушёл бы в автокоммит и не подействовал. Поэтому контекст выставляется внутри
  собственного `transaction.atomic()` в middleware, а `ATOMIC_REQUESTS`
  остаётся как второй контур (становится вложенной точкой сохранения).

### 2026-08-07 — T041: каркас, dev-вход, контекст пользователя в базе

Что появилось (`src/web/`):

| Файл | О чём |
|---|---|
| `dbcontext.py` | `set_db_context()` и middleware: транзакция запроса, `set local role app_user`, `set_config('app.user_id', …, true)` |
| `devauth.py` | вход «на время стройки»: три учётки сида, выключатель `DEV_LOGIN` |
| `principal.py` | кто вошёл: тенант, точки, видимые регистры; форма из контракта блока `auth` |
| `views.py` | список периодов, страница периода, вход и выход |
| `format.py` | деньги и названия регистров для показа |
| `templates/web/*.html` | базовый шаблон с шапкой, список периодов, страница периода, страница входа |

Маршруты: `/` (редирект), `/periods/`, `/periods/<uuid>/`, `/dev/login/`,
`/dev/logout/`. Переменная окружения: `DEV_LOGIN` (в `.env.example`).

> Эта таблица описывает состояние на конец T041. `devauth.py` во второй очереди
> заменён настоящим входом блока `auth` — актуальный состав файлов и маршрутов
> см. в записи от 2026-08-07 про T055 ниже.

Решения, принятые по ходу, и почему:

- **Транзакцию открывает само middleware.** `ATOMIC_REQUESTS` оборачивает
  только вызов представления, а middleware работает вне её — `set local` ушёл
  бы в автокоммит и не подействовал. `ATOMIC_REQUESTS` оставлен вторым
  контуром: внутри он становится вложенной точкой сохранения.
- **В сессии лежит код учётки, а не uuid.** В контекст базы попадает только
  один из трёх известных пользователей сида, а не любое число из cookie.
  Список учёток берётся из самой команды сида (`ROLES`, `det_id`), не
  переписывается — иначе разъедется с базой при первой правке сида.
- **Сессии — подписанной cookie** (`signed_cookies`). Запрос идёт ролью
  `app_user` внутри транзакции с контекстом, и запись сессии в базу тянула бы
  за собой права и политики на служебную таблицу. Настоящий вход выберет
  хранилище сам.
- **Чужой период и несуществующий отвечают одинаково (404).** По ответу нельзя
  установить, что период существует у другого партнёра.
- **Своей статики не заводил.** htmx и грид (D017) нужны на экране табеля;
  пустой `static/` с невостребованной библиотекой был бы мусором. Оформление
  пока в `<style>` базового шаблона.
- **Заготовка под ведомость показывает итоги по регистрам.** Это не расчёт
  (он в T042), а самое дешёвое место, где видно главное требование D023: итог
  считается по видимому срезу, а не маскируется на выводе.

Тесты — `tests/test_web.py`, 18 штук, живой Postgres со схемой и сидом.
Прогон: **61 passed, 8 skipped** (пропуски — сверка с настоящей таблицей, файла
нет и не должно быть). Покрытие 83% при пороге 80%; по `src/web/` — от 95%.

Проверка тестов порчей (конституция: проверка, которая не падает, — не
проверка):

- убрал `set local role app_user` → красными стали **8** тестов, включая
  видимость регистров, «без входа пусто» и выход;
- заменил `set_config(…, true)` на `false` → упал тест на то, что контекст не
  переживает транзакцию: `app.user_id` остался жить на соединении после
  коммита. Это ровно тот сценарий утечки на следующего пользователя из пула.

Проверка в живом браузере (свой headless Chrome, протокол отладки, клики
настоящими событиями мыши; сервер на 127.0.0.1:8000, база `dodo_pnl_web_smoke`
из `migrate` + `seed_dev`). Чтобы видимость регистров было на чём проверять,
в базу вручную положены три компонента выплаты — официальный 100 000,
дополнительный 50 000, внутренний 25 000:

| Сценарий | Что увидел |
|---|---|
| без входа, `/periods/` | периодов нет, тенанта нет, объяснение вместо данных |
| бухгалтер | Июнь 2026, 32 сотрудника; итоги: **только официальный 100 000,00**, «Итого» тоже 100 000,00 |
| директор | те же страницы; итоги: 100 000,00 + 50 000,00 + 25 000,00, «Итого» **175 000,00** |
| смена пользователя | шапка и суммы меняются в тот же переход |
| выход | список периодов снова пуст, ссылка на страницу периода отдаёт 404 |
| `DEV_LOGIN=0` | `/dev/login/` → 404, `/periods/` без данных даже с прежней cookie |

Ошибок в консоли браузера нет.

**Дефект, найденный в браузере и починенный здесь же:** многострочный
`{# … #}` — не комментарий Django (он однострочный), поэтому исходник шапки
вываливался текстом на каждую страницу. Тестами это не ловилось: они смотрели
на наличие нужного, а не на отсутствие лишнего. Заменено на
`{% comment %}`, добавлен тест на регрессию.

Что стоит знать следующему (T042 и блок `auth`):

- Ленивые выборки в шаблоне обязаны выполняться внутри запроса: контекст живёт
  в транзакции middleware. Поэтому представления отдают `render()` и списки, а
  не `TemplateResponse` с недосчитанным queryset'ом.
- `web/dbcontext.py` и `web/devauth.py` — временный дом кода блока `auth`.
  При появлении настоящего входа меняется источник пользователя, а не
  потребители: они ходят через `current_principal()`.
  *(Так и вышло: во второй очереди `devauth.py` заменён на `auth.py` блока
  `auth`, представления и шаблоны не менялись.)*
- Единицы измерения на странице периода (норма часов) берутся из первого
  табеля — заглушка, при разных нормах по точкам будет врать. Настоящее место
  этой цифры — календарь.
