## A. Продукт

**Проблема** (из документа, `discovery.md`). Партнёры Dodo ведут управленческий учёт в таблицах.
Всё на ручном труде: платежи, накладные, зарплаты, касса вбиваются людьми каждый день. Расходы
не привязаны к точкам — бухгалтерия работает с юрлицом, для неё пиццерии не существует. Данные
лежат в разных системах и не бьются между собой. Зарплата пересчитывается руками каждый месяц:
формулы зависят от календаря, ставок, коэффициентов, типа занятости, праздничных и ночных часов,
отпусков и больничных. Ошибки видно поздно или не видно вовсе.

Сейчас обходятся Excel-таблицами: на июнь 2026 по Сербии это 8 листов, 30 сотрудников,
четыре разные схемы расчёта, всё пересобирается руками.

**Аудитория** (из документа): бухгалтер партнёра, оперативный директор, управляющие точек,
администратор сети. Роли с разными правами и разным срезом данных — в том числе разной
видимостью регистров учёта.

**Главные сценарии** (первый — в скоупе MVP):

1. **Расчёт зарплаты за месяц.** Бухгалтер открывает период, вводит или импортирует часы
   сотрудников по типам (обычные, праздничные, отпуск, больничный), запускает расчёт, видит
   ведомость по сотрудникам с разбивкой на компоненты, правит что нужно, утверждает период.
   На выходе — ведомость к выплате и готовые строки для P&L, где начисления и налоги раздельно.
2. Внесение расхода наличными с телефона за несколько касаний (за пределами MVP).
3. Сборка месячного P&L из накопленных данных (за пределами MVP).

**Критерий успеха MVP.** Бухгалтерия Сербии считает очередной месяц в системе параллельно
со своей таблицей, и цифры сходятся. Технически: расчёт июня 2026 через веб-интерфейс на
данных, введённых через интерфейс, даёт тот же результат, что нынешний регрессионный тест.

**Что точно НЕ делаем в первой версии:** платежи поставщикам, импорт банковской выписки,
коннектор Dodo IS, классификатор документов, сборку P&L, Telegram, аналитику и дашборды,
мультивалютную консолидацию. Всё это — следующие модули из `CLAUDE.md`.

## B. Поверхности

**Через что пользуются** (из документа + ответ владельца):

| Поверхность | В MVP | Назначение |
|---|---|---|
| Веб-интерфейс | **да** | Основная: ввод часов, запуск расчёта, просмотр и утверждение ведомости, справочники |
| HTTP API | **да** | Закладывается сразу, веб работает поверх него; позже на нём же Telegram |
| Telegram | нет | Поверх готового API, следующие модули |

**Встраивается ли в существующую систему:** нет, живёт сам по себе. Позже — интеграция
с Dodo IS как источником часов и выручки, но это отдельный модуль и чужой контракт.

**Язык интерфейса:** мультиязычность закладывается с самого начала. Базовый язык — **русский**,
дополнительно английский и сербский. Демо-режим — всегда английский. → [D005](decisions.md)

**Телефон или компьютер:** приоритет компьютера — бухгалтер работает за десктопом с таблицами.
Телефон важен для будущего модуля наличных, в MVP достаточно, чтобы вёрстка не разъезжалась.

**Публичная и закрытая части:** всё закрытое, публичной части нет. Исключение — демо-режим
на изолированных выдуманных данных.

## C. Функционал

**Возможности с приоритетом** (скоуп MVP — «зарплатный модуль целиком», ответ владельца):

| Приоритет | Возможность |
|---|---|
| must | Вход и роли: у роли — набор точек и набор видимых регистров учёта |
| must | Справочники: сотрудники, группы, точки, юрлица, производственный календарь |
| must | Ввод часов за период: вручную по типам часов + импорт из xlsx (импортёр уже есть) |
| must | Правила расчёта в БД, а не в YAML: пресеты стран + переопределения по уровням |
| must | Цикл периода: черновик → расчёт → правки → утверждение, закрытый период не пересчитывается молча |
| must | Ведомость: по сотрудникам, с разбивкой на компоненты, с фильтром по видимым регистрам |
| must | Выгрузка: ведомость к выплате и строки для P&L |
| must | Демо-режим на изолированных выдуманных данных, самовосстанавливающийся |
| nice | Разнесение зарплаты по точкам при переводе сотрудника в середине месяца |
| nice | Сравнение периода с предыдущим и подсветка аномалий |
| nice | История правок с указанием, кто и что менял |

**Что нельзя ломать.** Работающего продукта нет, поэтому единственное — уже достигнутая
точность расчёта: `tests/test_serbia_june_2026.py` обязан оставаться зелёным на всех этапах.
Движок воспроизводит расчёт бухгалтерии за июнь 2026 по 30 сотрудникам и четырём схемам;
любое изменение, которое это ломает, считается регрессией, а не улучшением.

**Готовый контракт:** формат зарплатных таблиц партнёра (вход импортёра) менять нельзя —
он приходит извне. Сам импортёр уже написан и работает.

**Аккаунты:** нужны. Продукт мультитенантный, изоляция данных партнёров обязательна,
анонимного режима нет (кроме демо).

**Права** (из документа): роль определяет и набор доступных точек, и набор видимых регистров
учёта. Бухгалтер не видит внутренний регистр. Управляющий точки видит только свою точку.

**Что продукт хранит.** Персональные данные сотрудников партнёра: ФИО, национальный
идентификатор (в Сербии JMBG — используется как сквозной ключ `ext_id`), даты найма,
ставки, суммы выплат, больничные. Это чувствительные данные третьих лиц — отсюда прямое
ограничение: в репозиторий они не попадают ни при каких условиях. → [D003](decisions.md), [D004](decisions.md)

**Готовые решения** (из документа, `discovery.md`): прямого аналога нет. Западные ресторанные
ERP (Restaurant365, MarginEdge, Ottimate) — дорогие, только официальный учёт, заточены под США.
Ближе всего по стратегической цели — франчайзинговые платформы вроде Qvinci. Из открытого кода
полезны движок расчёта зарплат с правилами в конфиге и self-hosted разбор счетов через LLM.
Уточняется в фазе исследования.

## F. Ограничения

**Срок:** нет. «Чем раньше тем лучше» — глубину первой версии под дату не подрезаем.

**Стек:** Python 3.11+ задан существующим кодом (сейчас venv на 3.12.13, ruff 0.16.1,
зависимости: pyyaml, openpyxl, pytest). Хранилище — Postgres. Веб-фреймворк и способ
авторизации не выбраны — это развилки для исследования. Прямых запретов нет.

**Деньги:** внешние платные сервисы не используются, продукт живёт на своём сервере.
Бюджет фактически нулевой.

**Правовое и приватность:** хранятся персональные данные сотрудников партнёра, включая
национальные идентификаторы. Данные живут только в базе на сервере владельца, никогда
в репозитории и никогда в облаке третьих лиц. Владелец решил разместить на домашнем сервере
осознанно, после того как риск был назван → [D007](decisions.md).
