### 7.4. Известные несовместимости и депрекейты, которые нас касаются

**Django 6.0 → уже применимо, если стартуем на 6.1**
([6.0 release notes](https://docs.djangoproject.com/en/6.0/releases/6.0/)):
- поддержка Python сузилась до 3.12/3.13/3.14 — 3.10 и 3.11 отпали;
- `DEFAULT_AUTO_FIELD` теперь по умолчанию `BigAutoField` (нам это подходит, у нас всё на uuid);
- кастомные ORM-выражения обязаны возвращать `params` **кортежем**, а не списком;
- `Model.save()` при forced update без затронутых строк кидает `Model.NotUpdated`
  вместо общего `DatabaseError`;
- `Field.pre_save()` теперь может вызываться несколько раз — реализации должны быть идемпотентны;
- появились **template partials** (`{% partialdef %}` / `{% partial %}`) — прямо полезно для
  HTMX-фрагментов из раздела 2: фрагмент живёт в том же шаблоне, что и страница.

**Django 6.1** ([6.1 release notes](https://docs.djangoproject.com/en/6.1/releases/6.1/)):
- **поддержка PostgreSQL 14 снята**, минимум 15 — у нас 17, не задевает;
- депрекейт всей старой почтовой конфигурации: `EMAIL_BACKEND`, `EMAIL_HOST`, `EMAIL_PORT`
  и прочие `EMAIL_*` → новое `MAILERS`; `mail.get_connection()`, аргументы `connection`
  и `fail_silently` тоже депрекейтнуты. Если в проекте появится отправка почты (сброс пароля) —
  сразу писать через `MAILERS`, а не копировать примеры из старых туториалов;
- депрекейт `select_related()` без аргументов и `values_list(flat=True)` без имени поля;
- новые режимы `fetch_mode` (`FETCH_PEERS`, `FETCH_RAISE`) — `FETCH_RAISE` полезен как
  предохранитель против N+1 в отчётных экранах.

**psycopg2 vs psycopg3.** Django 6.0 всё ещё поддерживает psycopg2 (минимум 2.9.9), но пул
соединений (`OPTIONS: {"pool": …}`) работает **только с psycopg3** — «This requires
`psycopg[pool]` or `psycopg-pool` and is **ignored with psycopg2**»
([databases](https://docs.djangoproject.com/en/6.1/ref/databases/)). Раз пул нам нужен
(раздел 3), драйвер однозначно psycopg3.

**pytest 8 → 9.** `pyproject.toml` требует `pytest>=8.0`, а на машине уже стоит 9.1.1 —
то есть проект де-факто на pytest 9, при том что зафиксировано «>=8». Ломающее в 9.0.0
([changelog](https://docs.pytest.org/en/stable/changelog.html)): снята поддержка Python 3.9;
`pytest x.py x.py` теперь считается одним запуском (раньше гонялся дважды), вернуть старое —
`--keep-duplicates`; CI-режим включается только если `$CI`/`$BUILD_NUMBER` непустые;
**все предупреждения `PytestRemovedIn9Warning` стали ошибками**, а сами фичи убраны в 9.1.
Практический вывод: поднять нижнюю границу в `pyproject.toml` до `pytest>=9.1`, чтобы
«у меня работает, у коллеги нет» не случилось.

**ASGI и постоянные соединения.** Если когда-нибудь поедем на ASGI: «When using ASGI,
persistent connections should be disabled. Instead, use your database backend's built-in
connection pooling» ([databases](https://docs.djangoproject.com/en/6.1/ref/databases/)).
То есть `CONN_MAX_AGE` и ASGI несовместимы, и это ещё один довод за встроенный пул psycopg3.

**PgBouncer.** Нам он не нужен (один сервер, один процесс приложения), но если появится —
в transaction pooling режиме требуется `DISABLE_SERVER_SIDE_CURSORS = True`, потому что
серверные курсоры переживают конец транзакции, а следующая транзакция может уехать на другое
соединение (там же). Это ровно та же семья багов, что утечка контекста тенанта из раздела 3.

## 3. Доступ к БД и RLS с прокидыванием tenant_id

> Раздел вынесен вперёд остальных, потому что это единственная развилка с настоящим риском:
> утечка данных между тенантами хуже неверного расчёта (формулировка из задания).

### 3.1. Как это устроено в Postgres — механика и гарантии

**`SET LOCAL` живёт ровно одну транзакцию.** PostgreSQL 17,
[SQL SET](https://www.postgresql.org/docs/17/sql-set.html):

> «The effects of `SET LOCAL` last only till the end of the current transaction, whether
> committed or not.»

и там же:

> «Issuing this outside of a transaction block emits a warning and otherwise has no effect.»

Это и есть ключ к безопасности при пулинге: значение **не может** пережить транзакцию, поэтому
переиспользование соединения другим запросом не тащит чужой `tenant_id`. Обратная сторона того же
факта — **грабля номер один**: если код по недосмотру выполнит `SET LOCAL` в автокоммите
(вне явной транзакции), Postgres не упадёт, а тихо выдаст warning и проигнорирует установку.
Дальше политика увидит пустой GUC. Именно это делает «молчаливый сбой» из глобальных правил
реальным сценарием, а не теоретическим.

**Параметризация: только `set_config`.** `SET LOCAL` — утилитная команда, она не принимает
bind-параметры, поэтому подстановка tenant_id в текст SQL — прямой путь к инъекции. Правильная
форма — функция, у которой значение идёт обычным параметром. PostgreSQL 17,
[System Administration Functions](https://www.postgresql.org/docs/17/functions-admin.html):

> `set_config ( setting_name text, new_value text, is_local boolean ) → text`

`is_local = true` даёт ровно семантику `SET LOCAL`. Читается симметрично:

> `current_setting ( setting_name text [, missing_ok boolean ] ) → text` — «Returns the current
> value of the setting… `current_setting` throws an error unless `missing_ok` is supplied and is
> true (in which case NULL is returned).»

Отсюда канонический вид:

```sql
-- в начале КАЖДОЙ транзакции приложения, параметром, не конкатенацией
select set_config('app.tenant_id', $1, true);

-- в политике
using (tenant_id = current_setting('app.tenant_id', true)::uuid)
```

`missing_ok = true` обязателен: иначе транзакция, где GUC не выставлен, падает с ошибкой вместо
того, чтобы не увидеть ни одной строки. Что предпочесть — вопрос вкуса; безопаснее падать,
но тогда фоновые задачи и миграции надо аккуратно выводить из-под политик.

**Грабля номер два, самая тихая: владелец таблицы обходит RLS.** PostgreSQL 17,
[Row Security Policies](https://www.postgresql.org/docs/17/ddl-rowsecurity.html):

> «Superusers and roles with the `BYPASSRLS` attribute always bypass the row security system when
> accessing a table. Table owners normally bypass row security as well, though a table owner can
> choose to be subject to row security with `ALTER TABLE … FORCE ROW LEVEL SECURITY`.»

Это самая опасная ловушка для нашего сценария. По умолчанию в Docker-образе Postgres приложение
подключается ролью `postgres` — суперпользователем и владельцем. Все политики будут написаны,
`enable row level security` выполнен, тесты «на изоляцию» напишутся и **пройдут**, потому что
данные и правда видны — а видны они не потому, что политика разрешила, а потому что RLS вообще
не применялся. Обнаружится это на проде, когда в базе появится второй партнёр.

Отсюда два обязательных требования к схеме:

1. Приложение ходит **отдельной ролью** (`app_user`), которая не владелец таблиц, не суперпользователь
   и без `BYPASSRLS`. Владелец таблиц — отдельная роль (`app_owner`), которой ходят только миграции.
2. На всех таблицах с `tenant_id` — не только `ENABLE`, но и `FORCE ROW LEVEL SECURITY`, чтобы
   даже случайное подключение владельцем не проехало мимо.

Там же документировано поведение по умолчанию, которое нам на руку:

> «If no policy exists for the table, a default-deny policy is used, meaning that no rows are
> visible or can be modified.»

То есть «забыли написать политику» = ничего не видно. Ошибка громкая, а не тихая — это правильная
сторона fail-safe. Но: `ENABLE ROW LEVEL SECURITY` надо не забыть на **новой** таблице,
и вот это уже забывается молча. Нужен тест-детектор (см. раздел 8).

### 3.2. Утечка контекста между запросами при пулинге — где именно она возникает

Утечка возможна **не при `SET LOCAL`**, а при трёх других вещах:

**(а) Использовали `SET` вместо `SET LOCAL` (или `set_config(..., false)`).** Тогда значение
session-scoped и живёт до конца соединения. Соединение вернулось в пул, следующий HTTP-запрос
другого тенанта получил его — и унаследовал чужой `app.tenant_id`. Если при этом код по какой-то
ветке не выставил GUC заново (ранний `return`, кэшированный запрос, health-check), политика
пропустит чужие строки.

Психопг тут ничем не страхует. Из официальной документации
[psycopg3 / Connection pools](https://www.psycopg.org/psycopg3/docs/advanced/pool.html), раздел
«Connections life cycle», при возврате соединения:

> «if there is a transaction open, the transaction is committed (if the block is exited normally)
> or rolled back (if it is exited with an exception); **if a `reset` callback was provided**, the
> connection is passed to it, to allow application-specific cleanup if needed»

`reset` в [API ConnectionPool](https://www.psycopg.org/psycopg3/docs/api/pool.html) — параметр
со значением по умолчанию `None`. То есть psycopg3 **не делает `DISCARD ALL` сам**. Session-scoped
GUC переживёт возврат в пул. Вывод: либо только `SET LOCAL`/`set_config(...,true)`, либо
`reset=lambda conn: conn.execute("DISCARD ALL")` — но `DISCARD ALL` сбрасывает и prepared statements,
и это уже плата за невнимательность.

SQLAlchemy страхует чуть лучше, но не полностью: у пула
[reset on return](https://docs.sqlalchemy.org/en/20/core/pooling.html) по умолчанию
`reset_on_return="rollback"` — «The pool includes “reset on return” behavior which will call the
`rollback()` method of the DBAPI connection when the connection is returned to the pool».
`ROLLBACK` откатывает `SET LOCAL`, но **не** откатывает session-scoped `SET`. Документация это
прямо оговаривает: «“reset on return” consisting of a single `rollback()` may not be sufficient»
и упоминает `DISCARD`, `RESET`, `DEALLOCATE`, `UNLISTEN` как то, что может понадобиться.

**(б) Транзакция не открыта — GUC не выставился.** Разобрано выше: warning, тишина, пустая
выборка (или, если `missing_ok=false`, ошибка). В `asyncpg` это особенно легко словить: там
каждый запрос вне явного `async with conn.transaction()` идёт в автокоммите, и `SET LOCAL`
уходит в никуда. В SQLAlchemy 2.0 всё наоборот — соединение всегда «begin once» при первом
запросе, транзакция подразумевается, и это на нашей стороне.

**(в) Соединение отдали задаче, которая переживает запрос.** Фоновый воркер, `BackgroundTasks`,
кэш-прогрев. Тут проблема не в GUC, а в том, что контекст тенанта надо явно передавать в задачу,
а не наследовать.

### 3.3. Как выглядит корректная реализация

Единственно надёжная форма — **прокидывать tenant_id в момент открытия транзакции, в одном месте,
и не давать коду возможности взять соединение мимо этого места**.

SQLAlchemy 2.0, синхронный вариант (события пула + явная транзакция):

```python
# один вход в БД на всё приложение; ручного engine.connect() в коде быть не должно
@contextmanager
def tenant_session(tenant_id: str, user_id: str):
    with Session(engine) as s:
        s.begin()                       # явная транзакция ДО любого SET LOCAL
        s.execute(
            text("select set_config('app.tenant_id', :t, true), "
                 "       set_config('app.user_id',   :u, true)"),
            {"t": tenant_id, "u": user_id},
        )
        yield s
        s.commit()
```

Почему именно так, а не через `event.listen(engine, "begin")`: в обработчике `begin` нет
контекста запроса (кто сейчас пользователь), протаскивать его туда придётся через
`contextvars` — работает, но добавляет невидимую связь, которую через полгода никто не найдёт.
Явный `tenant_session(...)` как единственная точка входа читается и проверяется грепом.

Чтобы «взять соединение мимо» стало невозможно, помогает архитектурный приём: `engine` не
экспортируется наружу модуля `db`, наружу торчит только `tenant_session` и отдельный
`admin_session` (для миграций и системных задач, ходит ролью-владельцем, помечен явно).

Проверяемое утверждение, на котором всё держится, — тест из раздела 8: открыть две транзакции
подряд на **одном** соединении из пула с разными tenant_id и убедиться, что вторая не видит
строк первого. Плюс тест, что после транзакции `current_setting('app.tenant_id', true)` пуст.

### 3.4. Сравнение трёх кандидатов под наш профиль

| | SQLAlchemy 2.0 (Core, без ORM или с тонким ORM) | asyncpg + сырой SQL | psycopg3 (sync) + сырой SQL |
|---|---|---|---|
| Версия | 2.0.51 (2026-06-15) | 0.31.0 (**2025-11-24**) | 3.3.4 (2026-05-01) |
| Пул | свой, `reset_on_return="rollback"` по умолчанию | свой (`asyncpg.create_pool`) | `psycopg_pool`, `reset=None` по умолчанию |
| Транзакция по умолчанию | «begin once», подразумевается | **автокоммит** — `SET LOCAL` молча не сработает | автокоммит вне `with conn.transaction()` |
| Параметризация | именованные, `:name` | **только `$1`, позиционные** | `%s` / `%(name)s` |
| Alembic | нативно (общий автор) | не поддерживается напрямую | поддерживается |
| Уместность для проекта | подходит: движок остаётся на Decimal/dataclass, SQLAlchemy — только доступ к данным | быстро, но платим ручным контролем транзакций и отсутствием миграций | середина: удобный API, синхронный |
| Риск через 3 года | низкий, самая распространённая | средний: релизов нет с ноября 2025 | низкий, поддерживается активно |

Отдельно про **`Decimal`**. У нас деньги считаются в `Decimal` и это неприкосновенно
(`src/payroll/engine.py`: «деньги не считаем во float»). Все три драйвера умеют `numeric → Decimal`,
но по-разному: psycopg3 и SQLAlchemy отдают `Decimal` из `numeric` по умолчанию; **asyncpg тоже
отдаёт `decimal.Decimal` для `numeric`**, но у него есть привычка к явной регистрации кодеков
для нестандартных типов, а у нас в схеме `accounting_layer[]` — массив пользовательского enum
(`db/migrations/0001_core.sql`) и `jsonb`. Это не блокер, но ещё немного ручной работы, которую
SQLAlchemy/psycopg3 делают сами.

Ещё фактор: движок **синхронный** и таким и останется — это чистый CPU-расчёт по 30 сотрудникам,
async ему ничего не даёт. Если весь стек делать async ради async, расчёт всё равно придётся
уносить в `run_in_executor`/воркер, иначе он заблокирует event loop. То есть async-выгода тут
близка к нулю, а цена — вся асинхронная зараза в тестах и импортёрах.

### 3.5. Рекомендация по разделу 3

**SQLAlchemy 2.0 Core (+ ORM по вкусу для справочников), синхронно, драйвер psycopg3.**

- `reset_on_return="rollback"` из коробки откатывает `SET LOCAL` — один слой защиты бесплатно
  ([SQLAlchemy pooling](https://docs.sqlalchemy.org/en/20/core/pooling.html)).
- Транзакция по умолчанию подразумевается, а значит основная грабля («`SET LOCAL` в автокоммите»)
  не срабатывает по умолчанию, а требует специально её обойти.
- Alembic — тот же проект, интеграция без швов (см. раздел 4).
- Сырой SQL никуда не девается: `session.execute(text(...))` — законный первый класс. Схема уже
  написана руками, ORM-модели можно завести только там, где они реально экономят (справочники,
  CRUD-формы), а отчётные выборки оставить сырым SQL.
- Синхронно — потому что нагрузка «десяток пользователей одного партнёра», а расчёт CPU-bound.

`asyncpg` не брать: девять месяцев без релиза плюс автокоммит по умолчанию — ровно та комбинация,
где утечка тенанта возникает от невнимательности, а не от злого умысла.

### 1.3. Разбор по нашим критериям

**Сырой SQL и RLS.** Все три умеют сырой SQL. Разница — в том, где ставится `SET LOCAL`.
У Django это выходит почти бесплатно: `ATOMIC_REQUESTS = True` («Before calling a view function,
Django starts a transaction. If the response is produced without problems, Django commits the
transaction. If the view produces an exception, Django rolls back the transaction» —
[transactions](https://docs.djangoproject.com/en/6.1/topics/db/transactions/)), а внутри этой
транзакции middleware выставляет `set_config('app.tenant_id', ..., true)`. Один middleware,
десять строк, и все виды — включая админку — под RLS автоматически.

Оборотная сторона и **грабля**: без `ATOMIC_REQUESTS` Django работает в автокоммите («Django's
default behavior is to run in autocommit mode», там же), и тот же middleware молча ничего не
установит (см. раздел 3.1). То есть `ATOMIC_REQUESTS = True` здесь не «оптимизация», а условие
корректности — и это надо записать в тест, а не в комментарий.

**Схема, написанная руками, против Django-миграций.** Django хочет владеть схемой. Три
существующие миграции написаны SQL'ем под Supabase. Есть три пути:
(а) переписать схему как Django-модели и сгенерировать миграции, а RLS-политики положить в
`RunSQL` — «Allows running of arbitrary SQL on the database — useful for more advanced features
of database backends that Django doesn't support directly»
([migration operations](https://docs.djangoproject.com/en/6.1/ref/migration-operations/));
(б) оставить SQL как есть, а модели объявить `managed = False` — тогда админка и ORM работают,
а схему двигают руками;
(в) гибрид: Django владеет своими таблицами (auth, sessions), наши — `managed = False`.

Путь (а) даёт полную мощность Django (админка + формы + миграции), ценой однократного
переписывания 340 строк SQL в модели. Учитывая, что миграции **ни разу не применялись** и
править историю не надо — это дешевле, чем кажется, и делается один раз. Подробнее в разделе 4.

**i18n.** «Django has full support for translation of text, formatting of dates, times and
numbers, and time zones» ([i18n](https://docs.djangoproject.com/en/6.1/topics/i18n/)). Для
ru/en/sr это готовый gettext-конвейер: `{% trans %}`, `makemessages`, `LocaleMiddleware`,
переключение языка на пользователя. У FastAPI и Litestar в документации раздела про i18n нет
вовсе — собирать придётся руками на Babel (2.18.0), включая middleware выбора языка, извлечение
строк и локализованное форматирование чисел. Для сербского это не абстракция: разделитель
дробной части — запятая, и в зарплатной ведомости это видно сразу.

**Админка для справочников.** Прямая цитата из документации:
«It reads metadata from your models to provide a quick, model-centric interface where trusted
users can manage content on your site». И честное предупреждение оттуда же: «The admin's
recommended use is limited to an organization's internal management tool. It's not intended for
building your entire front end around»
([admin](https://docs.djangoproject.com/en/6.1/ref/contrib/admin/)).

Это ровно наш случай, если правильно провести границу: **справочники — в админке**
(сотрудники, группы, точки, юрлица, календарь, типы часов, контрагенты — их CRUD никому не
интересен, но написать надо), **рабочий процесс — свои виды** (ввод табеля, расчёт, ведомость,
утверждение периода). Второе — «process-centric interface», про которое админка сама говорит
«probably time to write your own views». Такое разделение экономит недели и при этом не
превращает продукт в админку, что было бы ошибкой.

**Зрелость и трёхлетний горизонт.** Здесь Django выигрывает не вкусом, а календарём.
Django публикует LTS-релизы с гарантированным сроком: 5.2 LTS — до апреля 2028, следующий
6.2 LTS выйдет в апреле 2027 и поддерживается до апреля 2030
([download](https://www.djangoproject.com/download/)). У FastAPI и Litestar LTS нет вообще,
FastAPI спустя годы **всё ещё на 0.x** (0.141.1) — то есть формально не обещает стабильности
мажорной версии. Для продукта, к которому раз в квартал заходит коллега, предсказуемый
календарь обновлений — это не бюрократия, а прямая экономия.

**Что теряем, выбирая Django.** Автогенерируемый OpenAPI — у FastAPI он лучший в экосистеме и
это его главный аргумент. У Django это решается `django-ninja` (FastAPI-подобный слой поверх
Django, тот же pydantic и та же генерация схемы) или DRF. Учитывая, что API нам нужен
«немного» и в основном для будущего Telegram, потеря не критична.
Ещё теряем нативный async — но, как разобрано в 3.4, расчёт CPU-bound и async ему не помогает.

### 1.4. Рекомендация по разделу 1

**Django.** Не потому что «модно» (модно как раз обратное), а потому что три из шести наших
требований — админка справочников, i18n, роли/сессии — у него закрыты из коробки, а у
конкурентов это работа, которую придётся написать и потом три года чинить самому. RLS от этого
не страдает: Django нормально живёт с сырым SQL и `RunSQL`, а `ATOMIC_REQUESTS` даёт транзакцию
на запрос почти даром.

**Версию брать 6.1 сейчас** (Python 3.13 поддержан) с планом перехода на **6.2 LTS в апреле 2027**.
Альтернатива «сразу 5.2 LTS» рабочая (поддержка до 04.2028, Python 3.10–3.14), но 5.2 вышла
в апреле 2025 и через год всё равно потребует прыжка через 6.0/6.1 — прыгать дешевле сейчас,
пока кода мало.

HTTP API поверх — **django-ninja**, чтобы не терять pydantic и OpenAPI и чтобы Telegram-модуль
в будущем цеплялся к нормально описанному контракту. *(Версию django-ninja проверить перед
фиксацией — в этой сессии не запрашивалась.)*

## 2. Как отдаём интерфейс: шаблоны + HTMX vs SPA vs гибрид

### 2.1. Что диктует продукт

Из `docs/forge/intake.md` (B, D): интерфейс плотный табличный, приоритет десктопа, публичной
части нет, «воздушный лендинг здесь вреден», команда — один разработчик. Из C: ключевой экран —
**ввод табеля с редактированием ячеек** (30 сотрудников × несколько типов часов).

Это два разных класса экранов, и их не надо решать одним инструментом:

- **95% экранов** — списки, формы, фильтры, ведомость, справочники. Классический server-rendered
  HTML. SPA здесь не даёт ничего, кроме сборки, роутера, стейт-менеджера и второго слоя
  валидации, который придётся держать в синхроне с серверным.
- **1 экран** — сетка ввода часов: табуляция между ячейками, вставка из Excel, пересчёт итогов
  по строке на лету. Вот здесь честно нужен клиентский виджет.

### 2.2. Варианты

**Server-rendered + HTMX.** Django-шаблоны отдают HTML, HTMX точечно подменяет фрагменты.
Текущая стабильная линия — **htmx 2.x** (npm `htmx.org` 2.0.10, лицензия 0BSD; GitHub-релиз
v2.0.9 от 2026-04-20). Официальная документация подтверждает: «Version 1 of htmx is still
supported and supports IE11, but the latest version of htmx is 2.x» ([htmx docs](https://htmx.org/docs/)).
**Важно и не по памяти:** в GitHub-релизах htmx с мая 2026 идут пререлизы **4.0.0-beta**
(последний beta6 от 2026-07-23), при этом в документации версии 3/4 ещё не упоминаются.
То есть htmx готовит мажорный скачок — закладываться надо на 2.x, пин версии обязателен,
и не тащить 4.0-beta в продукт.

Для Django есть `django-htmx` 1.29.0 (2026-08-05) — активно поддерживаемый пакет-хелпер.

Плюсы: одна модель данных, одна валидация, ноль сборки фронтенда, весь код на Python.
Один разработчик держит это в голове целиком.
Минусы: сложную клиентскую интерактивность (наша сетка табеля) HTMX не закрывает — он про
обмен фрагментами HTML, а не про редактируемый грид.

**SPA (React/Vue).** Даёт нормальный грид и офлайн-валидацию, ценой: сборка, две кодовые базы,
два набора типов, отдельный деплой статики, дублирование правил валидации, и — главное для нас —
**потеря бесплатной админки и i18n Django**, ради которых мы его и выбрали. Для одного
разработчика с плотным CRUD это удвоение работы почти без выгоды: у нас нет ни офлайна, ни
реалтайма, ни мобильного приложения.

**Гибрид: server-rendered + островки.** HTML и формы — с сервера; там, где нужен настоящий
виджет, вешается изолированный JS-компонент без сборки всего SPA. Для нашего единственного
тяжёлого экрана это либо небольшая обвязка на Alpine.js (3.15.12, MIT), либо готовый грид:

| Грид | Версия | Лицензия |
|---|---|---|
| Tabulator | 6.5.2 | MIT |
| AG Grid Community | 36.1.0 | MIT |
| Handsontable | 18.0.0 | **проприетарная** (нужна платная лицензия для коммерческого использования) |

(версии — npm registry, 2026-08-06)

## 4. Миграции: Alembic vs sqitch vs голые SQL-файлы

### 4.1. Исходная позиция

`db/migrations/` содержит три файла (`0001_core.sql` 176 строк, `0002_payroll.sql` 165,
`0003_rls.sql` 84) — итого ~425 строк SQL, **ни разу нигде не применённых**
(`docs/forge/intake.md`, E3). Это принципиально: нет продакшена, нет истории применений,
нет чужих баз в разных состояниях. Значит переезд на другой инструмент миграций сейчас стоит
ровно одного переписывания и ноль рисков — а через полгода будет стоить кратно дороже.

Плюс `0003_rls.sql` в любом случае подлежит переписыванию: он написан под Supabase
(`auth.uid()`), а Supabase мы не используем (решение D006). Объём переделки — в разделе 5.

### 4.2. Варианты

**Голые SQL-файлы + свой раннер.** То, что есть сейчас. Плюсы: полный контроль над SQL,
нулевая магия, RLS-политики пишутся как есть. Минусы: раннера **нет** — его придётся написать
(таблица применённых версий, блокировка от параллельного применения, транзакционность,
идемпотентность, откат). Это тот самый «утилитный код, который лучше не писать руками»
из глобальных правил. Плюс отсутствие связи со схемой в коде: рассинхрон обнаруживается
рантайм-ошибкой.

**Alembic 1.19.0 (2026-08-04).** Родной инструмент SQLAlchemy («Alembic's install process will
ensure that SQLAlchemy is installed» — [Alembic front](https://alembic.sqlalchemy.org/en/latest/front.html)),
даёт версионированные ревизии с направленным графом, `upgrade`/`downgrade`, `op.execute()` для
произвольного SQL. Autogenerate — удобство, а не обязанность, и у него документированные
пределы: детектирует добавление/удаление таблиц и колонок, `nullable`, базовые изменения
индексов, уникальных и внешних ключей, именованных CHECK; **не** детектирует переименования
таблиц и колонок (выдаёт их как пару drop+add), анонимно именованные ограничения, часть
free-standing constraints, последовательности
([autogenerate](https://alembic.sqlalchemy.org/en/latest/autogenerate.html)).
Для нас это значит: **RLS-политики, enum-типы, функции — autogenerate не увидит вообще**,
их надо писать руками в `op.execute()`. Что нормально, но иллюзий про «само сгенерируется»
быть не должно.

**Sqitch.** Инструмент, специально сделанный под «просто SQL, без ORM»: change/verify/revert
тройками, зависимости между изменениями, не привязан ни к какому фреймворку
([sqitch.org](https://sqitch.org/docs/manual/sqitch/), [github](https://github.com/sqitchers/sqitch)).
Идеологически ближе всего к тому, что у нас уже написано. Ловушка одна, но тяжёлая:
**Sqitch написан на Perl**. Ставится либо из Docker-образа `sqitch/sqitch`, либо сборкой из
исходников через `Build.PL`/`installdeps` ([download](https://sqitch.org/download/)).
Это второй рантайм в проекте, второй образ в compose и второй набор навыков у того, кто через
два года будет чинить миграцию. Уникальная фича sqitch — `verify`-скрипты — у нас частично
покрывается тестами RLS (раздел 8).

**Django-миграции (если брать Django).** Встроены, живут в том же репозитории и той же
кодовой базе, `RunSQL`/`RunPython` покрывают произвольный SQL — включая создание функций,
типов и политик ([migration operations](https://docs.djangoproject.com/en/6.1/ref/migration-operations/)).
`state_operations` и `SeparateDatabaseAndState` позволяют смешивать: схему создаёт руками
написанный SQL, а Django-состояние синхронизируется. Отдельный плюс — миграции применяются той
же командой, что и всё остальное (`manage.py migrate`), без второго инструмента в compose.

### 4.3. Что дешевле для нас

| | Голый SQL + свой раннер | Alembic | Sqitch | Django-миграции |
|---|---|---|---|---|
| Что надо написать сейчас | раннер (с нуля) | конфиг + перенос 3 файлов в ревизии | конфиг + перенос + Docker-образ | модели + перенос RLS в `RunSQL` |
| Второй рантайм | нет | нет | **Perl** | нет |
| Связь со схемой в коде | нет | через SQLAlchemy-метаданные | нет | через модели |
| Произвольный SQL (RLS, enum, функции) | естественно | `op.execute()` | естественно | `RunSQL` |
| Кто чинит через 2 года | автор раннера | широко известен | узкая ниша | любой, кто знает Django |

### 4.4. Рекомендация по разделу 4

**Django-миграции — если принят Django (раздел 1). Alembic — если по какой-то причине Django
не берём.** Голый SQL со своим раннером и sqitch не брать.

Обоснование: главная задача миграций в проекте с одним разработчиком — чтобы через год
кто-то мог применить их не думая, одной командой, без второго рантайма. Django-миграции живут
внутри уже выбранного фреймворка и не добавляют ни зависимости, ни образа. Sqitch концептуально
лучше подходит к «мы пишем SQL руками», но платить за это Perl-рантаймом в compose на домашнем
сервере — плохая сделка. Свой раннер — это писать инфраструктурный код вместо продуктового,
прямо против правила «battle-tested libraries over hand-rolled solutions».

**Практический план переезда** (дёшев именно сейчас, потому что миграции не применены):

1. Выразить `0001_core.sql` и `0002_payroll.sql` как Django-модели; enum'ы (`accounting_layer`,
   `payout_channel`, `allocation_method`, `period_status`) — либо нативные PG-типы через
   `RunSQL`, либо `TextChoices` + CHECK. Нативные типы уже написаны и работают — сохранить
   их `RunSQL`'ом, а моделям дать `db_type` через кастомное поле.
2. `0003_rls.sql` переписать под свою авторизацию (см. раздел 5) и положить целиком в
   `RunSQL` с честным `reverse_sql` (`drop policy …`).
3. Старые `.sql` не удалять сразу — оставить в `db/migrations/legacy/` как источник истины
   на время переноса, удалить, когда тесты RLS зелёные. Дока (`CLAUDE.md`, «Структура»)
   правится тем же изменением: путь `db/migrations/` меняет смысл.

## 5. Авторизация

### 5.1. Найденная по ходу ошибка в `db/migrations/0003_rls.sql` — читать до всего остального

> **Это не стилистическое замечание, а дефект безопасности в уже написанном коде.**
> Репозитория на GitHub ещё нет (`git remote -v` пуст, `docs/forge/intake.md` E1), поэтому issue
> завести некуда — **завести первым же issue сразу после создания репозитория.**

В файле две политики на одну таблицу:

```sql
create policy tenant_isolation on pay_components for all using (tenant_id in (...));
create policy layer_visibility  on pay_components for select using (layer = any (auth_visible_layers(tenant_id)));
```

Обе созданы **permissive** (это значение по умолчанию), а permissive-политики комбинируются
через **OR**, не AND. PostgreSQL 17,
[Row Security Policies](https://www.postgresql.org/docs/17/ddl-rowsecurity.html):

> «When multiple policies apply to a given query, they are combined using either OR (for
> permissive policies, which are the default) or using AND (for restrictive policies).»

и [CREATE POLICY](https://www.postgresql.org/docs/17/sql-createpolicy.html):

> «All permissive policies which are applicable to a given query will be combined together using
> the Boolean “OR” operator. By creating permissive policies, administrators can **add** to the
> set of records which can be accessed.»
> «All restrictive policies … will be combined together using the Boolean “AND” operator.
> By creating restrictive policies, administrators can **reduce** the set of records…»

**Следствие:** ограничение по слою учёта на `SELECT` — **no-op**. Любая строка, прошедшая
`tenant_isolation`, видна независимо от `layer`. То есть заявленное в `CLAUDE.md` и
`discovery.md` требование «бухгалтер не видит чёрную кассу» сейчас в схеме **не выполняется**,
хотя выглядит написанным.

Утечки между тенантами тут нет (проверено логикой: `auth_visible_layers(tenant_id)` для чужого
тенанта вернёт `'{}'`, и `layer = any('{}')` ложно), но требование по слоям не работает.

**Починка:** обе «сужающие» политики объявить `as restrictive`:

```sql
create policy layer_visibility on pay_components
    as restrictive for select
    using (layer = any (current_setting('app.visible_layers', true)::accounting_layer[]));
```

И помнить оговорку из тех же доков: «Note that there needs to be at least one permissive policy
to grant access to records before restrictive policies can be usefully used… If only restrictive
policies exist, then no records will be accessible». То есть `tenant_isolation` остаётся
permissive, а всё, что сужает, — restrictive.

### 5.2. Объём переписывания `0003_rls.sql` под свою авторизацию

Файл — 84 строки. Меняется:

| Что | Сейчас | Станет | Объём |
|---|---|---|---|
| `auth_tenant_ids()` | `select tenant_id from memberships where user_id = auth.uid()` | функция не нужна вовсе — `tenant_id` кладём в `app.tenant_id` прямо из приложения | −8 строк |
| `auth_visible_layers()` | джойн `memberships`+`roles` по `auth.uid()` | не нужна — слои кладём в `app.visible_layers` | −15 строк |
| `tenant_isolation` (цикл по 16 таблицам) | `tenant_id in (select auth_tenant_ids())` | `tenant_id = current_setting('app.tenant_id', true)::uuid` | правка 2 строк внутри цикла |
| `layer_visibility` ×2 | permissive (баг, см. 5.1) | `as restrictive` + чтение GUC | правка 6 строк |
| `read_all` ×3 | `auth.uid() is not null` | `current_setting('app.user_id', true) is not null` | правка 3 строк |
| `own_tenants` | `id in (select auth_tenant_ids())` | `id = current_setting('app.tenant_id', true)::uuid` | правка 1 строки |
| — | нет | **добавить** `force row level security` в цикл | +1 строка |
| — | нет | **добавить** роли `app_owner` / `app_user` и `grant` | новая миграция, ~15 строк |

**Итого: не переписывание, а правка примерно трети файла плюс маленькая новая миграция.**
Это работа на несколько часов, а не на дни. Причём результат получается **проще и быстрее**
исходника: исчезают две `security definer`-функции, которые дергали `memberships` на каждой
проверке строки — вместо них чтение GUC, которое Postgres умеет кэшировать в плане.

Дополнительно: `memberships.user_id uuid — auth.users` в `0001_core.sql` (комментарий прямо
ссылается на Supabase) превращается в FK на нашу таблицу пользователей.

**Django auth даёт из коробки ровно то, что нам нужно:** «Django comes with a built-in
permissions system. It provides a way to assign permissions to specific users and groups of
users», плюс `Group` — «A user in a group automatically has the permissions granted to that
group» ([auth docs](https://docs.djangoproject.com/en/6.1/topics/auth/default/)). Плюс сессии,
`LoginView`/`LogoutView`, смена и сброс пароля, хеширование паролей, интеграция с админкой.

**FastAPI-Users исключается по факту, а не по вкусу.** Прямая цитата из README проекта:

> «**This project is now in maintenance mode.** While we'll continue to provide security updates
> and dependency maintenance, no new features will be added. … We're currently working on a new
> Python authentication toolkit that will ultimately supersede FastAPI Users.»

Строить трёхлетний продукт на библиотеке, которую авторы сами объявили тупиковой и обещают
заменить чем-то другим, — ровно то, чего просили избежать. Плюс ролей и прав она не даёт вообще.

**Отдельный IdP (authentik / Keycloak) — избыточен и дорог по ресурсам.** Их смысл — единый
вход в много приложений, федерация, SSO с корпоративным каталогом. У нас **одно** приложение,
десяток пользователей и домашний ноутбук в роли сервера, который к тому же работает как UPS
(`CLAUDE.md`, MUSPELHEIM). Заявленные требования authentik — 2 ядра и 2 ГБ RAM только под IdP,
плюс собственные Postgres и Redis; Keycloak — минимум 750 МБ, «2 GB minimum for production-ready»
плюс JVM и своя БД. Это больше, чем весь наш продукт.

Главное же: **IdP решает аутентификацию, а не нашу авторизацию.** Наши права двумерные —
набор точек × набор видимых слоёв учёта (`intake.md`, C), и они всё равно живут в нашей БД,
потому что от них зависят RLS-политики. То есть IdP не убирает работу, а добавляет к ней
интеграцию OIDC и вторую систему, где заводят пользователей.

**Authelia** — самый лёгкий из троих, но это forward-auth портал перед reverse proxy: он
скажет «этот человек — Пётр», и на этом всё. Ролей приложения и слоёв учёта он не знает.

### 5.4. Рекомендация по разделу 5

**Django auth: сессии + `Group`/`Permission` + своя модель `Membership` (tenant × user × role
× units × visible_layers).** Никакого внешнего IdP.

Схема связи с RLS:

1. Логин — обычный Django-сессионный (cookie, `HttpOnly`, `Secure`, `SameSite=Lax`).
2. Пользователь выбирает активного тенанта (у большинства он один) — кладём в сессию.
3. Middleware внутри `ATOMIC_REQUESTS`-транзакции проверяет `Membership` и делает
   `set_config('app.tenant_id', …, true)`, `app.user_id`, `app.visible_layers`.
4. RLS в БД — последний рубеж: даже если во вьюхе забыли фильтр, база не отдаст чужое.
5. Точки (`unit_ids`) — фильтр уровня приложения или отдельная restrictive-политика;
   решается при проектировании, но по тому же принципу.

Пароли: включить `argon2` (`argon2-cffi` 25.1.0) как основной хешер — Django поддерживает
это штатно, а PBKDF2 по умолчанию слабее. **Проверить перед фиксацией:** точное имя и порядок
`PASSWORD_HASHERS` в Django 6.1 — в этой сессии не сверялось.

Если позже понадобится вход через корпоративный аккаунт Dodo — добавляется `django-allauth`
(65.19.0, релиз 2026-08-06, живой) поверх той же модели, без переезда на IdP.

## 6. Фоновые задачи

### 6.1. Что именно мы гоняем в фоне

Из `intake.md` (C): расчёт периода на 30+ сотрудников, импорт xlsx, генерация выгрузок.
Характер нагрузки честно оценить важнее, чем выбрать инструмент:

- **Расчёт периода:** 30 сотрудников × несколько компонентов, чистый Python на `Decimal`.
  Это **секунды, если не доли секунды**. В фон он выносится не ради скорости, а ради того,
  чтобы HTTP-запрос не висел и чтобы был понятный статус «считается / посчитано / упало».
- **Импорт xlsx:** openpyxl на файле в 8 листов — тоже секунды.
- **Выгрузки:** аналогично.

То есть **очередь нужна для наблюдаемости и повторяемости, а не для пропускной способности.**
Речь про единицы задач в день, а не тысячи в секунду. Это радикально меняет ответ: платить
брокером за throughput, которого не будет, — бессмысленно.

или RabbitMQ, есть интеграция с Django и периодические задачи.

### 6.3. Отдельно про `pg_cron` — важное ограничение площадки

**`pg_cron` не входит в наш образ.** Официальный Dockerfile `pgvector/pgvector`
([pgvector/Dockerfile](https://github.com/pgvector/pgvector/blob/master/Dockerfile)) собирается так:

```dockerfile
FROM postgres:$PG_MAJOR-$DEBIAN_CODENAME
ADD https://github.com/pgvector/pgvector.git#v0.8.6 /tmp/pgvector
```

То есть это официальный `postgres:17-bookworm` **плюс только pgvector 0.8.6**. Никакого pg_cron.
Чтобы его получить, придётся собирать свой образ, а затем менять `shared_preload_libraries`
и перезапускать сервер. На домашней машине, которую нельзя выключать (`CLAUDE.md`, MUSPELHEIM,
холодный старт требует физического входа), лишний повод перезапускать Postgres — плохая идея.

И главное: **pg_cron выполняет SQL, а не Python.** Наш движок — питоновский `Decimal`-код,
запустить его из pg_cron невозможно в принципе. pg_cron годится максимум для служебного
(vacuum, чистка, обновление демо-данных через SQL), но не для расчёта периода.

### 6.4. Рекомендация по разделу 6

**Очередь на самом Postgres. Конкретно: `django-q2`, если берём Django (пункт 1),
иначе `Procrastinate`.**

Обоснование:

- Лишний брокер на одном сервере — это ещё один контейнер, который надо мониторить, бэкапить
  (или сознательно не бэкапить и потерять задачи), обновлять и чинить, когда Docker поднялся,
  а Redis нет. Ради единиц задач в день это чистый минус. Celery/Dramatiq/arq не брать
  **по этой причине, а не по качеству** — все три хорошие.
- Postgres у нас уже есть, уже бэкапится задачей «PG Docker Backup» на сервере
  (`CLAUDE.md`, MUSPELHEIM), и задачи в нём получают транзакционность бесплатно: задача
  ставится в очередь **в той же транзакции**, что и запись «период отправлен на расчёт».
  С Redis это классический источник рассинхрона (запись прошла, задача потерялась, или наоборот).
- `django-q2` живёт внутри Django, использует ORM как брокер и не добавляет ни одной внешней
  зависимости. `Procrastinate` архитектурно чище (LISTEN/NOTIFY, блокировки, приоритеты,
  отмена) и не привязан к Django, но добавляет ещё одну библиотеку в стек.
- **Что проверить перед фиксацией** (в этой сессии не проверено фактически): как выбранная
  очередь ведёт себя с RLS. Воркер — не HTTP-запрос, `app.tenant_id` ему никто не выставит.
  Значит воркер должен либо ходить ролью, освобождённой от RLS (`admin_session` из 3.3),
  либо — правильнее — получать `tenant_id` **аргументом задачи** и сам открывать транзакцию
  с `set_config`. Второй вариант обязателен: иначе фоновые задачи станут дырой в изоляции
  ровно там, где её никто не проверяет.

`pg_cron` — не брать вовсе: не в образе, требует пересборки и рестарта, и не умеет Python.
Периодические задачи (самовосстановление демо-стенда из `intake.md` C) вешать на планировщик
самой очереди.

## 8. Тестирование веб-слоя и БД, и особенно RLS

### 8.1. Почему обычный подход здесь даёт ложную зелень

Три способа написать тест RLS, который **проходит, ничего не проверяя**:

**(1) Тест ходит в базу суперпользователем/владельцем.** Разобрано в 3.1: «Superusers and roles
with the `BYPASSRLS` attribute always bypass the row security system… Table owners normally
bypass row security as well»
([PG17 RLS](https://www.postgresql.org/docs/17/ddl-rowsecurity.html)). В Docker-образе Postgres
по умолчанию всё делается ролью `postgres`. Если тест подключился ею — политик как будто нет,
а «тенант видит свои данные» проходит.
→ **Тесты RLS обязаны подключаться ролью `app_user`** (не владелец, не суперпользователь,
без `BYPASSRLS`), и это надо утверждать отдельным тестом, а не верить конфигу.

**(2) Тест на SQLite или на моках.** RLS — фича Postgres, на SQLite её нет вообще. Любой тест
изоляции, гоняющийся не на настоящем Postgres, проверяет фильтр в Python, а не политику в БД.
→ Только реальный Postgres. Инструмент — `testcontainers` 4.15.0 (2026-07-24) либо контейнер
из того же compose, поднятый в CI.

**(3) Каждый тест открывает новое соединение.** Тогда утечка контекста между запросами
(раздел 3.2) невоспроизводима по построению: у каждого теста своя чистая сессия.
→ Нужен отдельный тест, который **намеренно** переиспользует одно соединение.

### 8.2. Минимальный обязательный набор тестов RLS

Записан как требования, а не как готовый код — конкретика зависит от выбора в разделе 1.

1. **Позитивный.** Тенант A под своей ролью видит свои строки.
2. **Негативный, главный.** Транзакция с `app.tenant_id = A` не видит **ни одной** строки
   тенанта B — по каждой из 16 таблиц из `0003_rls.sql`, не выборочно.
3. **Запись.** `INSERT` строки с чужим `tenant_id` падает на `WITH CHECK`, а не тихо проходит.
   (`with check` в текущей политике есть — это правильно.)
4. **Утечка через пул — тот самый тест.** На **одном** соединении из пула подряд:
   транзакция 1 с тенантом A читает строки; транзакция 2 **без** установки GUC —
   должна увидеть ноль строк. Если увидела строки A — контекст протёк.
5. **GUC не переживает транзакцию.** После коммита `current_setting('app.tenant_id', true)`
   пуст. Гарантия документирована («The effects of `SET LOCAL` last only till the end of the
   current transaction» — [SET](https://www.postgresql.org/docs/17/sql-set.html)), но проверять
   надо не гарантию Postgres, а то, что наш код использует `SET LOCAL`, а не `SET`.
6. **Слои учёта.** Роль с `visible_layers = {white}` не видит строк `black` в `pay_components`.
   **Этот тест сейчас упал бы** — см. дефект в 5.1. Он и есть регрессионный тест на починку.
7. **Инвариант схемы — детектор дрейфа, самый ценный из всех.** Не про данные, а про схему:
   пройтись по каталогу и убедиться, что **каждая** таблица с колонкой `tenant_id` имеет
   `relrowsecurity` и `relforcerowsecurity` = true и хотя бы одну политику. Колонки
   документированы в [pg_class](https://www.postgresql.org/docs/17/catalog-pg-class.html),
   политики видны в [pg_policies](https://www.postgresql.org/docs/17/view-pg-policies.html)
   (в том числе колонка `permissive` — ею же проверяется, что «сужающие» политики
   действительно restrictive, то есть дефект 5.1 не вернётся).

```sql
-- набросок теста 7: таблицы с tenant_id, у которых RLS не включён или не forced
select c.relname, c.relrowsecurity, c.relforcerowsecurity
  from pg_class c
  join pg_namespace n on n.oid = c.relnamespace
 where n.nspname = 'public' and c.relkind = 'r'
   and exists (select 1 from pg_attribute a
                where a.attrelid = c.oid and a.attname = 'tenant_id' and a.attnum > 0)
   and not (c.relrowsecurity and c.relforcerowsecurity);
-- ожидание: ноль строк
```

Именно этот тест ловит будущую ошибку «завели новую таблицу и забыли RLS» — то есть ту,
которая иначе обнаружится на проде. Он же — прямая реализация правила про детектор дрейфа
из глобальной документационной дисциплины, только применённая к схеме.

### 8.3. Ловушка транзакционных тестов

Django `TestCase` и типичные фикстуры pytest оборачивают каждый тест в транзакцию с откатом.
С `SET LOCAL` это взаимодействует: PostgreSQL документирует, что «The effects of `SET` or
`SET LOCAL` are also canceled by rolling back to a savepoint that is earlier than the command»
([SET](https://www.postgresql.org/docs/17/sql-set.html)). То есть вложенные savepoint'ы,
которые Django создаёт для вложенных `atomic()`, сбрасывают наш GUC при откате внутреннего
блока. Само по себе это корректно, но означает: **тесты RLS нельзя писать на обычном
транзакционном `TestCase`** — нужен вариант с настоящими коммитами
(в Django это `TransactionTestCase` / `pytest.mark.django_db(transaction=True)`), иначе
тестируется не то, что работает в бою. `pytest-django` — 4.13.0 (2026-08-05).

### 8.4. Остальной веб-слой

- **HTTP-уровень:** тесты вьюх штатным тестовым клиентом фреймворка. Проверять не только
  «200 OK», но и **403 для чужого тенанта и чужой точки** — это тот же класс риска.
- **Расчёт:** `tests/test_serbia_june_2026.py` остаётся неприкосновенным (`intake.md`, C:
  «единственное, что нельзя ломать»). Плюс новый end-to-end: данные вводятся **через
  интерфейс/API**, а не конструированием dataclass'ов, и результат совпадает с эталоном —
  это и есть заявленный критерий успеха MVP.
- **Миграции:** тест «поднять пустую базу, применить всё, откатить всё, применить снова».
  Ловит невыполнимый `reverse_sql` в `RunSQL` (раздел 4) — то, о чём вспоминают только когда
  надо срочно откатиться.
- **Демо-стенд:** смоук, что демо-сид разворачивается и вход в демо работает. По правилу №6
  глобальных инструкций демо — часть Definition of Done, а не «потом».
- **Чего не делать:** гнаться за 80% покрытия веб-слоя. Ценность здесь неравномерна: тесты
  изоляции и расчёта стоят кратно дороже тестов рендеринга шаблонов.

## Развилки

> Формат: **суть выбора** / варианты / **рекомендация с обоснованием**. Рекомендация есть у каждой.

### Р1. Веб-фреймворк

**Суть.** На чём строить веб и API: на минималистичном ASGI-фреймворке, где всё пишется руками,
или на «батарейках включены», где половина нашего скоупа уже написана.

**Варианты.** FastAPI 0.141.1 / Django 6.1 / Litestar 2.24.0.

**Рекомендация: Django 6.1, с планом перехода на 6.2 LTS в апреле 2027.**
Три из шести наших требований — админка справочников, i18n ru/en/sr, роли и сессии — у Django
из коробки, а у FastAPI и Litestar их нет вовсе: ни встроенной i18n, ни админки, ни модели
пользователя. Для одного разработчика это разница между «настроить» и «написать и потом три
года чинить». RLS при этом не страдает: `ATOMIC_REQUESTS = True` даёт транзакцию на запрос,
внутри которой middleware выставляет `set_config(..., true)`, а `RunSQL` в миграциях позволяет
держать политики как обычный SQL. Цена — теряем лучший в экосистеме автогенерируемый OpenAPI;
компенсируется `django-ninja`, а API нам нужен «немного». Дополнительный аргумент, не связанный
с фичами: у Django есть публичный LTS-календарь с гарантией три года, у FastAPI после стольких
лет всё ещё версия 0.x, у Litestar LTS нет.

### Р2. Способ отдачи интерфейса

**Суть.** Server-rendered HTML или клиентское приложение — при том что 95% экранов это формы
и списки, а один экран (ввод табеля) требует настоящего редактируемого грида.

**Варианты.** Шаблоны + HTMX / SPA (React, Vue) / гибрид «шаблоны + островки».

**Рекомендация: гибрид. Django-шаблоны + htmx 2.x как база, один изолированный островок
на экране табеля.**
SPA стоит удвоения кодовой базы (сборка, роутер, вторая валидация, отдельный деплой) и при этом
обесценивает главную причину выбора Django — бесплатные админку, формы и i18n. Чистый HTMX
не закрывает единственный по-настоящему интерактивный экран. Гибрид платит ровно за то, что
нужно: 95% интерфейса пишется как обычные шаблоны, а сетка ввода часов делается отдельным
компонентом, который можно заменить, не трогая остальное. Начинать с самого дешёвого варианта
островка — HTML-инпуты + Alpine.js (3.15.12, MIT); если упрёмся — Tabulator 6.5.2 (MIT).
Handsontable не брать: лицензия платная, бюджет нулевой. Сборку фронтенда не заводить,
версии пинить и класть в `static/`, а не тянуть с CDN — htmx 4.0 уже в бете, автообновление
однажды сломает продукт молча.

### Р3. Доступ к БД и способ прокидывания tenant_id

**Суть.** Чем ходить в Postgres и как гарантировать, что `tenant_id` не протечёт между
запросами при переиспользовании соединения из пула.

**Варианты.** SQLAlchemy 2.0 (Core/ORM) / asyncpg + сырой SQL / psycopg3 + сырой SQL.

**Рекомендация: psycopg3 как драйвер; SQLAlchemy 2.0 при самостоятельном стеке, Django ORM
при выборе Django (Р1) — но в обоих случаях синхронно и с сырым SQL там, где он уместен.
Контекст тенанта — только `set_config('app.tenant_id', $1, true)` внутри явной транзакции.**

Обоснование — механика, а не вкус:
- `SET LOCAL` физически не может пережить транзакцию («The effects of `SET LOCAL` last only till
  the end of the current transaction, whether committed or not» —
  [PG17 SET](https://www.postgresql.org/docs/17/sql-set.html)), поэтому утечка через пул
  невозможна **по построению**, а не по дисциплине.
- Обратная сторона: вне транзакции он молча не срабатывает («emits a warning and otherwise has
  no effect», там же). Значит нужен фреймворк, где транзакция открыта по умолчанию.
  У Django это `ATOMIC_REQUESTS`, у SQLAlchemy — «begin once». У asyncpg наоборот, автокоммит —
  и это делает его самым опасным вариантом здесь; плюс у него нет релизов с ноября 2025.
- Параметризация только через `set_config(name, value, true)` — `SET LOCAL` не принимает
  bind-параметры, а конкатенация tenant_id в SQL это инъекция.
- Никакой пул не чистит session-state сам: у psycopg3 `reset` по умолчанию `None`
  ([pool API](https://www.psycopg.org/psycopg3/docs/api/pool.html)), у SQLAlchemy
  `reset_on_return="rollback"` — откатывает `SET LOCAL`, но не `SET`
  ([pooling](https://docs.sqlalchemy.org/en/20/core/pooling.html)). Вывод один: `SET` не
  использовать никогда, только `SET LOCAL` / `is_local = true`.
- Синхронно, потому что расчёт CPU-bound и от async ничего не выигрывает, а тесты и импортёры
  от него дорожают.

**Обязательное сопутствующее решение, без которого всё вышеперечисленное — декорация:**
приложение ходит **отдельной ролью** `app_user` (не владелец, не суперпользователь, без
`BYPASSRLS`), а на таблицах стоит **`FORCE ROW LEVEL SECURITY`**. Иначе RLS не применяется
вообще: «Superusers and roles with the `BYPASSRLS` attribute always bypass the row security
system… Table owners normally bypass row security as well»
([PG17 RLS](https://www.postgresql.org/docs/17/ddl-rowsecurity.html)). В Docker-образе Postgres
по умолчанию все ходят ролью `postgres` — то есть без этого решения политики будут написаны
и не работать, а тесты — проходить.

### Р4. Миграции

**Суть.** Продолжать вести схему голыми SQL-файлами (три уже написаны, ни один не применён)
или переехать на инструмент.

**Варианты.** Голый SQL + свой раннер / Alembic 1.19.0 / Sqitch / встроенные Django-миграции.

**Рекомендация: Django-миграции (при Р1 = Django); Alembic — если Django не берём.
Переезжать сейчас, а не потом.**
Ключевой факт: миграции **нигде не применены** (`intake.md`, E3), истории применений нет,
`0003_rls.sql` в любом случае переписывается под свою авторизацию. Значит переезд стоит
одного переписывания и ноль риска — а через полгода будет стоить кратно дороже. Свой раннер
не писать: это инфраструктурный код (версии, блокировки, откаты) вместо продуктового, ровно
против правила «battle-tested libraries over hand-rolled solutions». Sqitch идеологически ближе
всего к «мы пишем SQL руками», но тянет **Perl-рантайм** вторым образом в compose на домашний
сервер — плохая сделка ради удобства формата. RLS-политики, enum-типы и функции в любом
инструменте пишутся руками: Alembic-autogenerate их не видит по документации
([autogenerate](https://alembic.sqlalchemy.org/en/latest/autogenerate.html)), Django — через
`RunSQL`, «Allows running of arbitrary SQL on the database»
([migration operations](https://docs.djangoproject.com/en/6.1/ref/migration-operations/)).
Никаких иллюзий про «сгенерируется само» быть не должно.

### Р5. Авторизация

**Суть.** Ставить отдельный сервер идентичности или обойтись своей аутентификацией внутри
приложения — при том что права у нас двумерные (точки × слои учёта) и всё равно должны
жить в нашей БД, потому что от них зависят RLS-политики.

**Варианты.** Django auth (сессии + Group/Permission) / FastAPI-Users / Authelia / authentik /
Keycloak.

**Рекомендация: Django auth — сессии, `Group`/`Permission`, своя модель `Membership`.
Внешний IdP не ставить.**
- FastAPI-Users отпадает по факту: авторы объявили проект в **maintenance mode** — «no new
  features will be added… We're currently working on a new Python authentication toolkit that
  will ultimately supersede FastAPI Users»
  ([README](https://github.com/fastapi-users/fastapi-users)). Плюс ролей и прав в нём нет вовсе.
- authentik и Keycloak — избыточны по ресурсам для домашнего сервера-ноутбука: authentik просит
  «at least 2 CPU cores and 2 GB of RAM» и приносит свои Postgres и Redis
  ([install](https://docs.goauthentik.io/install-config/install/docker-compose/)); Keycloak —
  «always set the memory limit… at least 750 MB… 2 GB minimum for production-ready» плюс JVM
  и своя БД ([containers](https://www.keycloak.org/server/containers)). Это больше, чем весь
  наш продукт.
- Главное: IdP решает **аутентификацию**, а нашу **авторизацию** — нет. Точки и слои учёта
  всё равно останутся у нас, потому что на них завязаны политики RLS. То есть IdP не убирает
  работу, а добавляет интеграцию и вторую систему, где заводят людей.
- Django auth даёт готовыми ровно недостающее: «Django comes with a built-in permissions system.
  It provides a way to assign permissions to specific users and groups of users»
  ([auth](https://docs.djangoproject.com/en/6.1/topics/auth/default/)), сессии, вход/выход,
  сброс пароля, интеграцию с админкой.

Переписывание `0003_rls.sql` при этом — **не переписывание, а правка примерно трети файла
плюс маленькая новая миграция на роли и гранты** (разбор построчно в 5.2). Результат выходит
проще исходника: две `security definer`-функции, дёргавшие `memberships` на каждой проверке
строки, заменяются чтением GUC.

### Р6. Фоновые задачи

**Суть.** Ставить ли брокер сообщений ради единиц задач в день на одном сервере.

**Варианты.** Celery 5.6.3 / Dramatiq 2.2.0 / arq 0.28.0 / Procrastinate 3.9.0 /
pgqueuer 1.3.2 / django-q2 1.10.0 / `pg_cron`.

**Рекомендация: очередь на самом Postgres — `django-q2` при Django, `Procrastinate` иначе.
Брокер не ставить. `pg_cron` не использовать.**
Наши задачи — расчёт на 30 сотрудников, импорт одного xlsx, выгрузка: это секунды, и в фон они
выносятся ради статуса и повторяемости, а не ради пропускной способности. Отдельный Redis/RabbitMQ
за такое — лишний контейнер, который надо мониторить, обновлять и чинить, плюс классический
рассинхрон «запись прошла, задача потерялась». Очередь в Postgres даёт транзакционность даром:
задача ставится **в той же транзакции**, что и запись «период отправлен на расчёт». Postgres уже
есть и уже бэкапится задачей на сервере (`CLAUDE.md`, MUSPELHEIM).
`pg_cron` отпадает по двум проверенным причинам: (1) его **нет в нашем образе** — официальный
Dockerfile `pgvector/pgvector` это `postgres:17-bookworm` плюс только pgvector 0.8.6
([Dockerfile](https://github.com/pgvector/pgvector/blob/master/Dockerfile)), а добавление
потребует своей сборки, правки `shared_preload_libraries` и рестарта сервера, который нельзя
холодно перезагружать; (2) он выполняет SQL, а наш движок — Python, запустить его оттуда
невозможно в принципе.
**Обязательное условие:** воркер не HTTP-запрос, `app.tenant_id` ему никто не выставит.
Задача обязана получать `tenant_id` **аргументом** и сама открывать транзакцию с `set_config` —
иначе фон станет дырой в изоляции ровно там, где её никто не смотрит.

### Р8. Как тестировать изоляцию тенантов

**Суть.** Как убедиться, что RLS действительно работает, а не выглядит работающим — при том
что здесь особенно легко написать тест, который проходит, ничего не проверяя.

**Варианты.** Тесты на уровне приложения (проверять фильтры в коде) / интеграционные тесты
на настоящем Postgres / инвариант схемы по системному каталогу.

**Рекомендация: все три уровня, но обязательны второй и третий; и три конкретных запрета.**

Обязательный минимум (разворот в 8.2):
- тесты ходят в **настоящий Postgres** (`testcontainers` 4.15.0 или контейнер из compose),
  никакого SQLite и никаких моков — RLS есть только в Postgres;
- тесты подключаются ролью **`app_user`**, и это утверждается отдельной проверкой. Иначе
  владелец/суперпользователь молча обходит все политики и тест зеленеет впустую;
- отдельный тест **на переиспользование соединения**: две транзакции подряд на одном
  соединении из пула, вторая без установки GUC — должна увидеть ноль строк. Без него утечка
  контекста невоспроизводима по построению;
- **инвариант схемы**: запрос по `pg_class` (`relrowsecurity`, `relforcerowsecurity`) и
  `pg_policies`, утверждающий, что каждая таблица с колонкой `tenant_id` имеет включённый
  и forced RLS и хотя бы одну политику, а «сужающие» политики действительно `restrictive`.
  Это единственный тест, который поймает будущее «завели таблицу и забыли RLS» — то есть
  ошибку, которая иначе всплывёт на проде;
- тесты RLS писать на **нетранзакционных** кейсах (`TransactionTestCase` /
  `pytest.mark.django_db(transaction=True)`): откат к savepoint отменяет `SET LOCAL`
  («The effects of `SET` or `SET LOCAL` are also canceled by rolling back to a savepoint that
  is earlier than the command» — [SET](https://www.postgresql.org/docs/17/sql-set.html)),
  и обычный транзакционный тест проверит не то, что работает в бою.

### Р9. Дефект в существующем `0003_rls.sql` — не развилка, а долг

**Суть.** Не выбор, а находка по ходу исследования, которую нельзя потерять.

Политики `layer_visibility` созданы **permissive** и потому комбинируются с `tenant_isolation`
через **OR**, а не AND ([CREATE POLICY](https://www.postgresql.org/docs/17/sql-createpolicy.html)).
Следствие: ограничение по слою учёта на `SELECT` — **no-op**, и заявленное требование
«бухгалтер не видит чёрную кассу» в схеме не выполняется, хотя выглядит написанным.
Утечки между тенантами нет, требование по слоям — не работает.

**Действие: как только появится репозиторий на GitHub (сейчас `git remote` пуст) — завести
issue первым.** Починка — `as restrictive` на все сужающие политики, регрессионный тест —
пункт 6 из 8.2. Отдельно проверить, что где-то остаётся хотя бы одна permissive-политика:
«If only restrictive policies exist, then no records will be accessible» (там же).
