## Находки

### Н1. Загрузка справочника статей молча подменяет дату «Действует с» из файла (T147)

**Что видно человеку.** Файл бухгалтера с колонкой «Действует с» и датой
`01.06.2026` загружается, продукт отвечает дословно:

> Загружено: 3 новых, 0 без изменений, 0 обновлено. Пропущены: HOZ — строка P&L
> не опознана: «—»; NEIZV — строка P&L не опознана: «Невнятная строка».

В справочнике у всех трёх статей стоит `2020-01-01` — значение поля формы
«Статьи действуют с», а не то, что написано в файле. Про подмену не сказано
**ни слова**: ни в сообщении, ни в списке пропущенных, ни где-либо ещё.

**Как воспроизвести.** Роль `admin` (только у неё `directory.manage`),
`/directory/expense-items/`. Книга xlsx: строка 1 — название документа, строка 2 —
заголовки `Шифра | Наименование | Строка P&L | Действует с`, дальше строки
`ARENDA | Аренда помещения | Себестоимость | 01.06.2026` и
`KOMM | Коммуналка | Себестоимость | 01.06.2026`. Загрузить с умолчанием
«Статьи действуют с» = 2020-01-01. В списке — `2020-01-01` у обеих.

**Чему противоречит.** Принципу проекта «никогда не проглатывать ошибку молча»
и духу самой задачи T147: соседние негодные строки (`HOZ`, `NEIZV`) продукт
называет поимённо и отказывается их заводить, а негодную дату — принимает и
заменяет своей. Две ошибки одного класса в одном файле обработаны
противоположно.

**Почему важно.** Дата действия статьи — не украшение: `cash.items_on`
отбирает статьи по дате, и `cash_views._item` отказывает расходу словами
«Статья на такую-то дату не действует». Статья, которую бухгалтер завела с июня,
после загрузки действует с 2020 года — то есть её предложат и примут для трат
за любой прошлый месяц, включая закрытые. Ошибка при этом не видна никогда:
человек не может отличить «дату взяли из файла» от «дату подставили за меня».
Формат `дд.мм.гггг` — не экзотика, а обычная запись даты и в Сербии, и в России;
`date.fromisoformat` его не принимает.

**Причина (по коду).** `src/web/expense_items_upload.py`, `_date_or`:

```python
def _date_or(raw: str, fallback: date) -> date:
    if not raw:
        return fallback
    try:
        return date.fromisoformat(raw[:10])
    except ValueError:
        return fallback
```

Пустая ячейка и **нечитаемая** ячейка обработаны одинаково, хотя это разные
события: в первом случае человек ничего не написал, во втором — написал, и его
не поняли.

**Чем проверил.** Настоящая загрузка файла в продукт запросом
`POST /directory/expense-items/upload/` под сессией `admin`; результат прочитан
на экране справочника и подтверждён в базе:
`select code, valid_from from expense_items;` → у всех трёх `2020-01-01`.

**Готово, когда** нечитаемая дата в файле либо называется человеку так же, как
непонятая строка P&L, либо разбирается наравне с ISO (`дд.мм.гггг`), а не
заменяется умолчанием формы молча.

### Н2. Подсказка поля после T148 не существует для незрячего и дёргает форму при табуляции

**Что видно человеку.** На форме справочника (проверено на «Новая касса»,
`/directory/tills/new/`) под полем «Код» подсказка «Короткий код кассы, например
NS1-main.» не показана. Она появляется, когда в поле встаёт курсор, — и вместе с
ней вся форма ниже, включая кнопку «Сохранить», сдвигается вниз на **22,6 px**.
Проходя форму клавишей Tab, человек видит, как кнопка прыгает на каждом поле.

**Как воспроизвести.** Роль `admin`, `/directory/tills/new/`. В консоли
браузера:

```js
const save = document.querySelector('form button');
const before = save.getBoundingClientRect().top;   // 460.63
document.getElementById('code').focus();
save.getBoundingClientRect().top;                  // 483.23 → сдвиг 22.59
```

Клавиатурой то же самое: Tab в поле «Код» — подсказка разворачивается, кнопка
уезжает.

**Разметка.** Подсказка — соседний `<span class="note">` внутри `<p class="field">`,
и правило `form.card .field > .note { display: none }` снимается только
`form.card .field:focus-within > .note { display: block }`. Связи с полем нет:
у `<input id="code">` **нет** `aria-describedby`.

**Чему противоречит.** Требованию задания к T148 «ничего не пропало и всё
достижимо, включая клавиатуру», и ECC-правилу web (`a11y`: подсказки поля
связываются с полем; анимировать/двигать layout-свойства нежелательно).

**Почему важно, и почему это не придирка.** `display: none` **выкидывает узел из
дерева доступности целиком**. Пока поле не в фокусе, подсказки для незрячего не
существует вовсе; когда поле в фокусе, она появляется в дереве **отдельным
текстом рядом**, а не описанием поля, — экранный диктор, объявляя поле, читает
«Код, поле ввода, обязательное» и подсказку не произносит никогда. До T148
подсказка была обычным текстом на странице и хотя бы читалась при обходе. То
есть выигрыш в лаконичности оплачен тем, что часть смысла формы стала
недоступна одной группе пользователей полностью, а не «менее заметна».

**Чем проверил.** Живой Chrome на 8094; снимок дерева доступности до и после
`focus()` (подсказка появляется как `StaticText`, у поля `aria-describedby = null`);
вычисленные стили (`display: none` → `block`); измерение сдвига
`getBoundingClientRect`.

**Догадка (не проверено):** то же должно быть на всех формах с `form.card`
(расход, сотрудник, точка, юрлицо, статья) — правило CSS одно на все. Проверена
одна форма.

**Готово, когда** подсказка либо связана с полем (`aria-describedby`) и остаётся
в дереве доступности всегда, либо показывается способом, не двигающим layout
(резерв места / наложение), — и это проверено диктором или снимком дерева, а не
глазами.

### Н3. Удаление расхода закрытого месяца ПОСЛЕ его правки — молчаливая пустышка: деньги остаются

**Что видно человеку.** Расход закрытого месяца сначала правят (продукт честно
предупреждает и кладёт в текущий месяц сторно + исправленную строку), потом
решают, что расхода не было вовсе, и жмут «Удалить расход». Продукт отвечает
**302 и возвратом в список — без единого слова**. Ничего не удалено: строка
«ПОДОПЫТНЫЙ правленый» на 700,00 остаётся живой в открытом августе, итог не
меняется ни на копейку. Человек уходит с экрана уверенный, что расхода в учёте
больше нет.

**Как воспроизвести** (проверено полностью, роль `director`):

1. Июнь 2026 закрыт (`/periods/<id>/approve/`).
2. Расход июньской датой существует: 500,00, NS1, касса NS1-main, НДС 20.
3. Правка карточки `/expenses/<id>/` — сумма 700,00. Продукт пишет
   «Месяц Июнь 2026 закрыт… Правка ляжет в Август 2026 двумя строками» и делает
   ровно это: июнь = 4 550,01 (не сдвинулся), в августе появляются −500,00
   «сторно» и +700,00 «исправление».
4. На той же карточке нажать «Удалить расход» → `POST /expenses/<id>/delete/`
   отвечает **302**.
5. Итоги: июнь 4 550,01, август 8 325,00 — **те же, что до удаления**. В списке
   `/api/expenses/?from=2026-06-01&to=2026-06-30` строка «ПОДОПЫТНЫЙ правленый
   700,00, исправление, Август 2026» на месте, состояние `active`.

**Причина (по коду).** `src/web/cash.py`: `remove_expense` для закрытого месяца
зовёт `storno_expense`, а тот кладёт факт с ключом
`entry_key_of(fact) + STORNO_SUFFIX`. Правка (`revise_expense`) уже создала
сторно **с этим же ключом**. Второй `upsert_fact` видит ту же строку и не делает
ничего — идемпотентность, задуманная как защита от двойного нажатия
(«повторная отправка той же правки не должна давать второе сторно»), здесь
срабатывает на другом действии: сторно есть, а `#fix`-строку на 700,00 никто не
снимает. `remove_expense` возвращает `Recorded`, представление проверяет только
факт возврата и уводит в список как после успеха.

**Чему противоречит.** Собственному обещанию `remove_expense` в docstring:
«оставить расход, которого не было, тоже нельзя» — а он именно остаётся. И
сквозному правилу проекта не сообщать об успехе там, где ничего не произошло
(тот же класс, что T132 и T136: продукт молчит или называет неверную причину).

**Почему важно.** Это единственный найденный за прогон случай, когда **деньги
остаются в P&L после того, как человек их удалил**, и узнать об этом неоткуда:
ни отказа, ни предупреждения, ни следа. Строка уедет в файл «Строки для P&L»
августа и попадёт в отчёт партнёру. Сценарий не выдуманный: «исправил сумму —
понял, что документа вообще не было — удалил» — обычный ход бухгалтера, и
именно закрытый месяц он правит чаще всего.

**Чем проверил.** Настоящие POST под сессией `director` на стенд 8094; суммы
сняты прямо из базы до и после каждого шага
(`select period, sum(amount) from facts where superseded_at is null and unit_id is not null group by 1`);
состояние строк прочитано в `/api/expenses/`.

**Готово, когда** удаление расхода в закрытом месяце после правки либо снимает
`#fix`-строку (то есть удаляет по-настоящему), либо отказывает словами
«эта строка уже исправлена — удалите её исправление в текущем месяце». Молчаливое
«ничего не произошло» после нажатия кнопки удаления недопустимо ни в каком виде.

### Н4. На карточке закрытого месяца пояснение к удалению описывает поведение ОТКРЫТОГО месяца

**Что видно человеку.** На карточке расхода закрытого месяца рядом с кнопкой
«Удалить расход» стоит дословно:

> Удалённый расход не стирается: строка останется в списке помеченной, а из
> итога выйдет.

В закрытом месяце не происходит ни того, ни другого: исходная строка **не
помечается** (в списке она остаётся `active`, без пометки), и из итога она **не
выходит** — июнь не двигается вовсе. Вместо этого в текущий месяц ложится сторно.

**Как воспроизвести.** Роль `director`, июнь закрыт, открыть карточку любого
июньского расхода. Наверху формы предупреждение про закрытый месяц есть, но оно
говорит только про **правку** («Правка ляжет в Август 2026 двумя строками»); про
удаление на всей странице не сказано ничего, кроме процитированной фразы, верной
для открытого месяца. Проверено: удаление чистой июньской строки «Коммуналка в
чёрную» 1 000,00 → июнь остался 4 550,01, в августе появилась −1 000,00.

**Почему важно.** Само поведение правильное (закрытый месяц не сдвинулся), а
объяснение — от другого случая. Человек, прочитавший это перед нажатием, будет
искать помеченную строку в июне и не найдёт, а изменение в августе не свяжет со
своим действием. Продукт в остальных местах эту разницу проговаривает тщательно
(тот же экран, поле «Дата расхода»: «Месяц Июнь 2026 закрыт: расход ляжет в
Август 2026»), то есть пропущено именно удаление.

**Чем проверил.** Текст снят с живой страницы `/expenses/<id>/` под `director`;
последствия удаления сверены с базой до и после.

**Готово, когда** пояснение к удалению на карточке закрытого месяца говорит то
же, что говорит про правку, — что ляжет сторно в текущий месяц и закрытый не
сдвинется.

### Н5. «Завести месяц» в производственном календаре молча затирает уже заведённый — единственный справочник, где занятый ключ не отказ

**Что видно человеку.** Кнопка «Завести месяц» на `/directory/calendar/`, форма
называется «Новый месяц календаря», кнопка — «Сохранить». Если ввести месяц,
который уже заведён, продукт отвечает **302 и возвращает в список без единого
слова**, а прежние числа заменены новыми. Ни «такой месяц уже есть», ни «вы
меняете существующий», ни показа старого значения.

**Как воспроизвести** (роль `admin` — только у неё `directory.manage`):

```
ДО:      2026-06-01 | norm_hours 176.00 | working_days 22
POST /directory/calendar/new/   month=2026-06  norm_hours=99  working_days=9
         → HTTP 302, редирект в список, сообщений нет
ПОСЛЕ:   2026-06-01 | norm_hours  99.00 | working_days  9
```

Страница месяца `/periods/<id>/` после этого показывает «Норма часов ·
производственный календарь RS · **99,00**».

**Чему противоречит.** Поведению **всех остальных** справочников продукта на
занятый ключ, проверенному в том же прогоне тем же способом: точка с кодом NS1,
касса NS1-main, группа kitchen, статья ARENDA — все четыре отвечают **400** и
дословно «Такая запись уже есть: «Код» не повторяется. Задайте другое значение.»
У календаря ключ ровно такой же — уникальное ограничение базы
`calendars_country_period_uniq (country_code, period)`. Это прямо тот приём,
который T136 и T142 доводили «до конца на всех справочниках»: календарь его не
получил, и обнаружить это по коду отказов нельзя — здесь отказа нет вовсе.

**Почему важно.** Три довода, по нарастающей:

1. Человек, нажавший «Завести месяц», уверен, что добавляет, а не заменяет.
   Прежних чисел он не видел и не увидит: старое значение нигде не показано и
   никуда не записано.
2. Календарь **общий на страну** — продукт сам об этом предупреждает на обеих
   формах: «правка подействует на всех партнёров этой страны». То есть
   промахнувшийся месяцем администратор одного партнёра молча переписывает норму
   часов всем остальным.
3. Норма часов и рабочие дни — вход расчёта зарплаты. Экран месяца после подмены
   показывает **новое** число как норму месяца, хотя ведомость посчитана по
   старому: числа на одном экране перестают сходиться между собой.

**Что при этом НЕ подтвердилось, и это важно для чинящего.** Подмена нормы
календаря **не сдвинула уже посчитанную ведомость**: пересчёт периода после
замены 176 → 100 дал те же 107 строк и те же 1 951 806,13. Причина —
`timesheets.norm_hours` держит норму по каждому сотруднику отдельно (в базе семь
разных значений: 176, 120, 96, 88, 64, 40, 20), а необлагаемый минимум движок
берёт из пресета страны (`reference_norm_hours: 176` в
`src/payroll/presets/serbia-2026.yaml`), а не из `calendars`. То есть беда здесь
в молчаливой подмене и в разъезде показанного с посчитанным, а **не** в сдвиге
денег. Не переписывайте это в «поменял календарь — поехала зарплата»: проверено,
не поехала.

**Чем проверил.** Настоящие POST под сессией `admin`; значения сняты из базы до
и после (`select period, norm_hours, working_days from calendars where
period='2026-06-01'`); отказы соседних справочников на занятый ключ проверены
тем же способом в том же прогоне; влияние на деньги проверено пересчётом периода
и сравнением `select count(*), sum(amount) from pay_components` до и после.

**Готово, когда** «Завести месяц» на уже заведённый месяц отказывает так же, как
остальные справочники (400 и человеческий текст), либо честно называет себя
правкой существующего и показывает, что именно заменяет.

**Мелочью рядом, в той же форме:** принимаются `norm_hours=0` при
`working_days=0` (месяц без единого рабочего дня) и `working_days=40` (в месяце
столько дней не бывает) — оба сохранились с 302 и без вопросов; отрицательная
норма при этом отказывается правильно («Норма часов»: отрицательное значение.).

### Н6. Табель приписывает базу взносов человеку, который её не ставил (T143)

**Что видно человеку.** Наводишь на ячейку «База взносов» — всплывает дословно:

> Вход расчёта наравне с часами: по ней считаются взносы и бруто · **поставил
> Бухгалтер, 16 августа 2026 г. 14:37**

Бухгалтер этой ячейки не касался. Он поменял соседнюю — «Больничный», — а база
пересчиталась сама и записала его автором.

**Как воспроизвести** (проверено на чистой строке):

1. Строка табеля ARSIC SARA, июнь 2026. В базе:
   `hours = {"regular": "40"}`, `insured_hours = 40.00`, `edited_by = null`.
   Подсказка базы: «кто поставил, не записано».
2. Ролью `accountant` изменить **только часы**:
   `POST /timesheets/<period>/cell/ row=<id> kind=sick hours=8` → 200.
3. В базе `insured_hours` стала `48.00` сама. Подсказка ячейки «База взносов»
   теперь: «…· поставил Бухгалтер, 16 августа 2026 г. 14:37».

**Чему противоречит.** Подписи внизу того же экрана, дословно: «Наведите на
ячейку — увидите, кто поставил это число и когда. «Не записано» значит, что часы
попали в табель не с этого экрана и не загрузкой файла.» То есть продукт сам
определяет «поставил» как действие человека — и здесь называет им пересчёт.
И задаче T143, которая заводилась ровно затем, чтобы на вопрос «кто поставил
это число» был честный ответ (issue #52).

**Почему важно.** База взносов — не производная величина, а самостоятельный вход
расчёта: смысл второй половины T143 (issue #54) в том, что она **законно
отличается** от часов. Когда она отличается, спор о взносах решается вопросом
«кто её такой поставил», и продукт даст неверное имя. Бухгалтер, правивший
больничный, окажется автором цифры взносов, которую он не выбирал; настоящий
автор (или факт «никто, посчиталось само») потеряется.

**Что при этом работает и трогать не надо.** Проверено отдельно:

* след правки **часов** точен по ячейкам, а не по строке: директор поставил
  «Отработанные» 90,00, бухгалтер потом «Больничный» 4,00 — и каждая ячейка
  показывает своего автора («поставил Оперативный директор, …14:34» и «поставил
  Бухгалтер, …14:36»), чужую правку на себя не берёт;
* база взносов **задаётся с экрана** и **переживает** последующую правку часов:
  выставленные вручную 80,00 остались 80,00 после того, как другой человек
  добавил 2 часа отпуска. Автоподстановка перестаёт вмешиваться, как только
  число задано руками, — это верно;
* итог строки честно помечается «проверьте» с пояснением «ANDRIC UROS: 94,00 ч
  при норме 88,00 ч».

**Чем проверил.** Настоящая правка ячейки мышью и клавиатурой в живом Chrome
(директор) + запросы `POST /timesheets/<period>/cell/` и `/insured/` под
сессиями `director` и `accountant`; значения и авторы сняты из базы
(`select hours, insured_hours, edited_by from timesheets`), подсказки — с живой
страницы после перезагрузки.

**Готово, когда** ячейка «База взносов», которую человек не задавал, говорит
«посчитано по часам» (или «кто поставил, не записано»), а имя автора появляется
только после правки самой этой ячейки.

### Н7. Демо не показывает ни кассу, ни НДС на том экране, куда приводит посетителя, — и там же противоречит само себе

**Что видно человеку.** Заходишь на демо (`/demo/` → «Enter the demo →»,
`http://127.0.0.1:8104`), открываешь Expenses. Колонки **Till** и **VAT** есть, и
во **всех девяти строках** в обеих стоит «—». Обе возможности этой итерации
(T145 касса, T146 НДС) посетителю не показаны вовсе.

Хуже: строка

> 2026-08-14 · NS1 · Courier fuel · 9,800.00 · Till **—** · VAT **—** ·
> Official · **Fuel paid from the till**

прямо говорит «оплачено из кассы» при пустой колонке «Till». Смотрящий читает это
как поломку продукта, а не как незаполненный сид.

**Как воспроизвести.** `http://127.0.0.1:8104/demo/` → «Enter the demo →»
(входит директором) → Expenses. Список открывается на **текущем** месяце —
августе 2026, — а в демо-сиде касса и НДС проставлены только в июне и июле:

```
demo db: select count(*) всего, count(vat_rate) с_НДС, count(till_id) с_кассой
         from facts where superseded_at is null;
         → всего 30, с_НДС 4, с_кассой 5
demo db: select ... from facts where period='2026-08-01';
         → 9 строк, till_id пусто у всех, vat_rate пусто у всех
```

**Причина (по коду).** `src/demo/dataset.py`, список `EXPENSES`: `till=` и `vat=`
проставлены только у июньских и июльских строк. У августовских — ни одной. И
`note="Fuel paid from the till"` стоит на **двух** строках (2026-06-18 BG1 и
2026-08-14 NS1), у которых `till` не задан ни у одной.

**Чему противоречит.** Правилу владельца о демо: живое демо обязано за один клик
показывать наполненный продукт, и **новая фича поддерживается в демо как часть
Definition of Done** — сид и флоу должны её показывать. T145/T146 приняты, в
журнале записано «Демо показывает кассы и НДС», а на экране входа их нет.

**Почему важно.** Демо существует ради одного клика для заказчика или портфолио.
Смотрящий не станет менять фильтр дат: он увидит две пустые колонки и строку,
которая сама себе противоречит, и уйдёт с выводом, что касса и НДС не работают.
Всё остальное демо при этом в порядке — проверено: `/demo/` по-английски, вход
без регистрации работает всеми тремя ролями (director / accountant / manager),
данные наполнены.

**Чем проверил.** Живой демо-стенд на 8104, поднят профилем `demo` этого же
compose-проекта; вход по всем трём ссылкам лендинга (HTTP 200, роль в шапке
верная); экран Expenses прочитан как есть; сид сверен запросами к базе
`dodo_pnl_demo`; источник — `src/demo/dataset.py`.

**Готово, когда** в августе демо есть хотя бы один расход из кассы и хотя бы один
с НДС, а строка с комментарием «Fuel paid from the till» либо получает кассу,
либо меняет комментарий.

### Н8. Инструкция к загрузке справочника переведена, а названия колонок в ней оставлены русскими — сербскому бухгалтеру она советует неверное

**Что видно человеку.** Английская страница `/directory/expense-items/`, текст
над формой загрузки, дословно:

> The accountant's list of items as an Excel workbook. The product looks for
> columns by name — **"Название", "Код", "Строка P&L"** — column order and extra
> columns do not matter.

Сербская — то же самое:

> Proizvod traži kolone po nazivu — **„Название“, „Код“, „Строка P&L“** —
> redosled i suvišne kolone nisu bitni.

**Как воспроизвести.** Роль `admin`, `/directory/expense-items/`, переключить
язык на EN или SR. Источник — оба каталога переводов,
`src/locale/en/LC_MESSAGES/django.po:2022` и
`src/locale/sr_Latn/LC_MESSAGES/django.po:1995`: в `msgstr` кириллические
названия колонок перенесены из `msgid` как есть.

**Чему противоречит.** Собственному разбору файла. `COLUMNS` в
`src/web/expense_items_upload.py` принимает и `name`, `title`, `naziv`, и
`code`, `sifra`, `kod`, и `kategorija`, `grupa`, `pnl` — на трёх языках, с
нормализацией регистра и диакритики. То есть продукт **умеет** прочитать
сербский файл как есть, а его же инструкция велит переименовать колонки в
русские слова.

И соседнему сообщению того же модуля, которое сделано правильно: отказ по файлу
и в английском, и в сербском каталоге перечисляет все три написания — «Название»,
«Naziv» или «Name». Значит приём известен и применён на одной строке из двух.

**Почему важно.** Первый живой пользователь этой формы — бухгалтер Сербии, и
файл, ради которого заведена вся задача T147, ведёт она. Она прочтёт сербскую
инструкцию, переименует рабочие колонки `Naziv`/`Šifra` в кириллицу, которую у
себя не наберёт, и решит, что продукт требует русских заголовков. Это не
непереведённая строка (класс, знакомый по issue #96) — это **переведённая строка,
дающая неверный совет**.

**Чем проверил.** Страница прочитана на живом стенде на всех трёх языках;
`msgstr` сверены в обоих `.po`; список принимаемых заголовков сверен с `COLUMNS`
в коде, а не по памяти.

**Готово, когда** в переводах названия колонок либо перечислены на всех трёх
языках (как уже сделано в тексте отказа), либо заменены на те, что человек
увидит у себя.

### Проверено и НЕ дефект: прячущие решения T148, кроме подсказки поля

Задание просило особо проверить, не пропало ли что-то из спрятанного. Проверено
руками в живом Chrome, дефектом не является:

* **История периода под свёрткой** — обычный `<details><summary>История
  периода</summary>`. Родной элемент: в дереве доступности присутствует всегда,
  разворачивается Enter/Space, содержимое (750 знаков истории) на месте.
* **Колонка «Спор»** — поле причины и кнопка «Заморозить` **не** скрыты, у них
  снят только контур: `border-color: transparent`, `background: transparent`,
  `::placeholder { color: transparent }`. Из DOM и из дерева доступности ничего
  не уходит. Проверено по вычисленным стилям: при `focus` поле возвращает рамку
  `rgb(227,230,234)`, фон `rgb(251,251,252)` и текст `rgb(22,24,29)`, плейсхолдер
  «из-за чего спор» — `rgb(107,114,128)`; кнопка при `focus-visible` даёт
  `rgb(31,79,216)` и рамку. `tabIndex` у обоих ≥ 0 — Tab доводит до них без
  мыши. Текст кнопки виден и без наведения (`#6B7280` на белом ≈ 4,8:1, проходит
  AA).
* **Пояснение шага показывается только у текущего** (`ol.steps li:not(.now) .what`)
  — на закрытом периоде все три шага `done`, поэтому не показано ни одного, и
  это верно: текущего шага нет.

Единственное прячущее решение T148 с настоящей потерей — подсказка поля формы,
см. Н2.

Замечание без статуса дефекта: у поля причины заморозки нет ни `<label>`, ни
`aria-label`, ни `id` — единственное его имя приходит из `placeholder`
(шаблон зовёт `action.html` с `reason_label=""` и `reason_id=""`). Это было и до
T148; после T148 плейсхолдер стал ещё и невидим до наведения. Имя у поля
формально есть (браузеры берут плейсхолдер запасным), поэтому в находки не
вынесено, но при следующей правке этой колонки метку стоит завести.
